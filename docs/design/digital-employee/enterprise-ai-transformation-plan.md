# 7000 人科技企业 AI 转型与数字员工建设方案

版本：2026-10-09 v1.1  
状态：规划建议，待业务评审；不构成新增功能的开发授权。  
范围：企业提效路线、Forge CRM 已有 Agent/数字员工评审、产品能力与有限试点规划。  
来源：[蓝图原始要求](../../../.specify/sources/20261009-enterprise-ai-planning-review/source.md)、[岗位与行业案例补充要求](../../../.specify/sources/20261009-role-ai-industry-cases/source.md)。

## 1. 结论：围绕工作成果建设，而非围绕技术名称建设

建议建设“员工普惠工具、业务内嵌助手、流程自动化、少量受控 Agent”四类互补能力，用共同的身份、数据授权、连接、评测和运营制度管理。数字员工是有责任人的业务角色与任务容器；Copilot 是人主导的交互方式；Agent 是动态组织步骤的执行方式；Skill 是可复用工作方法；页面只是使用入口。它们不是互相替代的产品选项。

公司 AI 转型的目标，应从“做多少 Agent”改为“哪些工作减少等待、重复录入和核查，哪些业务提高交付、质量和响应速度”。7000 多人的规模需要统一规则和分部门推进，不意味着要为每人开发一个数字员工，也不意味着全部需求由本项目承载。

本项目建议定位为**销售及相关运营场景的 AI 业务应用与受控执行试点**，逐步提供验证过的公共能力。企业办公、研发工具和制造核心系统继续各负其责。暂不把 Forge CRM 改造成覆盖全公司的通用 AI 平台。

## 2. 事实、证据与未知项

### 2.1 已知事实

- 用户明确企业规模为 7000 多人，属于科技企业，并希望结合电子制造业提高员工效率。
- 项目有客户、商机、报价、订单、库存、组织权限及审批相关模块，可作为业务场景基础。
- 商机 Agent 抽屉已有单商机分析、沟通计划、任务记录与确认保存的设计和服务实现。
- 个人 CRM Agent 已有会话、业务检索、引用和待办相关服务实现；查询仍须遵守账号业务可见范围。
- 邮件处理已有连接、增量同步、运行计划、规则、模板、处理动作和任务闭环相关实现。
- 舆情已有来源适配器、聚合事件及处理实现；当前 MAXHUB 场景按用户选择手工触发，不能因本规划改为自动巡检。
- 大宗商品已有行情服务及月度免费来源方案，不属于纯场景卡。具体实时性、授权、币种和单位仍需按来源核查。
- 其他制造业菜单、场景卡和配置入口不能证明 ERP/MES/QMS 数据源已接入。

以上来自文档和源代码抽查，**不是本轮运行验收、生产认证或 7000 人并发容量评估**。未连接真实来源、模拟样例、真实试点和生产运行须分别标识。

## 3. 到底该开发什么：工作类型与实现方式

| 工作特点 | 推荐方式 | 例子 | 必须具备 |
|---|---|---|---|
| 人正在编辑、判断，希望即时辅助 | Copilot/内嵌助手 | 写回复、总结商机、写代码、解释报表 | 当前上下文、可编辑草稿、来源、人工责任 |
| 输入和步骤明确，主要搬运或核对 | API/规则/工作流自动化 | 邮件同步、交期逾期提醒、库存核对、BI 报表定时获取 | 可靠连接、规则、调度、防重、失败恢复 |
| 需要理解非结构化资料，但流程固定 | AI 辅助工作流 | RFQ 抽取→核查→草稿→审核 | 结构化校验、缺失提示、明确状态 |
| 需要根据查询结果动态选择后续步骤 | 受控 Agent | 多轮商机调查、质量事件材料收集 | 白名单工具、停止条件、预算、证据、接管 |
| 方法重复，可标准化表达 | Skill/模板 | 8D 初稿方法、报价检查表、日报分析方法 | 版本、适用范围、样例、维护人、评测 |
| 业务人员要配置和观察执行 | 业务应用页面 | 邮件队列、任务详情、场景配置 | 业务动作、运行记录、权限与反馈 |
| 检测、优化、预测要求专门算法 | 专用算法＋业务系统 | AOI 缺陷识别、APS 排程、销量预测 | 专业验证与业务约束；大模型辅助解释 |

Skill 本身不提供调度、凭据托管、组织授权、事务和审计，不能用一个 SKILL.md 替代企业运行服务。Agent 的工具调用协议也不是权限控制。固定任务先用确定性方法，仅当动态规划带来可测增益时升级为 Agent；这一取舍参考 [Anthropic 的工作流与 Agent 区分](https://www.anthropic.com/engineering/building-effective-agents)。

每天登录 BI、打开固定报表：先查 BI API/订阅/导出能力；没有接口再考虑浏览器自动化。网页用于配置时间、页面、账号授权及查看日志，执行器放在允许访问 BI 的运行环境。只有页面不稳定、路径不确定时才考虑视觉电脑操作。验证码/MFA、凭据失效转人工，不能把 Skill 当作无人值守机制。此项当前是候选方案，未实施。

## 4. 企业建设地图：谁使用，在哪里使用

| 层次 | 使用人群 | 能力 | 建设策略 |
|---|---|---|---|
| 员工普惠 | 有相关工作的办公员工 | 写作、翻译、会议、表格、资料整理 | 优先评估成熟办公工具；受控接入知识，按岗位开放 |
| 专业岗位 | 研发、销售、采购、财务、质量 | 编码测试、RFQ、比价、核对、8D | 成熟专业工具与业务内嵌能力结合 |
| 业务闭环 | 部门协作与运营人员 | 邮件、交期、客诉、库存异常、审批 | 项目承载已具备数据和接口的闭环 |
| 现场智能 | 工程、产线、设备人员 | 视觉检测、预测维护、排程 | 与专用系统集成；不交给通用 LLM 决定放行 |
| 共同治理 | IT、安全、业务运营 | 身份、模型路由、知识、连接、评测、成本 | 先复用企业现有服务，仅补缺口 |

入口不要求统一为聊天窗口：员工常用工具中辅助，业务页面中辅助，数字员工菜单中处理队列，管理页面中看配置与运行。企业可有统一能力目录和授权入口，但不强迫各场景使用相同页面、字段和状态机。

## 5. 对原方案的 Review 与调整决策

| 原方案/现状 | 判断 | 本次建议 |
|---|---|---|
| 制造业场景清单覆盖广 | 保留，作为候选地图 | 增加成熟度和优先级；停止把全清单作为开发承诺 |
| 总方案仍写原型、未接真实邮箱 | 与当前实现状态不一致 | 历史原型范围保留；新增当前状态及企业建设层次 |
| Agent、数字员工各有入口 | 合理，但容易重复造能力 | 统一身份/连接/证据等契约；业务流程分别适配，暂不做大规模代码合并 |
| 单商机抽屉和个人会话工作台 | 使用场合不同，应保留 | 抽屉处理当前对象；工作台处理持续问答；共用可复用运行能力 |
| 所有事项汇到统一任务中心 | 适合总览，不适合统一处理 | 总览统一责任、期限、来源；邮件、舆情、质量采用各自处理流程 |
| 统一启用评分 80 分 | 不能替代上线判断 | 评分用于辅助排序；权限、凭据、评测、接管等关键项采用必须满足的条件 |
| 高风险动作要求确认 | 保留 | 自动回复仍需独立授权和受限模板；超范围转人工，不靠模型自评分放行 |
| 行情、舆情和制造菜单 | 接入与成熟度不同 | 展示等待配置/演示/试点/生产状态，禁止把示例当采集结果 |
| 先扩功能再评估价值 | 易分散投入 | 为现有邮件与商机建立基线和效果数据，再选择新增闭环 |

**建议建设**：场景能力登记、证据与结果核验、评测与成本统计、责任人与接管机制；复用已有公共能力。  
**建议集成**：企业身份、文档平台、办公/研发 AI 工具、现有审批与通知。  
**建议暂缓**：通用无边界电脑操作、自由生成并执行代码、模型直接库存过账/付款/生产放行、全公司自主多 Agent 集群。  
**建议减少**：无数据源的空功能承诺、重复聊天页面、只有摘要而没有处理结果的演示。

这是产品层决策建议，不宣称已补齐相关代码。

## 6. 优先场景与推荐试点

岗位级任务、行业证据、八个场景包及开源参考见第 14 章；本章保留已有试点优先级。

### 6.1 先筛选，再排序

用频率与人工耗时、价值和可验收性、数据就绪、流程稳定性、风险及运行成本逐项评估。安全和必要接口不过关的场景暂不进入上线候选，即使价值高。每个候选同时比较“不做、普通自动化、购买成熟工具、定制 AI”四个选项。

### 6.2 当前项目优先级

| 优先级 | 场景 | 首个可验收交付 | 主要依赖 | 结果指标 |
|---|---|---|---|---|
| A | 邮件收件到业务处理闭环 | 邮件→分类→分派→回复/暂挂→结果核验→关闭 | 授权邮箱、规则与责任人、发送许可 | 净处理时间、漏办、逾期、重复发送、误分类 |
| A | 商机跟进辅助 | 授权证据→建议→确认待办→跟进结果 | CRM 数据质量、现有 Agent | 净准备时间、引用正确、待办执行率 |
| B | 采购交期异常协同 | 订单＋供应商回签→差异→催办草稿→确认→结果 | 采购订单和回签数据、接入权限 | 差异发现及时率、催办耗时、异常闭环率 |
| B | 客诉/质量事件材料与 8D | 客诉＋检验记录→材料包→8D 草稿→复核 | QMS/工单/追溯数据，不只 CRM | 资料准备时间、遗漏、复发与关闭质量 |
| B | 经营 BI 异常解释 | 受控指标→差异→证据→解释→责任事项 | 指标口径、BI 只读接口 | 报告准备时间、口径一致、异常处理率 |
| C | BOM/ECN 影响、齐套与排程 | 专业系统计算→影响解释→处理建议 | PLM/MES/ERP/APS 与算法 | 工程/交付指标，须单独定义 |

企业侧建议并行做一个**研发工具小规模试点**：按代码安全边界使用成熟工具，评估开发、测试、评审与返工总时间；不用先在 CRM 重造编码助手。

第一批建议只保留两个已有项目试点（邮件、商机）和一个企业侧研发工具试点。采购/质量/BI 三者中，再按数据就绪和业务价值择一进入下一批。试点人数和部门在盘点后定，不在此虚构公司人员结构。

### 6.3 邮件案例：分清自动执行、人的决策和业务完成

1. 连接授权邮箱，按配置同步；原邮件与业务处理状态分开。
2. 规则先识别已知来源与类别；模型补充提取、摘要和回复草稿。
3. 指定队列、处理人及期限；未知归属/低证据质量进入复核。
4. 操作按邮件情况提供回复、转派、关注、备注、等待外部、暂挂、忽略等；禁止强套给其他场景。
5. 发送默认人工确认；受控自动回复仅在明确启用、限定模板/范围/限流后执行。商业报价、赔付、交期承诺等仍走业务审核。
6. 发出邮件须有发送结果；发送失败不能标记为已回复。仅 SMTP 接受不代表对方收到或问题解决。
7. 用户“已处理”须记录处理结论；关联业务仍有待办时说明剩余责任。定时结束等待可重新提醒，不能自动认定业务已完成。
8. 逾期升级到接管人；删除按当前回收站策略执行。审计保留来源、操作者、状态变化及结果。

这是在已有实现上补充的目标验收口径。哪些已经覆盖、哪些需新增，下一有限切片逐项核查后确定，不由本规划直接宣告完成。

## 7. 应补齐的公共能力与边界

| 能力 | 职责 | 对已有项目的处理 |
|---|---|---|
| 场景与工具登记 | 目标、输入、输出、责任、版本、风险、适用范围 | 补充现有场景卡，给出实际成熟度 |
| 身份与数据授权 | 员工身份、部门/法人范围、共享资源授权 | 复用 RBAC，检查知识检索和工具层一致性 |
| 连接管理 | 账号授权、凭据、健康、范围和撤销 | 复用连接中心，不重建邮箱配置体系 |
| 知识与指标口径 | 文档版本、所有者、权限、引用、指标定义 | 从小范围已维护知识开始，避免全盘导入 |
| 运行控制 | 调度、防重、重试、取消、超时、接管、恢复 | 先盘点现有能力；按场景缺口补齐 |
| 动作执行 | 草稿、审批、执行、结果核验 | 通过业务服务执行，不绕过库存/订单规则 |
| 评测与观测 | 样例、回归、模型版本、运行结果、费用 | 建最小评测和运营报表，再按证据扩展 |
| Skill/模板资产 | 工作方法、样例、版本、发布和停用 | 维护业务方法与工具授权的分离 |

不要求此刻建设庞大平台或采购特定框架。先让两个试点共享必要的公共能力；稳定且有第二个使用者后，再提炼为企业资产。

## 8. 安全、授权及自动化等级

| 等级 | 行为 | 放行条件 |
|---|---|---|
| 辅助读取 | 搜索、分析、整理资料 | 已授权范围、证据来源、敏感内容控制 |
| 辅助起草 | 写邮件、报告、单据草稿 | 草稿标识；正式发布/写入由人确认 |
| 有限自动执行 | 内部标签、限定提醒、已授权模板回复 | 明确动作范围、测试、限流、防重、可停止和接管 |
| 正式业务变更 | 单据提交、状态改变、库存动作 | 业务接口校验、审批/职责分离、结果核验 |
| 高影响决策 | 付款、生产放行、召回、人员处置 | 不纳入首批自主执行；由授权人员决策 |

风险还取决于对象敏感度、数量、影响范围、可恢复性，不能因“可逆”就默认低风险。模型置信度只辅助复核排序，不扩大执行权限。

邮件、网页、附件和检索结果都是不可信输入，其内容不能授予工具权限。读取权限与执行权限逐次核验；共享邮箱用受控服务身份及已授权业务范围，不借用个人账号实现全公司访问。日志与评测集最小化保存敏感文本；密钥不进入页面、Skill、普通日志或方案。

对模型/提示/知识/工具变更做小范围评测再发布；支持停用单场景、撤销工具、人工接管和恢复。正式单据、库存流水与审批记录仍由业务系统保存。具体数据出域、保留期、供应商协议与本地/云部署必须结合企业政策另行确定，参考 [NIST 生成式 AI 风险管理 Profile](https://www.nist.gov/publications/artificial-intelligence-risk-management-framework-generative-artificial-intelligence)，本规划不替代合规评审。

## 9. 组织转型与日常运营

建议采用中央小团队与业务共同负责的模式，人员配置按现有组织再定：

- 企业负责人：确定价值目标、预算边界和优先流程，解决跨部门职责问题。
- 中央 AI/IT 能力团队：共享连接、授权、模型、评测、发布与成本，复用已有基础设施。
- 业务流程负责人：定义怎样算完成、谁审批、谁接管，对业务结果负责。
- 场景产品负责人：组织样例、培训、反馈、迭代和效果统计。
- 安全/数据负责人：审查资源范围、出域和敏感数据，明确数据所有者。
- 部门骨干：把有效方法整理为模板/Skill，辅导同事，报告失败案例。

培训按岗位任务开展：如何给上下文、核验来源、保护资料、确认执行、处理异常。不要只培训提示词，也不以 AI 调用次数考核员工。AI 节省的时间用于客户响应、质量改善和研发验证；时间节省不自动等于可裁撤岗位或财务收益。

每个试点每周评审失败、积压、误报与反馈；每月检查价值和成本，决定继续、收紧、停止或扩围。事件有指定接管人和恢复步骤，不能把故障转成无人处理的新待办。

## 10. 如何证明提效

上线前采样实际工作，记录任务难度、准备/操作/等待/核查/返工时间和质量。上线后采用类似任务的对照或分批试点，避免只凭主观问卷。研发尤其应同时计算评审和返工。

| 指标 | 定义与用途 |
|---|---|
| 净节省时间 | 原人工主动处理时间－AI 后准备/操作/核查/返工时间；等待时间另统计 |
| 合格完成率 | 符合质量与授权要求的完成任务/有效试点任务 |
| 一次采纳率 | 无重大修改被采用的建议；不是最终正确率替代 |
| 任务闭环率 | 按场景完成标准关闭且结果可核验的任务比例 |
| 可靠性 | 失败、重复动作、漏办、误分类、恢复成功与接管耗时 |
| 业务改善 | 响应时效、交期异常、质量材料准备等，采用业务负责人口径 |
| 单个合格任务成本 | 模型、订阅、连接、基础设施、维护和人工复核成本/合格任务 |
| 持续采用 | 目标岗位完成有效工作的人数与反馈，而非单纯登录率 |

收益估算使用本企业测得的有效工作量和净节省；时间价值与实际现金收益分别列示。客服领域的 [Generative AI at Work 研究](https://arxiv.org/abs/2304.11771) 发现效果存在人员差异，这说明应按岗位和任务验证，不能直接复制外部平均提升数字作为本公司目标。

建议试点验收至少包含正常输入、资料缺失、过期知识、错误分类、重复事件、权限撤销、外部指令注入、模型/接口失败、取消、发送失败及接管。抽样量与质量阈值由任务风险和基线确定；越权和未经授权对外动作是阻断项。连续两轮效果无改进或成本不可承受时收缩/停止，先排查数据及流程，不靠换更贵模型掩盖问题。

## 11. 推进路线与退出条件

以下为建议的阶段节奏，非已批准工期；资源与接口未盘点，不能承诺上线日期。

| 阶段 | 建议节奏 | 范围 | 完成/退出条件 |
|---|---|---|---|
| 盘点与基线 | 起步约 2–3 周 | 岗位工作、工具、数据、接口、政策；选择试点 | 有业务责任人、样例、完成标准、基线与授权边界 |
| 现有能力试点 | 随后约 4–6 周 | 邮件、商机；企业侧研发工具 | 质量可接受、无授权越界、可接管、能计算成本和净节省 |
| 选择性扩展 | 随后约 6–12 周 | 在采购/质量/BI 中选一个闭环；提炼复用能力 | 新数据源可用、共性复用有效、业务指标得到验证 |
| 部门复制 | 经试点验证后 | 扩至适用部门及业务，完善培训运营 | 容量、隔离、恢复与值班满足扩围需要，成本可控 |
| 受控自治 | 满足动作条件后 | 逐动作提升自动执行范围 | 每个动作通过风险/评测/恢复与授权检查，随时可撤销 |

并发试点数量受团队承载能力限制。每阶段交付后停在对应评审点，以具体下一任务继续；企业蓝图不授权持续开发全部场景。

## 12. 下一阶段建议：有限范围的“现有试点准备与差距核查”

建议下一次明确任务仅包含以下四件事：

1. 邮件和商机分别列出已实现、待配置、待验证、缺失能力；用真实授权样例核查一次完整链路。
2. 给两个场景补齐责任人、完成标准、接管、基线及测量表。
3. 盘点员工办公/研发工具及采购/质量/BI 数据，选择下一场景，比较购买/集成/自研。
4. 将确需补齐的功能拆成有限切片，逐项写验收和验证等级；未选中的场景继续候选状态。

本轮只完成方案评审与优化，不新增页面、接口、模型调用、自动化任务、邮箱动作或数据库变更。尚需明确试点部门、预算、数据政策及业务负责人；它们是后续部署决策条件，不影响本方案交付。

### 14.2 六条行业经验如何转成产品决策

1. **嵌入专业工作环境**：奔驰研发案例与西门子工程案例说明辅助可放在已有工具链中。建议研发优先选成熟 IDE 工具，CRM 不另造代码工作台。[奔驰案例](https://github.com/customer-stories/mercedes-benz)、[西门子案例](https://press.siemens.com/global/en/pressrelease/siemens-and-microsoft-scale-industrial-ai)。
2. **围绕一次工作交付连接上下游**：Morgan Stanley 的会议、草稿、CRM 记录链可借鉴为客户会议→确认行动→跟进，先取得会议处理授权。[企业公告](https://www.morganstanley.com/press-releases/ai-at-morgan-stanley-debrief-launch)。
3. **自助与人工服务并存**：Wiley 客服和 IBM AskHR 均披露常规事项与复杂事项分工。建议标准政策问题先做辅助，明确转人工，并测量转交后是否解决。[Wiley 案例](https://www.salesforce.com/customer-stories/wiley/)、[IBM 案例](https://www.ibm.com/case-studies/ibm-askhr)。
4. **制造能力建立在业务数据之上**：美的、华为/长安公开场景依赖图纸、工厂/质量数据。建议质量先做证据包，齐套先确保库存、BOM 和在途可靠；不凭 LLM 推断现场真实情况。[美的案例](https://www.midea.com.cn/zh/about-midea/news/_16)、[华为/长安案例](https://e.huawei.com/cn/case-studies/industries/manufacturing/202412-changan-yubei-new-factory)。
5. **知识资产化是独立价值**：Eaton 的 SOP 整理和 Lilli 的知识综合提示可以先用 AI 形成经审核的方法和资料，再复用于服务与培训。模板、文档版本和维护人比增加聊天入口更有价值。[Eaton 案例](https://www.microsoft.com/en/customers/story/19830-eaton-microsoft-365-copilot)、[Lilli 介绍](https://www.mckinsey.com/about-us/new-at-mckinsey-blog/meet-lilli-our-generative-ai-tool)。
6. **成熟案例也要验证安全与归因**：Lilli 后续公开确认并修复漏洞，因此不能仅凭上线人数证明治理成熟。部分案例混合产品采用、整体系统 ROI 和计划收益，本方案不把它们作为 Agent 独立收益。[安全声明](https://www.mckinsey.com/about-us/media/statement-on-strengthening-safeguards-within-the-lilli-tool)。

### 14.3 八个具体场景包：用于下一步选择和访谈

以下均为规划候选；只有邮件、商机可先基于已有代码核查，其他不宣称已经接入。外部案例支撑模式选择，业务规则由本企业确定。

#### ROLE-01 研发变更与验证助手

- 工作起点：已批准需求/缺陷、指定代码库和允许读取的文档。
- 处理：定位相关模块→提出修改→生成必要测试→在隔离环境执行→整理差异与失败。
- 交付：可评审改动、验证记录、未解决风险；研发人员决定合入和发布。
- 借鉴：CASE-01/02 的工具链集成；代码生成量不能代替质量。
- 首次试点：限定一种仓库和常见任务，对比开发＋测试＋评审＋返工总耗时；禁止自动生产发布。

#### ROLE-02 客户会议到商机跟进

- 工作起点：经授权会议纪要或跟进记录、当前商机与客户资料。
- 处理：提取诉求/竞争/问题→列事实与待核实项→生成行动草稿→人确认负责人和日期。
- 交付：可追溯商机摘要与正式跟进任务；结果写回原业务对象。
- 借鉴：CASE-03；首期不承诺自动录音转写，先处理已有文字资料。
- 首次试点：复用商机 Agent 和个人工作台，测量引用准确、核查耗时及后续执行。

#### ROLE-03 邮件与售后工单处理

- 工作起点：授权邮箱，产品/订单/政策依据；共享邮箱明确队列责任。
- 处理：分类→补查依据→分派→回复草稿/等待/升级→核验结果→结论关闭。
- 交付：客户答复、正确转派的客诉或已记录结论的任务；发信成功不代表客诉解决。
- 借鉴：CASE-04 的可信知识与人工处理复杂事项，结合已有邮件独立策略。
- 首次试点：一类常见业务邮件；复核样例含拒绝承诺、超期、重复与发送失败。暂不默认开外部自动回复。

#### ROLE-04 供应商回签与交期异常

- 工作起点：采购订单、供应商确认邮件及承诺交期；只读当前订单。
- 处理：抽取回签→按行核对料号/数量/价格/交期→按需求日识别差异→催办草稿。
- 交付：差异清单、责任事项、确认后的催办及供应商反馈；改变采购订单另走审批。
- 借鉴：CASE-10 的采购任务分解，非可直接套用的成熟收益证明。
- 首次试点：单个业务队列，覆盖部分回签、分批交货、多个交期和币税差异；订单接口未就绪则暂缓。

#### ROLE-05 客诉事件证据包与 8D 草稿

- 工作起点：客诉描述、检验/返修、产品版本、批次追溯和历史事件。
- 处理：整理时间线→关联证据→区分现象、假设、已确认根因→起草 8D 与缺失清单。
- 交付：可复核证据包和报告草稿；质量工程师确认根因、措施及验证。
- 借鉴：CASE-07/09 的跨系统数据链，仅借鉴数据与协同原则。
- 首次试点：选一种失效类型；禁止自动质量放行、召回、赔付或冻结库存。

#### ROLE-06 财务核对与标准作业知识

- 工作起点：同法人订单、收货、发票与财务规则，或经授权财务操作记录。
- 处理：代码做数量/金额/税率及勾稽→AI 整理不一致说明；或生成 SOP 初稿并由财务审核。
- 交付：差异责任队列、证据链接、SOP 版本；审批、过账及付款由财务系统执行。
- 借鉴：CASE-06 文档整理与 CASE-11 产品能力；不混淆文档提效与三单自动付款。
- 首次试点：财务数据未准备好时先做 SOP，不开放模型自行计算账务或生成任意查询。

#### ROLE-07 HR/IT 员工服务

- 工作起点：受维护的制度、地区/组织适用范围和已授权流程。
- 处理：检索现行依据→回答/指引→选择已开放申请→复杂事项转专家。
- 交付：有来源的答复、正确创建并可追踪的服务工单；涉及个人信息重新授权。
- 借鉴：CASE-05 的常规与复杂服务分工；避免强制撤掉人工渠道。
- 首次试点：制度问答或报修分类二选一；不自动作招聘淘汰、薪酬、处分或心理健康判断。

#### ROLE-08 经营异常分析与行动

- 工作起点：已定义指标及只读数据服务；期间、法人、币种、单位、版本明确。
- 处理：规则确定差异→查询分解→模型解释可见证据→标记未知原因→生成会议行动草稿。
- 交付：图表、可复算数字、来源及责任事项；没有因果证据不得写成根因。
- 借鉴：OSS-05 的交互探索形式；业务指标口径不能由示例项目替代。
- 首次试点：选销售订单或库存一个主题；已有 BI 无接口时先评估导出/订阅，再考虑浏览器自动化。

### 14.5 建设组合与新的有限下一步

- **继续已有试点**：邮件闭环与商机辅助，补效果测量和完成证据。
- **企业侧评估**：研发成熟工具；测试、产品/项目方法随研发试点联动，不开发独立重复入口。
- **横向普惠候选**：HR/IT 或 SOP 知识，适用知识已维护且权限明确时可推进；它们不必依赖制造系统全部接入。
- **下一业务闭环择一**：采购回签、质量证据包、财务核对、经营 BI，按数据和负责人准备度选择，不同时启动。
- **暂缓深度自治**：排程发布、设备操作、财务支付、质量放行及通用电脑无人值守。

下一次可交付一份“岗位场景筛选表”：每岗位收集 2–3 个真实任务样例及实际耗时，填责任人、数据、工具、风险、建设方式和完成标准；再决定有限切片。每岗位样例数是访谈建议，不是已批准验收样本量。

复用候选是场景卡、证据、评测和工具契约；采购订单规则、质量根因判定、财务口径、HR 地域政策属于业务专属。跨项目验证前不晋升为通用标准。此次完成文档后停止，不顺带实施八个场景。
