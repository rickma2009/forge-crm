## 同条件重新查询回归（2026-10-03，TC-20）

新增测试发现两页的 effect 仅依赖条件字符串与页码，同条件再次查询不重新取数，空条件重置也不会刷新。最初运行 2 项新测试失败，3 项旧测试通过；缺陷为预期 2 次请求但只有初始 1 次。修正由页面增加显式刷新序号，查询/重置触发重新请求，输入草稿和库存计算不变。

`pnpm --filter @forge-crm/web test -- src/showcase/InventoryStockPages.test.tsx`：5 项通过（3.98 秒），包含原有联动、筛选、导出及事务行号用例。新的两项分别检查初始加载后同条件查询、空条件重置都产生新的调用，URL 不变。

真实浏览器命令：`PLAYWRIGHT_MODULE_PATH=<现有 Playwright 入口> node scripts/check-inventory-refresh-browser.mjs`。本机 1440×1000 桌面两页各执行“查询、查询、重置”，每次先捕获点击之后的新 GET，再核对该请求返回 200 和 items 数组；三次参数相同，页面运行异常为空。初版脚本只等待响应，随后改为请求与响应关联并重新执行通过，避免旧在途响应造成假通过。Browser plugin not available，使用已有 Chrome/Playwright。没有修改库存数据，没有重新声称窄屏排版或后端聚合已在本轮验证。

复用结论：查询值与刷新动作是不同语义。目标项目可用显式刷新序号、查询事件或查询库 refetch，不能仅把 filters 设置为相同值就假定网络会重发。见[React 状态归属案例](../training/cases/react-state-ownership.md)与汇总下钻验证模板。

边界：验证的是页面组件如何处理模拟 Promise 的时序，不证明真实请求已经 Abort、服务端停止计算、加载超时策略或多页导出一致性。当前实现忽略过期结果，但没有因为本次测试而新增网络取消能力。

## 全部分页导出完整性回归（2026-10-03，TC-23）

原库存 allPages 仅按第一响应的 totalPages 循环，后页为空或 total 改变时仍生成 CSV。两项新页面反例首次均失败（未出现错误提示）。改为汇总/明细共同调用公共 loadAllGridRows，沿用已提交筛选和精确物料/币别条件；每次请求 100 条，不再另写 200 条循环。总数变化或累计条数未达到总数却遇到空页时抛错，页面显示错误并恢复导出按钮，不创建下载 Blob URL。

最终执行相同两文件命令：16 项通过（页面 12 + 公共导出 4，7.53 秒）。新增两项直接验证汇总导出错误、无文件以及按钮恢复。现有成功分页夹具原为“total=1、totalPages=2、所有 items 为空”，与成功业务不一致；已改为两页各一条、total=2，保留原有筛选继承断言。明细分支复用同一公共函数，本轮未新增其单独失败注入。

范围：公共工具只发现数量变化、空缺页或累计超出总数，不是数据库快照；总数不变但内容替换、稳定排序失效造成等量重复/遗漏仍可能漏检。大数据量内存、权限变更、请求取消和服务端快照另行验证。本轮未改公共算法、服务端查询或库存数据。
## 公共分页总数异常回归（2026-10-03，TC-24）

继续检查公共 loadAllGridRows，发现它信任回调声明的 number，而 JavaScript 回调仍可能返回小数、非有限数或其他类型。新增 7 类反例：-1、1.5、NaN、Infinity、undefined、null、字符串 "2"。首轮均失败：小数、非有限数、缺失值和字符串触发第二次请求；负数/null 虽停止，但没有明确的无效总数错误。

回调夹具只提供第一次无效响应，第二次立即抛出哨兵错误，因此测试有确定上限，不会为复现问题而无限请求。修复为先要求 total 是非负安全整数，再比较总数及累计条数。合法 total=0/items=[] 正常返回，且不修改调用方 URLSearchParams。

最终同两文件命令共 24 项通过（公共导出 12、库存页面 12，8.77 秒）。该工具同时由客户、物料和库存导出调用，本轮不修改这些调用的正常查询参数或业务字段；新增验证集中在公共工具与库存回归，没有重新执行客户/物料浏览器流程。NaN/Infinity 是 JavaScript 回调边界夹具，不声称标准 JSON 能传这些字面值。完整响应 schema、最大数据量、请求超时、同总数记录替换和服务端快照仍不在本次证明范围。
