# 从销售出库提炼过账不变量

来源：Forge CRM 的销售与库存模块，2026-10-03 源码、针对性单元测试及后续隔离数据库测试。本案例用于识别可复用的事务边界，不是完整库存产品方案；并发证据限于下文明确列出的场景。

## 先分清业务事实

本项目销售出库审核时过账：校验单据和来源订单、按仓库批次扣库存、追加负向流水、更新订单行已出货数量及履约状态，保存本次出库成本并记录操作事件。冲销增加反向流水，恢复库存与订单可出货量，原流水保留。

这些是当前项目选择；其他系统可能分离审核和过账，允许部分冲销或采用不同计价法。跨项目采用时先定义业务规则，不直接复制本项目状态枚举。

| 不变量 | 当前实现证据 | 验证范围 |
|---|---|---|
| 同一余额维度唯一 | `tenantId + legalEntityId + warehouseId + itemCode + batchNo` 唯一键 | Schema 声明已核对；本轮不重新执行迁移 |
| 库存模块负责余额与流水 | 销售服务向 SalesPostingService 传入同一个事务客户端 | 源码调用关系 |
| 批次属性一致 | 批次物料必填批次，非批次物料不带批次 | 模拟事务反例通过 |
| 数量与金额不可超扣 | 移动平均计算及带版本、数量/金额条件的更新 | 计算和服务单元测试；不是实际并发调度 |
| 流水可追溯单据行 | sourceOrderId/sourceLineId/lineNo、法人仓库批次及事务类型 | 服务单元测试核对写入参数 |
| 同一来源行/事务类型不重复 | 流水唯一键 `(sourceLineId, movementType)` | Schema 声明；数据库冲突回滚仍需集成测试 |
| 冲销沿用原出库成本 | 读取出库行保存的 costAmount，确认存在原出库流水后写反向流水 | 模拟事务验证不会按当前移动平均重计成本 |
| 库存与订单同成同败 | outboundCommand 在 Serializable 事务内调用库存、回写订单、单据和事件 | 源码结构；后续数据库测试补充第二行失败的整单回滚 |

## 一笔可手算的例子

同一法人、仓库、物料、批次当前数量 8、金额 80；出库 2，成本 20。过账后余额 6/60，流水数量 -2、金额 -20，订单行累计出货增加 2。

如果库存之后发生其他入库，原单冲销仍恢复原出库数量与原成本，不按新的平均价计算。练习中可把保存成本设为 25，验证冲销增加 2/25，而不是按当前 8/80 重新算出 20。服务当前检查原流水存在，但未比较原流水金额与保存成本是否一致；这不证明历史数据损坏时也能自动恢复正确。

对账应限定相同粒度：期初余额 + 期间有效事务净变动 = 期末余额。销售金额不是库存成本，不能直接拿订单售价对库存余额金额；不同币别也不能直接相加。

原金额测试的名称曾称“精确仓库与批次”，实际只调用纯金额函数；本轮将名称改成它真正覆盖的计算范围，并由新服务测试补齐维度检查。测试名、注释和绿灯都不能扩大实际断言的证明范围。

后续实际执行 `node scripts/test-sales-posting-integration.mjs`：随机隔离 PostgreSQL 数据库中 3 项通过，覆盖第二行库存不足后的整单回滚、两笔受控竞争仅一笔提交及补库后的显式重试、顺序重复审核/冲销与余额净流水对账。库存由真实入库单建立，没有直接改共享余额。测试库清理已独立确认，详见[数据库验证记录](../../testing/sales-posting-integration.md)。运行器使用当前 schema 和销售专项约束，不代表完整迁移验证。

随后扩展为 5 项并通过同一命令：增加真实 CHECK 约束拒绝流水插入的回滚，以及同键同时审核。后者一笔提交、一笔并发冲突，但仅一条负向流水和一个对应事件；冲突请求用原键显式重试后快照不再变化。教学时要区分“重复请求不会重复业务影响”与“每个并发请求都立即成功”，本项目证据只支持前者及已描述的重试路径。

## 幂等与并发仍要继续验证的地方

当前出库命令按 applicationId、actorId、requestKey 查操作事件，重复键校验单据 ID 和动作；重复请求返回当前单据状态。它没有比较完整请求内容，也不重放原始响应快照。因此不能宣称“相同幂等键的任何内容差异都会拒绝”或“重试总返回原响应”。跨操作者的重复由单据状态/版本及流水唯一约束参与保护，不能只靠操作者作用域内的请求键。

Serializable 隔离与条件更新不等于自动重试或所有竞争场景已验证。后续数据库证据已覆盖本项目两笔抢余量、第二行失败回滚、流水插入被拒绝、同键同时审核及顺序重复审核/冲销；目标采用仍要按[过账评审模板](../../../_methodology/templates/transactional-posting-review-template.md)执行自己的测试，并补同键不同内容及提交成功后断线等异常响应场景。使用隔离数据库和合成数据，不直接运行演示 Seed 去修改共享库存。

## 团队练习与可复用边界

先让学员画出单据、余额、流水和来源订单的原子写入范围，再用上述例子计算正向与冲销结果。提交字段维护权、作用域、幂等载荷策略和失败注入矩阵，逐项标记“源码证据 / mock 已验证 / 数据库待验证”。评审重点是能否指出证据不足，而不是是否复述“必须用事务”。

可复用的是余额唯一维度、追加流水、来源追溯、原子回写、并发条件与按原成本冲销的评审方法。仓库权限、批次政策、币别、审核人员分离、计价法和具体幂等响应语义由目标业务确认。当前材料为培训候选，未进行团队试讲或跨项目采用。
