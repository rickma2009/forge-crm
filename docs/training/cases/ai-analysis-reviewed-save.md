# AI 应用练习：可追溯的分析草稿与人工确认保存

## 目标与准备

通过 Forge CRM 商机分析案例，练习把模型调用接入业务系统：定义资料范围、持久化任务、检查输出、保留依据、人工审阅后保存，并为其他业务对象划清复用边界。预计 45—60 分钟，适合具备后端接口和事务基础的开发者。

本案例于 2026-10-03 核对下列源码，执行两组单元测试及独立临时库集成测试，状态为项目内实现案例，尚无独立项目采用证据。没有运行真实模型或浏览器测试。准备本仓库及依赖即可阅读和运行下述单元测试；这些单元测试模拟网络，不需要真实模型凭证。

来源与入口：

- [功能与接入说明](../../ai/opportunity-analysis.md)：已确认的业务范围与部署说明；其中历史验收记录保留其原日期，不代表当前状态。
- [任务与确认服务](../../../packages/server/src/ai/ai-analysis.service.ts)：快照、任务、工作进程及确认事务。
- [接口授权](../../../packages/server/src/ai/ai-analysis.controller.ts)：查看、AI 分析和新增分析的权限检查。
- [结果校验](../../../packages/server/src/ai/analysis-domain.ts)与[模型适配器](../../../packages/server/src/ai/ai-provider.ts)。

## 从代码提炼的责任边界

| 环节 | 本项目实现事实 | 其他项目采用时需要决定 |
|---|---|---|
| 取数 | 服务端按商机及应用范围形成资料快照，并保存快照哈希 | 目标对象的数据范围、行级权限、敏感字段、大小限制 |
| 生成 | 持久化任务从 QUEUED 进入 RUNNING，再到 SUCCEEDED 或 FAILED；worker 领取任务后重新检查查看与 AI 分析权限 | 队列规模、并发、超时与费用策略，执行时是否还需重查对象权限 |
| 校验 | 检查结果结构、引用 ID；FACT 必须有依据，历史分析不能成为其唯一依据 | 目标业务结果结构、有效来源类型、需要人工复核的内容 |
| 审阅 | 原始结果与人工确认结果分别保留；成功生成尚不等于正式分析已保存 | 谁可审阅、能修改什么、哪些动作需要审批 |
| 保存 | 本人确认；确认接口额外检查新增分析权限；锁住任务并检查是否已有 analysisId；资料变化默认拒绝，显式接受旧快照才继续 | 幂等范围、资料过期处理、业务状态变更与审计要求 |

生成状态和保存状态分开：`SUCCEEDED` 表示已生成结果；`analysisId/confirmedAt` 表示已确认保存。不要为便于画图而虚构代码中不存在的 `CONFIRMED` 任务状态。关闭弹窗不会取消任务；页面上未确认的人工修改也不是服务端自动保存。

本实现的确认路径创建分析记录并关联任务，不调用人工分析中可能存在的阶段回写逻辑。是否允许 AI 改订单、库存、审批状态，应由新业务重新设计，不能由此案例推断授权。

## 可复现任务

1. 从接入说明写出六条验收：生成不直接保存业务记录、资料可追溯、无效引用失败、资料变化需处理、重复确认不重复写、权限不足拒绝。给每条找到源码位置。
2. 沿 `start → tick → confirm` 阅读服务，画出任务状态与保存状态；注明“模型输出不合格”“生成后资料更新”“用户重复点击确认”三个分支。
3. 阅读 `parseAnalysisResult`。用“引用一个真实跟进 ID，但写出资料并未支持的结论”解释：结构校验和引用存在性不等于内容真实性。提出人工审阅清单，避免声称提示词已经消除幻觉或提示注入风险。
4. 在仓库根目录运行以下最小测试，并记录自己的日期和输出：

   ```sh
   pnpm --filter @forge-crm/server exec jest --runInBand --runTestsByPath src/ai/analysis-domain.spec.ts src/ai/ai-provider.spec.ts
   ```

   2026-10-03 实际结果：两个文件通过，共 8 项（领域 5 项、适配器 3 项）。前者检查虚假引用、事实依据、哈希、历史分析来源限制及语义验证边界，后者模拟 fetch 检查请求配置、错误信息处理与截断输出。未来测试更新时以实际结果为准；学员应记录自己的执行日期与输出。

5. 阅读[数据库集成测试](../../../packages/server/src/ai/ai-analysis.integration.spec.ts)，指出并发生成/确认、草稿可见性、资料更新和商机状态不变分别如何断言。单元测试不能替代这些数据库证据。
6. 为“售后工单分析”写采用方案：替换资料获取、权限、结果结构和业务保存适配，保留生成与确认分离的行为。使用[采用记录模板](../../../_methodology/templates/ui/adoption-record-template.md)标记 adopt/adapt/reject；方案练习不登记为实际采用。

可使用的 AI 提示词：

> 请读取指定 AI 分析服务、权限控制器及测试，按取数、生成、校验、审阅、保存列出责任和证据。为售后工单提出适配方案，明确保留与替换部分。不要调用真实模型或传送业务数据，不把存在测试文件写成测试已通过；列出仍需验证的权限、并发和分析质量问题。

## 验证层次与反例

| 证据 | 可以说明 | 不能说明 |
|---|---|---|
| 当前源码核对 | 已实现的检查、状态和写入路径 | 并发运行效果、模型当前连通性 |
| 模拟网络单元测试 | 结构与引用规则、适配器分支 | 真实供应商兼容性、语义准确率 |
| 隔离库集成测试 | 测试覆盖的持久化、权限与并发行为 | 完整生产迁移链、真实分析质量 |
| 获准样本的真实模型评审 | 指定模型及样本上的结果表现 | 全部业务数据、其他模型或未来版本同样可靠 |

需要实际验证持久化时，使用[隔离库脚本](../../../scripts/test-ai-integration.mjs)并先阅读它：脚本创建随机临时库、准备 schema/seed、使用 mock，最后删临时库；需要数据库建库权限。它不验证完整历史迁移链。仅写培训文档时无需执行，也不要直接对业务库运行集成测试。

2026-10-03 已执行上述隔离库脚本：3 项集成测试通过，并单独核对临时库已删除。具体断言、准备方式及 pg 弃用警告见[实际验证记录](../../testing/ai-analysis-training-verification.md)。这补充了持久化与确认行为证据，不补足真实模型质量或独立项目采用证据。

反例一：在模型请求成功的回调里自动保存并更新业务状态。这样会绕过审阅，且网络重试可能导致重复写入；应将模型结果保存为任务草稿，再按业务规则确认。

反例二：只在生成时校验权限和资料。用户权限或业务资料可能在等待期间变化；执行及确认路径应按目标系统要求重查，确认事务处理幂等和资料过期。

反例三：把携带真实来源 ID 的文本标记为“已核实”。当前校验器没有语义证明能力，审阅者仍要核对引用资料是否支持结论。

可运行的具体反例已放入 `analysis-domain.spec.ts`：F1 的内容为“客户要求十月交付”，结果却写“客户已收到全部货物并完成验收”，引用仍填 F1。当前校验器接受该结构，测试据此记录能力边界，并非认可结论。另一个用例证明仅引用历史分析 H1 的 FACT 被拒绝；补上 F1 后结构允许通过，但仍不证明结论真实。若未来引入语义核验，应重新设计这些断言并评估误报/漏报，不能只改测试以维持绿色结果。

人工审阅至少核对：引用原文、要求/计划/已发生事实的区别、主体与日期、推断标识、缺失信息。例中应拒绝“已经验收”的表述，改为“客户要求十月交付”；实际是否交付须保留待核实。培训评分看学员能否识别差异，不看生成文本是否流畅。

## 学员交付与复用限制

交付：一张状态图、一份六条验收与源码/测试映射、自己的验证记录、一个失败案例，以及售后工单采用方案。评审重点是保存边界、证据真实性、权限变化和重复请求，不能仅看生成文字是否流畅。

可复用的是快照可追溯、生成与保存分离、版本和审计记录、确认时处理资料变更，以及分层验证方法。现有服务仍绑定商机、Prisma、项目授权和六部分结果；`AiProvider` 也接收商机快照并使用领域校验，因此不能宣称已经是任意业务可直接调用的通用 AI SDK。领域拆分应在第二个真实调用场景出现后，以契约与测试证据推进。

明确排除：商机字段、角色配置、模型凭证、旧摘要字段兼容、固定次数和超时值。新项目重新确定这些内容；不复制本机配置或历史网络判断。接口、权限、结果结构或模型策略变化时，通过[培训入口](../README.md)复审本案例。
