# 重复初始化与字段维护权

目标：让学员能审查 AI 生成的初始化脚本，证明它既不重复建记录，也不覆盖其他维护者的数据。适合有 ORM 基础的开发者，基础练习约 30 分钟，只需项目依赖。文末可选进阶练习需要本机 PostgreSQL 和创建临时数据库的权限，不需要模型服务。

## 来源与事实

2026-10-03 核对：[目录初始化实现](../../../packages/server/src/style-scene/template-library.seed.ts)、[回归测试](../../../packages/server/src/style-scene/template-library.seed.spec.ts)、[数据库规范](../../../_methodology/11-数据库设计与数据分层规范.md)、[Prisma 约定](../../../_methodology/profiles/typescript-enterprise-web/database-conventions.md)。

目录来源文件负责模板/组件描述；应用中还会累积评审证据和状态。如果把包含默认空证据、初始成熟度的创建对象直接传给更新，每次同步都会覆盖人工评审，即使记录总数完全没变。

当前实现将默认值放在 `create` 中，`update` 仅同步来源元数据及执行主体。这里的字段归属是本项目决策；其他项目须重新指定维护者，不能照抄字段名。

| 字段类别 | 本项目例子 | 重复初始化行为 |
|---|---|---|
| 来源维护 | description、templateJson、artifactsJson、sortNo | 同步来源 |
| 首次默认值 | 空 evidenceJson、candidate 成熟度、初始 status | 仅创建时设置 |
| 人工/运行期事实 | evidenceCardsJson、maturity、status、nextEvidence、pagePath、note、doneAt | 更新时保留 |
| 审计 | updatedBy | 写入实际 Seed 主体；不伪装成人工评审 |

证据保留不代表仍适用于新版本。来源变化后须复审适用性并保留历史；本案例没有实现自动证据失效管理。

## 可复现练习

1. 阅读实现，先画出 `systemCode + assetCode` 唯一键和上述字段分类，说明哪些字段为何允许同步。
2. 阅读第一个回归用例：首次生成 42 个模板和 15 个组件，修改两个样本的评审字段并放入旧元数据，额外放入另一系统记录，然后重新初始化。
3. 在项目根目录执行：

   ```sh
   pnpm --filter @forge-crm/server exec jest --runInBand --runTestsByPath src/style-scene/template-library.seed.spec.ts
   ```

4. 在独立工作副本中故意给 `update` 加入 `evidenceJson: []`，只运行第一项用例，观察证据保留断言失败，再撤销反例。不要运行数据库 Seed，也不要修改共享开发库。
5. 学员提交字段维护表、失败原因及实际输出。将本规则用于另一个初始化脚本时，先判断管理员授权、业务状态、排序等字段实际由谁维护。

AI 提示词：请审查此初始化脚本，列出每个字段的唯一维护者、首次默认值与更新策略。用“初始化—人工修改—再次初始化”证明数据保留，并测试其他作用域不受影响。不要只断言记录数量，不要连接真实业务库，不要推断尚未执行的数据库行为。

## 验证边界

回归使用 Map 模拟 upsert：预期 58 条记录（57 条目录加一条其他系统记录），两个样本的评审事实保留而来源元数据刷新，其他系统记录不变。此测试能验证创建/更新载荷划分；不能证明真实数据库并发、事务回滚或线上升级安全。

2026-10-03 本轮为 L1 文档工作：已核对上述实现和测试断言，Markdown 本地引用与改动空白检查通过，未重新运行 Jest 或数据库同步。数据库治理检查中新增的字段维护权引用均通过；整个检查仍因已有 `ai_analysis_task`、`agent_task` 两张表未登记层级而失败，不能报告治理全绿。学员运行时须记录自己的测试输出，不能把本节的预期结果当成执行证据。

评审应追问：若多表同步中途失败如何恢复？代码维护字段是否有人工覆盖机制？来源已改变时旧评审如何标识适用版本？这些问题需要目标项目设计，不能因本案例通过而默认成立。

## 复用与维护

### 从临时同步升级为可维护命令

后续新增[目录增量维护命令](../../testing/component-library-maintenance.md)，与初始化共用源码字段定义，默认只预览、显式 apply、无差异不更新、缺少登记拒绝。新增 4 项维护测试与原 6 项目录测试合计 10 项通过；首阶段本机真实预览和执行均为空差异，后续隔离库测试先通过 2 项，再增加人工并发编辑场景，当前 3 项通过。

练习延伸：对照 `componentLibraryEntries`、`planComponentSync`、`assertComponentSyncPreserved`，解释为什么默认预览不应该偷偷执行 seed、为什么仅比较记录数不够、为什么其他系统记录也需保护。运行新单元测试，故意改变评审字段观察拒绝。不要把模拟数据的断言成功解释为真实数据库回滚已验证，也不要未经授权在共享库制造故障。

进阶练习：运行 `node scripts/test-component-library-integration.mjs`，在独立测试库调用真实维护 CLI。2026-10-03 的 2 项测试通过：非空预览不写、实际同步保留人工和其他记录、再次执行无变化；第二条更新被 CHECK 拒绝时，第一条更新通过 AFTER UPDATE 测试序列证明已执行，但目录全表最终回滚。清理与命令前提见维护文档。

评审问题：如果故障在输入解析阶段发生，为什么快照不变不能证明回滚？如果把观察标记写入同一事务的普通表，为何回滚后无法区分“执行后撤销”和“从未执行”？用本次隔离库序列结果和全表快照分别回答“曾发生什么”和“最终留下什么”。该验证技术有数据库前提，不能直接套到其他存储，也不能在生产库添加测试触发器。其他并发时序、断线与版本升级仍需另外设计实验。

进一步的并发练习已用实际 CLI 验证：读取源码同步快照 → 第一条更新进入测试锁等待 → 独立连接提交第二条人工备注和证据 → 解锁 → CLI 写入冲突退出。全表只保留人工修改，重新预览并重试后源码说明更新且人工版本不变。3 项隔离库测试总计 15.678 秒，测试库已清理，具体命令和时序见维护文档。

让学员对比固定 sleep 与查询 pg_locks 的区别：必须证明两个操作按预期交错，不能因一次运行没有丢数据就声称并发安全。再解释为什么“保留人工数据”和“两个请求都立即成功”是不同的要求，以及为什么自动重试需要单独定义适用条件。本例只证明指定时序，未测试两个同步命令竞争或高并发压力。

可复用的是字段维护权分类和反例验证顺序，不是 42/15 的目录规模、字段名或应用成熟度枚举。接入时填写 [Plan 模板](../../../_methodology/templates/plan-template.md) 和 [测试模板](../../../_methodology/templates/testcases-template.md) 的初始化条目。源码更新集合、唯一键或评审工作流变化时重新核对本案例。当前仍是项目内经验，尚无独立业务项目采用证据。
## 实际维护练习补充：元数据必须忠于运行行为

2026-10-03 将单据/抽屉演练接入系统目录时，发现 CMP-11 说明有“点击遮罩退出”，源码却未绑定遮罩关闭。处理是修正说明，不因错误元数据反向新增业务行为。CMP-10/11 的接入步骤与 CMP-15 自有 CSS 登记通过正式增量 CLI 同步，仅三个条目变化，保留人工评审后再次预览无差异；真实目录中复制的参考指令也与显示内容一致。详见[目录展示验证](../../testing/component-adoption-catalog.md)。

学员应区分：源码事实、说明错误、待决定的新能力；再说明为何“数据库更新成功”仍需检查页面可读性和复制内容。只保存人工字段并不自动让旧运行证据适用于新源码。
