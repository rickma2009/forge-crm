# AI 开发练习：从库存余额到来源单据

余额与流水如何由业务单据产生，可继续阅读[销售出库过账不变量](inventory-posting-invariants.md)。查询侧汇总一致性与写入侧事务完整性需要不同证据，不能互相替代。

目标：让开发者从一个真实业务需求中识别数据粒度、页面联动和来源追溯，再判断哪些能力值得复用。案例来源与边界见[候选萃取](../../../_methodology/reference-cases/forge-crm-inventory-summary-drilldown-candidate.md)。预计 45—60 分钟；需本地 Forge CRM 的依赖和测试环境。

## 任务背景

用户先查某物料的当前库存，再看不同法人、仓库、批次的明细，并从事务记录定位是哪张单据的哪一行改变了库存。不要一开始复制页面；先写出三种记录的粒度和关联键。

| 层 | 每行代表 | 必须保留的关键口径 |
|---|---|---|
| 物料汇总 | 筛选范围内的一个物料及币别 | 过滤范围、数量单位、金额币别 |
| 维度明细 | 一个法人、仓库、物料、批次的余额 | 上层选择键、所有已提交筛选条件 |
| 库存事务 | 一次已过账的库存增减 | 发生时间、来源单据、来源行、数量和金额方向 |

## 练习步骤

1. 阅读[用户要求](../../../.specify/sources/REQSRC-089-current-inventory-transaction-pages-20261003/source.md)，写出五条可测试的验收条件。先指出余额和流水为何不能共用一行定义。
2. 对照[余额与事务模型](../../../packages/server/prisma/schema.prisma)，找出余额唯一维度以及事务中的来源单据、来源行字段。解释批次管理和币别对汇总的影响。
3. 阅读[查询服务](../../../packages/server/src/inventory/inventory.service.ts)与[页面实现](../../../packages/web/src/showcase/InventoryStockPages.tsx)，画出“查询 → 选择物料 → 加载明细 → 改条件 → 清空选择”的状态转移。
4. 运行针对性测试：`pnpm --filter @forge-crm/web exec vitest run src/showcase/InventoryStockPages.test.tsx`。指出测试证明了什么、没有证明什么；不把绿色组件测试视为大数据量性能或真实业务验收。
5. 做一次设计评审：当前汇总在服务端取得全部分组后分页，导出在客户端逐页拉取。给出数据量扩大时的替代方案和触发条件；说明如何定义同一时点的余额—事务对账。
6. 用[采用记录模板](../../../_methodology/templates/ui/adoption-record-template.md)为一个不同业务对象填 `adopt / adapt / reject`。业务字段、权限和计价口径必须由目标项目决定。

## 交付与评审

### 已执行的数据库练习

2026-10-03 新增[库存查询隔离库测试](../../../packages/server/src/inventory/inventory-summary.integration.spec.ts)，运行 `node scripts/test-sales-posting-integration.mjs`。同一个随机测试库运行 2 项查询测试与原有 5 项过账测试，7 项全部通过（Jest 5.675 秒）。不是 HTTP、权限或完整迁移验收。

样本：同一物料在人民币法人仓 A 的两个批次分别有 2、3 件，仓 B 有 5 件，金额分别为 20、30、50；另一个分类物料 11 件作为干扰项。人民币余额由真实入库过账生成。另在美元法人仓 C 直接构造 7 件/70 美元余额，仅用于查询服务防御性分组。

断言包含：人民币组为 10 件/100 元、美元组为 7 件/70 美元；每页 1 行遍历所有明细，检查无重复且与各组数量、金额一致；法人、仓库、名称、每级分类、组合条件与矛盾条件共 11 组查询；下钻使用精确物料编码，排除前缀相近的干扰物料；不存在的编码返回零行及总数 0。

第一次尝试通过入库创建美元余额失败，原因是现行 `inboundOrderWriteSchema.currencyCode` 只接受 CNY。进一步核对发现 `inventoryBalanceSchema` 也只接受 CNY，前端 gateway 使用该契约解析。因此，查询服务能按币别分组，不代表美元入库或美元页面流程已可用。最终测试明确区分真实人民币单据与模拟美元查询数据，没有放宽业务契约；模拟美元余额不能用于证明流水对账。

本例可用于练习“从失败修正证据边界”：先让学员判断绿色服务测试是否足以承诺多币别支持，再要求沿输入契约 → 业务写入 → 查询输出 → 前端解析逐层找证据。使用[汇总下钻验证模板](../../../_methodology/templates/aggregate-drilldown-verification-template.md)提交，不隐去第一次夹具失败。具体运行与清理见[验收记录](../../testing/current-inventory-acceptance.md)。

剩余缺口：跨租户/跨应用数据隔离攻击、HTTP/RBAC、跨页并发变更的一致性、大数据量和小数精度专项；测试中小整数的 JavaScript 求和只用于固定样本手算，不应复制为生产金额算法。

交付一页说明，包含：三层粒度与关联键、五条验收条件、测试结果及实际命令、一个失败或边界场景、至少一项不可复用内容、独立项目采用时仍需确认的问题。评审时重点检查是否把“上表筛选”完整带入下表、是否混算不同币别、是否能定位来源行，以及是否把单项目案例误称为行业最佳实践。

参考答案不是固定的页面截图。符合要求的方案可以替换前端框架和数据库，只要能证明上述行为与边界。当前案例成熟度为 `candidate`，尚无跨项目采用或目标用户效率证据。
## 延伸练习：导出编码和业务查询分开

本项目库存页曾另写 CSV cell 函数，遗漏公共网格已有的 Tab/CR 前缀处理。通过读取下载 Blob 的反例测试确认差异后，统一到 `createCsvBlob`：库存仍负责按授权条件取全量行，公共工具只负责 CSV 编码，下载名称与用户动作仍在页面。新增用例及实际结果见[验收记录](../../testing/current-inventory-acceptance.md)。

练习：给定含引号、逗号、字段内换行、空值、Tab 开头文本和带小数数量的合成数据，比较两个入口输出的实际字节。说明为什么“文件成功下载”不能证明列值正确，为什么“序列化一致”不能证明授权正确或跨页数据快照一致，以及为什么当前前缀策略不是完整公式安全审计。禁止为了共享工具而把库存客户、法人或仓库字段写进通用编码器。
## 延伸练习：导出成功不等于取齐数据

库存页面原来仅按第一响应的 totalPages 遍历，忽略后续总数变化和空页；公共网格已有 loadAllGridRows 检查，但页面没有复用。两项失败反例后接入公共函数，页面与导出共 16 项测试通过。重构还发现原成功测试的夹具宣称总数非零却每页为空，应修正夹具，而非放宽生产检查来保留绿灯。

练习：分别设计“缺页”“总数增加”和“总数相同但记录替换”的响应，说明前两种当前会阻止下载，第三种为何可能通过。需要严格快照时，应由后端提供相应能力，不能把前端计数包装成强一致保证。依据及局限见[库存验收记录](../../testing/current-inventory-acceptance.md) TC-23。
## 延伸练习：运行时延迟加载不等于无编译依赖

原 grid-export.ts 即使只调用 CSV 分支，源码仍有动态 import('exceljs')。为了只复制 CSV 编码，将 csvCell/createCsvBlob 提到无 imports 的 csv-export.ts，原入口再导出兼容。实际在无 node_modules 的临时工程中复制、编译并执行通过，见[单文件接入](../../../_methodology/examples/csv-export-adoption/README.md)。

学员需区分运行时是否执行某个分支、类型检查是否解析其依赖，以及目标工程是否安装相应包。不要为了复制一段字符串编码逻辑把整个 React 网格、业务契约和 Excel 工具链带入新项目；也不要因为拆出了 CSV 就声称完整导出业务可独立运行。
## 延伸练习：不要用无限循环测试无限循环

公共取数回调声明 total:number 不保证运行时值合法。本项目用 -1、小数、非有限数、缺失值、null 和字符串构造反例，第二次请求立即抛出哨兵，先观察错误分支而不制造无界测试。加入非负安全整数校验后，首个无效响应即拒绝；合法零结果仍通过。

练习时分别说明类型约束、回调运行值和 JSON 表达能力：NaN/Infinity 是回调层样本，不是合法 JSON 字面量。记录请求次数和终止条件，而非仅等待测试超时。实际结果见[TC-24 验收记录](../../testing/current-inventory-acceptance.md)，公共导出 12 项与库存页面 12 项通过；大数据量上限和数据库快照仍需另验。
