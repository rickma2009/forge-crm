# ADR-006：平台访问管理与无损迁移架构

> 状态：accepted  
> 日期：2026-09-21  
> 关联：切片 `012-organization-access-administration-foundation`、`REQSRC-043`—`REQSRC-046`

## 背景

当前导航授权已在 PostgreSQL 中运行，但使用 `iam_*`、`ui_*` 历史命名，菜单/操作 target 同时承担授权语义，缺少正式 tenant/application、稳定权限目录、可管理角色页面和结构化安全审计。直接删除重建会丢失现有账号、角色、导航和列表视图数据；长期双写又会形成两个授权事实源。

## 决策

1. 平台身份与授权统一进入 `sys_` 系统平台层；组织员工保持后续 `org_` 独立切片。
2. 采用协调停写切换，以新的不可改写 Prisma migration 保留数据迁移；不改写历史 migration，不长期双写。
3. 新增默认租户和应用登记。外部 URL 保留 application code，服务端在认证 tenant 下解析为 application UUID；平台表内部关系只使用 UUID 作用域。
4. 权限点成为独立、稳定的服务端安全事实；菜单与菜单操作引用权限点，API 直接校验 permission code。用户仍只能通过角色获得权限。
5. 既有菜单/操作 grant 一对一转换为新权限点关联并保留 grant ID；无法映射或存在冲突时迁移失败，不静默丢弃。
6. 角色成员使用独立 UUID 和多段半开有效期，数据库阻止有效期重叠；角色权限通过停用/恢复保留关联历史。
7. 系统管理员角色每应用唯一且受保护；权限发布必须在同一事务中为其补齐显式授权并验证至少一个有效管理员成员。
8. 高风险成功变更和白名单化审计记录同事务；权限拒绝默认失败并产生可关联安全事件，任何日志均不记录凭据或完整敏感请求体。
9. 权限矩阵使用 role version 乐观锁和 Serializable 事务原子保存；不增加权限缓存、DENY、继承或用户直授权。
10. 本切片不启用 PostgreSQL RLS；使用复合外键、服务层作用域查询和失败默认拒绝落实隔离。
11. 管理端沿用现有企业页面样式和 gateway seam，不引入新的 UI/状态库。

## 备选方案

| 方案 | 结论 | 原因 |
|---|---|---|
| 保留 `iam_*`、`ui_*`，只做页面 | 拒绝 | 继续违反已批准数据库分层，权限事实仍依赖 UI target |
| 建新表后长期双写 | 拒绝 | 两套授权事实难以保证原子一致，撤权路径风险高 |
| 删除旧表并重新 Seed | 拒绝 | 无法保留用户、角色、grant、视图 ID 和历史关系 |
| 菜单 action code 继续作为唯一 API 权限 | 拒绝 | UI 结构调整会改变服务端安全契约 |
| 角色成员继续使用 `(role_id,user_id)` 主键 | 拒绝 | 无法保存重新授权的多段历史 |
| 物理删除被移除的 role permission | 拒绝 | 丢失稳定 ID 和授权历史，难以审计恢复 |
| 本切片启用 RLS | 延后 | 当前单默认租户且已有服务层边界，RLS 会扩大连接身份和运维范围 |
| 复制参考项目表和页面组件 | 拒绝 | 参考域、DDL 流程和视觉依赖不符合目标规范 |

## 后果

- 优点：权限点与 UI 解耦，平台表符合分层规范，现有 ID/授权语义可对账，系统管理员和有效期由强约束保护，页面/API 使用同一安全事实。
- 代价：迁移和部署必须协调切换；复合外键、GiST 排斥约束和事务内跨行校验增加实现与测试复杂度。
- 限制：本轮只有默认租户，不提供租户切换、RLS、组织员工、数据权限、审批流或零停机迁移。
- 复审条件：出现生产零停机、多租户登录、角色成员重叠业务、显式拒绝/继承、外部身份源、数据权限或审计合规留存要求时重新评审。
