# ADR-001：交互模式工作台前端架构

> 状态：historical-accepted-for-slice-001; review-required-for-new-slices
> 日期：2026-08-30  
> 关联功能：`001-pattern-catalog-preview`  
> 决策 Gate：Architecture Gate

> 当前边界：该 ADR 的批准只适用于历史切片 001。`REQSRC-007/008` 引入 103 项资产索引、无 Demo 投影和场景契约，已经触发本 ADR 的复审条件；不得用旧批准授权切片 002。增量替代方案见待 Architecture Gate 决定的 `ADR-002-资产索引与验证切片扩展架构.md`。

## 1. 背景

首个切片需要在一个桌面优先工作台中展示两个已有模式，并满足统一选择、说明切换、错误隔离、键盘操作、可分享定位和确定性重置。Demo 不需要账户、后端或业务数据持久化。

现有两个金标准交互案例是独立 HTML/CSS/JavaScript 页面，其中导航案例包含本地偏好持久化。直接复用视觉和行为证据是合理的，但直接嵌入其运行状态会与“切换、重置或重新打开后恢复预置状态”的已批准规则冲突。

## 2. 决策驱动因素

- `_methodology/` 必须继续是通用模式的权威来源；
- 两个案例要共享目录、上下文、说明和错误处理；
- 每个案例内部状态和样式不得污染其他案例；
- 重置行为必须统一，不要求每个案例暴露复杂命令接口；
- 新增第三个案例时不应修改工作台主流程；
- 首期保持静态部署，不引入后端、数据库或在线编辑；
- 测试应穿过与真实调用者相同的接口。

## 3. 备选方案

| 方案 | 优点 | 代价与风险 | 结论 |
|---|---|---|---|
| A. iframe 直接嵌入现有案例 | 接入最快，样式天然隔离 | 旧案例状态持久化与 Spec 冲突；重置、错误通信、地址同步和键盘验收复杂 | 不采用 |
| B. 在单页中直接硬编码两个案例 | 实现简单，无跨文档加载 | 第三个案例会继续扩大主页面；目录、说明、Demo 和测试容易耦合 | 不采用 |
| C. 注册表驱动工作台 + 原生 Demo Adapter | 工作台只理解统一元数据和 Demo 接口；案例独立、可懒加载、可重置、可测试 | 首次需要把两个案例去业务化实现一次，并建立投影一致性检查 | 采用 |
| D. 通用 Schema/低代码渲染器 | 长期可配置，减少手写页面 | 首片只有两个异构案例，接口会比实际变化更复杂；特殊交互仍需扩展代码 | 暂缓，达到复审条件再评估 |

## 4. 决策

采用单包静态 Web 应用：React + TypeScript + Vite，使用 pnpm 管理依赖。首期不引入 UI 组件库、路由库、状态管理库或后端。

工作台采用两个真实 seam：

1. **模式目录 Module**：向页面提供查询后的模式列表和按 ID 获取的模式定义；隐藏搜索归一、分类、来源投影和验证状态细节。
2. **Demo Adapter seam**：每个模式提供一个无业务参数的可渲染 Demo Adapter。案例内部自行管理临时状态；工作台通过重新挂载 Adapter 完成统一重置。

两个 Adapter 分别实现企业双层导航壳层和记录管理工作区。它们复用方法论中的不变量、设计令牌和验收要求，但不复制 MCRM 业务字段、角色、认证或后端契约。

## 5. Interface 约定

### 5.1 模式目录 Module

```text
listPatterns(query?) → PatternSummary[]
getPattern(patternId) → PatternDefinition | null
```

调用者只需理解模式 ID、分类、验证状态、展示总结、来源引用和 Demo 加载入口。搜索归一、稳定排序、缺失字段检测和来源指纹检查留在 Module 内部。

### 5.2 Demo Adapter seam

```text
PatternDemo → 可渲染、无业务输入的 Demo
```

- Adapter 不接收生产客户端、账号或业务对象；
- 所有样例数据由 Adapter 内部提供且去业务化；
- 所有交互状态只存在当前挂载生命周期；
- 工作台改变实例键即可重置，无需为不同案例学习独立重置命令；
- Adapter 异常由工作台错误隔离层捕获，不影响目录和模式说明。

该 seam 已有两个 Adapter，属于真实变化点；不为尚未出现的渲染器建立额外抽象。

## 6. 方法论资产投影

应用内模式定义是面向展示的派生投影，不是第二份通用规范。每个条目必须包含：

- 方法论分类编号；
- 方法论 pattern 与 example 的来源引用；
- 来源文件指纹；
- 验证状态；
- 去业务化展示总结；
- 对应 Demo Adapter。

校验脚本在构建和 CI 中验证来源存在、指纹匹配、编号唯一、验证状态合法、必填总结完整以及两个种子 Adapter 可定位。方法论来源改变后，投影必须显式复核并更新，禁止静默漂移。

当模式数量或维护频率达到复审条件时，再评估把机器可读清单晋升到 `_methodology/`；首片不修改通用模式存储格式。

## 7. 技术基线

拟采用工作台本地已经验证可运行的基线：

- Node.js `>=22.12`；
- pnpm `9.15.x`；
- React `19.x`、TypeScript `5.7.x`；
- Vite `5.4.x`；
- Vitest `3.2.x`、React Testing Library；
- ESLint `10.x` 与 TypeScript ESLint `8.68+`；
- 原生 CSS 与 CSS Custom Properties。

这项选择基于本工作台已有安装、构建和测试证据，不继承 MCRM 的业务架构、Ant Design、路由、权限或服务端方案。具体锁定版本在 Architecture Gate 批准后的安装步骤中记录。

实现期依赖解析确认旧版 TypeScript ESLint 8.42 的 peer 范围不包含 ESLint 10；升级到明确支持 ESLint 10 的 TypeScript ESLint 8.68，保留已批准的工具链基线。这不改变架构边界、运行时或产品行为。

## 8. 后果

### 正面

- 工作台主流程不会随着案例细节增长；
- 每个案例可以独立开发、测试和失败；
- 重置行为由生命周期统一保证；
- 不依赖后端即可静态部署；
- 避免大组件库限制多样化模式展示；
- 第三个模式只需新增投影、Adapter 和测试，而不是修改主流程。

### 代价

- 两个现有案例需要根据已验证行为重新实现；
- 方法论 Markdown 与展示投影之间需要指纹检查和人工复核；
- 原生 CSS 需要更严格的命名空间和令牌纪律；
- 未建立通用 Schema 渲染器，复杂新模式仍需编写 Adapter。

## 9. 复审条件

满足任一条件时复审本 ADR：

- 可交互模式达到 10 个，手工投影维护成为明显负担；
- 出现除 React Adapter 之外的第二种真实渲染方式；
- 需要在线编辑、多人协作、权限或内容发布；
- 模式资产需要被多个独立应用机器读取；
- 用户明确要求 Open Design 与工作台形成自动双向同步。
