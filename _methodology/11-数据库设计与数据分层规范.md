# 数据库设计与数据分层规范

> 状态：approved-governance-baseline  
> 版本：v1.1  
> 决策来源：`REQSRC-043`、`REQSRC-059`  
> 本文是技术栈中立的数据库治理规范；具体数据库和 ORM 实现由对应 Technology Profile 与项目 ADR 补充。

## 1. 适用范围

本规范适用于工作台内新建或整改的企业管理信息系统。只要切片新增或修改持久化数据，就必须在 Architecture Gate 中说明如何符合本规范；不使用关系数据库的项目也必须映射相同的数据所有权、隔离、生命周期和迁移原则。

本规范不替项目决定数据库品牌、部署拓扑、容量、备份产品、RLS 或微服务拆分。具体选择必须来自项目需求与 ADR。

## 2. 首要原则

1. **先定所有权，再建表。** 每个事实只能有一个权威责任模块。
2. **共享使用不等于共享写入。** 其他应用通过 API、应用服务或事件使用数据，不绕过责任模块直接写表。
3. **应用不是业务领域。** CRM、SCM、MES 是使用者；客户主体、物项、销售订单、采购订单才是稳定业务概念。
4. **数据库落实关键不变量。** 唯一性、同作用域外键、必填和合法取值不能只靠前端。
5. **历史可追溯。** 核心主数据、安全数据和交易数据默认停用或归档，不因页面“删除”而丢失审计链。
6. **迁移是代码。** 迁移可审查、可重放、不可改写，并有数据验证和恢复方案。

## 3. 数据层级与命名

| 层级 | 命名 | 典型内容 | 可复用性与所有权 |
|---|---|---|---|
| 系统平台 | `sys_` | 租户、应用、用户、角色、权限、菜单、字典、列表视图、审计 | 公共基础模块；安全边界必须统一 |
| 组织主数据 | `org_` | 组织单元、员工、雇佣、任职、岗位、负责人 | 可选公共模块；企业级共享 |
| 企业共享主数据 | `md_` | 客户、供应商、产品及公共基础信息 | 独立主数据责任模块；跨应用使用 |
| 销售域 | `sd_` | 商机、销售订单、销售发货 | 销售责任模块唯一写入；CRM/MES/SCM 可作为使用者 |
| 供应链制造域 | `scm_` | 采购、库存、生产、调拨、物料需求、领料 | 采购/库存/生产子模块需继续明确唯一责任边界 |
| 研发域 | `rd_` | BOM、研发项目及研发过程 | 研发责任模块唯一写入 |
| 财务域 | `fin_` | 财务费用、报销、工资及核算事实 | 财务责任模块唯一写入 |
| 集成 | `int_` | 外部标识、同步游标、集成事件状态 | 连接边界；不是业务事实源 |
| 暂存 | `stg_` | 导入暂存、清洗中间结果 | 有明确保留期，不供在线业务直接依赖 |
| 分析 | `dim_`、`fact_` | 数仓维度和事实 | 只用于分析模型，不作为 OLTP 主数据 |

禁止用 `public_` 表达模糊的“大家都能用”。PostgreSQL 的 `public` 是 Schema 名，也不表示数据所有权。`dim_` 仅用于分析维度；在线客户、供应商、产品等权威主数据统一使用 `md_`。

### 3.1 公共系统表基线

下列能力可以作为其他系统的公共模块采用，但仍需按项目范围启用：

- 必选平台基线：`sys_tenant`、`sys_application`、`sys_user`、`sys_role`、`sys_role_user`、`sys_permission`、`sys_role_permission`；
- 导航能力：`sys_menu`、`sys_menu_action`；
- 配置能力：`sys_dictionary`、`sys_dictionary_item`、系统/角色/用户列表视图及偏好；
- 安全运营：认证凭据、会话、`sys_audit_log`；
- 可选组织模块：`org_unit`、`org_employee`、`org_employment`、`org_employee_assignment`、`org_position`、`org_unit_leader`；
- 可选企业主数据模块：`md_customer`、`md_supplier`、`md_product` 及按业务能力拆分的扩展表；需要统一主体模型时再通过批准的 ADR 引入 `md_party`、`md_party_role`。

“公共”表示可复用的职责和不变量，不表示所有项目必须复制全部表，也不表示多个部署共享一个物理数据库。

### 3.2 业务表基线

业务表按企业既有业务域前缀和稳定业务实体命名，而非按当前界面或应用名命名：

- 销售：`sd_opportunity`、`sd_sales_order`、`sd_sales_order_line`；
- 采购、库存、生产：`scm_purchase_order`、`scm_inventory_transaction`、`scm_production_order`；
- 研发：`rd_bom`、`rd_project`；
- 财务：`fin_expense_claim`、`fin_accounting_voucher`。

不得因为多个系统需要订单就按应用复制 `crm_sales_order`、`mes_sales_order`、`scm_sales_order`，也不得建立无明确语义的通用 `order` 表。每个交易聚合必须明确状态机、责任模块和唯一写入入口。

## 4. 表与字段命名

既有命名偏差按具体表登记例外，不能把旧前缀加入新表允许清单。新增例外须记录维护模块、来源证据、整改目标和迁移状态，并保留字段命名检查；登记通过仅表示偏差可追踪，不表示迁移完成。目标项目应在 Plan 说明处理范围，迁移验收后移除例外。

本仓库早期已登记表的字段检查兼容集合固定在治理脚本中，新增例外不能通过省略或关闭 `enforceFieldNaming` 进入该集合。整改目标仍须符合长度、格式和批准前缀。校验器的隔离反例测试纳入 `verify-workbench.sh`，不能只用当前登记全绿证明它能够识别错误。

- 物理表名和物理字段名统一使用小写 `snake_case`，各自长度不得超过 32 个字符；表名使用单数或项目已批准的一致形式，不混用。
- 域前缀计入 32 个字符限制。名称过长时使用登记过的稳定业务缩写，不得依赖 PostgreSQL 自动截断，也不得删除关键业务语义来凑长度。
- 索引和约束同样使用小写 `snake_case`；其长度遵循技术 Profile 和项目部署数据库限制。
- 内部主键统一命名 `id`；外键命名 `<referenced_entity>_id`。
- 稳定业务编码命名 `<entity>_code` 或业务公认编号；显示名称命名 `<entity>_name`。
- 布尔字段使用能读成事实的 `is_`、`has_`、`can_` 前缀；不能用多个布尔字段模拟可扩展分类。
- 排序字段使用 `sort_no`；备注使用 `remark`；并发版本使用 `version`。
- 时间点使用 `_at`，自然日期使用 `_date`。有效时间统一为 `effective_at`、`expires_at`。
- 技术标识、权限编码和集成代码使用稳定英文编码；展示名称允许本地化。

## 5. 主键、业务键与外部标识

- 内部关系使用 UUID 主键，不使用可变业务编码作为外键。
- 业务编码是带明确作用域的候选键，必须定义大小写、空格、规范化和变更规则。
- 唯一约束必须包含真实作用域，例如 `(tenant_id, application_id, permission_code)`。
- 同一实体在 ERP、MES 或旧系统的不同编码进入 `int_external_reference` 或领域专属映射表；不得不断向主表追加 `erp_code`、`mes_code`。
- 导入文件行号、外部流水号和自然键不能替代内部身份，除非 ADR 证明其永久稳定。

## 6. 租户、应用与作用域隔离

- 企业级数据以 `tenant_id` 为边界；菜单、角色和权限通常再以 `application_id` 为边界。
- 所有租户拥有的数据表必须明确携带或可无歧义推导 `tenant_id`。
- 跨表关系通过复合唯一键、复合外键或等价数据库约束阻止跨租户、跨应用引用。
- 服务端每次访问均验证作用域；前端传入的租户或应用不能直接作为可信事实。
- RLS 不是全局默认。高安全项目可通过 ADR 启用，但不能替代服务层授权和数据库关系约束。

## 7. 关系、树与时间模型

### 7.0 引用存储与页面展示

- 关系数据库中的内部引用统一保存被引用记录的稳定主键 ID，例如入库单保存 `legal_entity_id`、`warehouse_id`，客户地址保存 `customer_id`；不得只保存易变名称来替代外键。
- 对数据字典或其他可变主数据的业务引用，持久化稳定引用标识/编码，不把可变名称当作关系事实保存。字典引用保存字典项稳定编码（本仓库字典消费接口中的 `itemValue`），其他表关系优先保存内部稳定主键，并在需要跨系统传递时同时保留稳定业务编码。关键页面、列表、表单回显、导出和打印展示时，通过受控关联解析当前有效名称/值。
- 名称快照仅适用于确实需要还原历史语义的交易记录，须与当前引用分开定义用途；不能以快照替代当前关系。值不属于可变引用且其业务规则保证初始化后不可更改时，可直接保存名称/快照，例如员工姓名；若引用对象可能改名或调整（如员工部门），必须保存其稳定引用并在当前态展示时重新解析最新名称。
- Architecture Gate 与 Specification 必须逐字段说明：是否为可变引用、保存的稳定键、展示解析来源/批量方式、历史快照用途、引用停用或缺失时的行为。不得仅凭“当前名称看起来稳定”跳过该判断。
- ID 是存储与接口关联标识，不是面向业务用户的展示值。所有列表、详情、表单回显、导出和打印在展示引用时，必须显示当前用户有权查看的业务名称、编码或“编码 · 名称”，不得直接把 UUID/内部 ID 当作法人、仓库、客户、物料、人员等业务内容显示。
- API 应返回引用 ID 以及展示所需的名称/编码字段，或通过受控批量解析接口提供名称；前端不得逐行发起无界 N+1 查询，也不得自行缓存跨租户名称映射。
- 交易与过程记录需要保留历史语义时，在保存引用 ID 的同时保存批准的名称/编码快照；当前主数据名称与历史快照的使用边界必须在需求中明确。
- 引用对象不存在、越权或已停用时，历史页面使用已保存快照或统一的“对象不可用”占位，不回退为直接显示内部 ID。
- Architecture Gate 和页面评审必须逐项登记：保存的外键、展示字段、名称解析方式、历史快照策略、作用域校验与批量查询性能。

### 7.1 外键与删除

- 默认 `RESTRICT` 或等价限制删除。
- 只有纯依附、无独立审计价值且可由父记录完整重建的数据允许级联删除。
- 核心主数据、安全数据、交易单据被引用后不得由普通页面物理删除；采用停用、结束有效期或归档。
- 多对多关系必须有唯一约束，防止重复关联；安全关系还必须记录授权人和授权时间。

### 7.2 树结构

- 基线采用 `parent_id` 邻接表；父子必须处于同一租户和适用的同一应用。
- 事务内阻止自引用和循环；根节点规则必须明确。
- `level`、完整路径等派生值不能成为无维护机制的第二事实源。
- 只有真实规模与查询证据证明必要时，才增加闭包表、物化路径或数据库扩展，并通过 ADR 记录同步机制。

### 7.3 有效时间

- 有效期统一使用半开区间 `[effective_at, expires_at)`；`expires_at` 可空表示无已知结束时间。
- 必须明确是否允许重叠，并用数据库约束或事务内不变量校验落实。
- 当前状态和历史事实不得互相覆盖；调岗、角色成员、负责人等使用带有效期的关系记录。

## 8. 状态、字典与类型

- 认证状态、迁移状态等封闭技术集合使用数据库约束、枚举或等价强类型。
- 客户等级、行业等可配置业务分类使用数据字典或业务主数据。
- 有流程含义的状态必须有状态机和允许转换，不能因“可配置”而放入任意字典。
- 用户锁定、员工离职、组织停用属于不同领域状态，不共用一个含义模糊的全局枚举。
- 新状态的失败行为、兼容策略和历史数据迁移必须在 Specification / Architecture Gate 中说明。

## 9. 审计、并发与敏感数据

可变主数据、配置和交易实体至少评审：`created_at`、`created_by`、`updated_at`、`updated_by`、`version`。纯关联表按风险保留必要时间字段；授权关系必须保留授权主体和时间。

以下操作进入结构化审计日志：账号和会话变更、角色成员及权限变更、员工账号绑定、组织移动、任职变化、关键配置和主数据变更。日志包含关联 ID，但不得记录密码、Token、Cookie、完整敏感请求体或不必要的个人信息。

敏感字段必须完成分类，并落实最小采集、接口最小返回、页面脱敏、导出授权和日志排除。是否采用字段级加密由威胁模型和合规要求决定，不机械加密所有字段。

## 10. 迁移、种子与恢复

- 迁移历史是唯一 DDL 事实源；已在任何共享环境应用的迁移禁止改写。
- 重命名和结构调整优先使用保留数据的迁移，不以删除重建冒充升级。
- 迁移必须评审锁表时间、兼容窗口、数据回填、索引创建、失败恢复和验证查询。
- 已应用变更通常通过新迁移前滚修复；需要回退数据时先备份并演练。
- Seed 必须幂等、使用中性数据、区分生产必需配置与演示数据，并验证跨表不变量。
- Seed 字段维护权：逐字段区分代码权威配置、仅首次创建的默认值、用户/运行期事实。重复执行只更新明确由代码维护的字段；默认值不得覆盖已有审批、评审证据、人工说明或业务状态。不产生重复记录只是幂等的一部分，还必须保留非 Seed 所有者的数据。
- 重置或修复已有业务字段应使用单独、明确授权的作用域操作，记录变更前后值、恢复办法及验证；不得隐藏在日常初始化中。源配置变化后应复审既有证据的适用性，保留历史，不自动清空证据或晋升成熟度。
- 禁止连接或修改参考项目、生产系统数据库来完成本地验证。

## 11. 索引与查询

- 索引来自已知查询、唯一性和外键维护，不按字段数量机械创建。
- 外键、作用域过滤、列表排序和有效期查询必须在 Architecture Gate 评审索引。
- 组合索引顺序与过滤条件一致；重复或被前缀覆盖的索引应删除。
- 分页必须有稳定排序；大数据集合优先游标或经验证的分页方案。
- 性能承诺必须绑定数据规模、查询计划和测量证据。

## 12. Architecture Gate 数据检查清单

新增或修改持久化数据时，Plan 必须回答：

1. 数据属于 `sys_`、`org_`、`md_`、`sd_`、`scm_`、`rd_`、`fin_`、`int_`、`stg_` 还是分析层？
2. 唯一责任模块、权威写入口和数据使用者是谁？
3. 租户、应用或业务作用域如何进入唯一键和外键？
4. 主键、业务键、外部标识和规范化规则是什么？
5. 状态机、有效期、重叠规则和删除策略是什么？
6. 哪些不变量由数据库保证，哪些由同事务服务校验？
7. 敏感字段、接口返回、导出和审计策略是什么？
8. 并发、幂等、索引和预期数据规模是什么？
9. 迁移、回填、兼容、备份恢复和验证步骤是什么？
10. 对应需求、验收条件、数据库集成测试和失败测试在哪里？

缺少以上答案时，Architecture Gate 不应批准物理数据实现。

## 13. 禁止模式

- 用 CRM、MES 等应用名称代替领域所有权，或允许多个应用共同直写同一领域表；`scm_` 虽覆盖采购、库存和生产，仍必须在模块登记中区分子域责任；
- 因为“大家都用”就允许多个系统直接写同一表；
- 用 `dim_` 命名在线主数据，或继续新增旧 `mdm_` 表；
- 同一关系在双方各保存一个外键；
- 只在前端校验唯一性、租户边界或权限；
- 为所有页面自动生成新增、修改、删除和导出权限；
- 用无继承语义的 `parent_role_id` 模拟角色分组；
- 修改已应用迁移、Seed 非幂等、测试连接生产库；
- 用 JSON 逃避核心业务字段、约束和查询设计。

## 14. 技术 Profile 与项目级决策

- PostgreSQL/Prisma 项目同时遵循 [`profiles/typescript-enterprise-web/database-conventions.md`](profiles/typescript-enterprise-web/database-conventions.md)。
- 其他技术栈建立自己的 Profile 附录，不复制 PostgreSQL 特有实现为通用规则。
- 项目可通过 ADR 偏离本规范，但必须记录约束、替代保证、风险、验证和复审条件。
