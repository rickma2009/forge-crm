## 2. 业务框架

### 2.1 来源事实

- `Role`、`PermissionPoint`、`RolePermission` 将角色、权限点和授权关系拆分；权限点包含资源、动作、名称和域。
- 角色页面支持关键词和域筛选，展示角色编码、名称、域、权限数和成员数，并通过抽屉维护权限矩阵。
- 权限页面支持按域和关键词筛选，呈现编码、资源、动作和描述。
- 主体、成员页面采用“筛选—紧凑表格—行操作”的企业后台列表结构。

### 2.2 可候选复用的业务不变量

1. 角色和权限点分离，角色通过显式关联拥有权限。
2. 角色授权页面应让管理员看到“当前角色、可选权限、已选集合、保存结果”。
3. 系统内置角色不能按普通角色删除。
4. 权限编码是稳定技术标识，展示名称和说明是管理端解释信息。
5. 列表查询、授权修改和结果反馈应形成可复核闭环。

### 2.3 不纳入本切片

- `DataScope` 及行级数据范围；
- 个人主体升级/降级、黑名单、客户/供应商双域；
- 风险等级、企业开户、NDA/IP 协议等供应链平台专属流程；
- 组织员工主数据页面。来源只提供简化组织树，不足以支持已批准的雇佣、任职和负责人模型。

## 3. 架构

来源架构把身份、授权和安全模型放在账号中心包中，前端以管理端页面调用相应 hooks/API。其可借鉴部分是职责拆分：身份主体、角色、权限点、关联关系和审计各自独立。

目标工程不能照搬的架构差异：

| 来源做法 | 目标决策 | 原因 |
|---|---|---|
| Prisma 只生成类型，建表依赖手工 `schema.sql` | Prisma migration 是唯一 DDL 历史 | `_methodology/11-数据库设计与数据分层规范.md` 要求迁移可审查、可重放、不可改写 |
| `domain` 用 customer/supplier 等字符串表达授权域 | `tenant_id + application_id` 表达正式作用域 | 应用和租户是明确安全边界，不能依赖松散字符串 |
| 主体角色、成员角色并存 | 统一 `sys_role_user` | 本切片只有账号通过角色获权，不支持个人直接授权或多套角色关系 |
| 权限关系级联删除 | 核心安全数据默认限制删除或停用 | 保留审计链，防止授权事实静默丢失 |
| `OrgTree.level` 持久化 | 目标 `org_unit` 不保存权威 `level` | 避免派生层级成为第二事实源 |

## 4. 技术

### 4.1 来源技术事实

- PostgreSQL + Prisma 类型模型，表位于 `gongfu` schema。
- React + TypeScript + Ant Design。
- 角色和权限页面通过 hooks 分页查询，权限矩阵通过 checkbox group 编辑后统一保存。

### 4.2 目标采用方式

- 保留“查询参数—列表—详情/授权抽屉—保存反馈”的交互契约。
- 使用目标工程现有 React/Vite 页面结构、contracts zod、NestJS service/controller 和 Prisma migration。
- 使用现有 `.enterprise-page`、`.query-card`、`.table-toolbar`、`.enterprise-table-wrap`、`.enterprise-modal` 等客户管理页样式，不引入 Ant Design。
- 服务端按相同 `permission_code` 强制授权；前端隐藏按钮不是安全边界。

## 5. 设计思想

### 5.1 值得验证的候选模式

1. **角色工作台**：一屏完成查询、角色状态查看、成员维护入口和权限矩阵入口。
2. **权限按资源分组**：权限矩阵按资源或菜单分组，显示编码、动作和说明，降低平铺列表认知成本。
3. **内置资产保护**：内置角色和系统权限在界面中明确标识，禁用不允许的修改或删除动作，并由服务端再次拒绝。
4. **紧凑企业列表**：默认一行常用查询条件，操作集中在工具栏和行操作列，符合现有客户管理页的空间密度。

### 5.2 适用边界

适用于角色数量和权限点数量仍可通过分组、搜索和分页管理的企业系统。若权限点达到大规模、存在显式拒绝、角色继承或审批流，需要另立需求和架构方案。

### 5.3 不复用项

- 来源品牌色、组件库默认间距和页面外壳；
- `track`、customer/supplier 域、个人主体迁移等组织专属字段；
- 任意创建或重命名系统权限编码；
- 将数据范围并入本次功能权限切片。

## 6. AI 使用说明

AI 用于定位源码、对照页面和数据模型、区分事实/推断/未知，并把候选模式转换为目标工程的评审输入。AI 没有运行来源项目的生产环境，没有访问来源数据库，也没有验证页面与线上部署完全一致。因此：

## 7. 局限、风险与建议

### 7.1 局限

- 未访问来源数据库，无法确认迁移数据质量、真实数据量和索引表现。
- 未运行来源 UI 的完整浏览器任务，不能把源码阅读等同于可用性验证。
- 来源组织树模型缺少雇佣、任职、岗位和负责人有效期，不足以作为目标组织模型依据。
- 来源物理删除和级联策略与目标审计要求存在冲突。

### 7.2 风险控制

- 物理表改名必须保留主键和数据，以正式 migration 前滚完成，禁止删除重建。
- 系统权限点首轮由 seed/migration 初始化并只读展示，避免管理端任意改变服务端安全契约。
- 系统管理员角色不可删除、不可失去基本管理能力；授权变更必须审计。
- 页面采用目标样式令牌和组件，不复制来源 CSS 或 Ant Design 依赖。

### 7.3 建议切片顺序

1. `012-organization-access-administration-foundation`：平台表迁移、用户/角色/权限管理、角色授权矩阵。
2. 后续独立切片：组织、员工、雇佣、任职、岗位和负责人。
3. 再后续按真实需求评审菜单管理、审计日志运营和数据权限。

## 8. 总结

`supply` 账号中心证明了角色列表、权限目录和分组授权矩阵的可实现性，但其手工 DDL、Ant Design 视觉、混合授权域和数据权限不能直接复用。下一切片应只萃取信息结构和交互闭环，以目标工程的 Prisma 迁移、稳定权限点、角色授权与客户管理页样式重新实现；组织员工能力另立切片验证。
