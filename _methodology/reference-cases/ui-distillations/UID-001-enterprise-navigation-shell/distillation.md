# 《企业导航壳层系统蒸馏萃取报告》

## 1. 系统总览

### 1.1 系统定位与核心目标

本次只分析已有系统登录后的左侧导航壳层，目标是提炼一个可替换菜单数据、但保持布局和视觉层级稳定的企业导航候选。

### 1.2 解决的业务问题

它解决功能入口较多时的持续定位问题：高频业务入口位于主滚动区，低频管理入口固定在底部，通过搜索、展开和激活反馈降低查找成本。

### 1.3 输入、输出与业务边界

输入是菜单树、图标 key、当前路由和搜索词；输出是可导航的树和底部管理分组。它不负责业务数据权限、后台授权或页面内容。

### 1.4 材料范围与分析可信度

主证据为 `_ref/gf_scm/` 读取时工作区中的前端源码，提交基线为 `3c8b69304d78c7bd01dd9627454fe8d496be8f07`；该参考工作区存在未提交改动，因此报告同时记录具体文件路径。用户截图用于视觉核对。未运行参考系统，未验证动态接口响应、键盘路径和移动端。

## 2. 业务框架

### 2.1 业务域与能力模型

导航将用户入口分为业务/资产入口和管理入口两类。前者承载日常任务，后者承载用户、角色、菜单、日志和资源等治理任务。

### 2.2 端到端业务流程

用户进入系统后，从首页或业务菜单进入目标页面；也可以搜索菜单。管理入口在底部分组中展开，避免与高频业务入口竞争首屏空间。

### 2.3 核心业务实体及关系

核心对象是菜单节点：稳定 ID、名称、路由、图标、子节点和所需 capability。管理分组也是菜单节点，但在壳层布局中拥有固定区域。

### 2.4 业务规则、约束与例外

- 搜索命中子项时保留祖先；
- 当前页面必须有唯一激活反馈；
- 管理分组位于主菜单下方且有明确分隔；
- 没有权限的菜单不应因接口失败回退成全量可见；
- 菜单可见性不能代替服务端权限。

## 3. 系统应用架构

### 3.1 整体分层架构

实现分为菜单数据、远程加载、树转换、组件呈现和视觉令牌五层。候选复用这五个职责，但不复制来源接口和身份系统。

### 3.2 核心模块及职责

- `nav.tsx:9-26,29-113`：菜单数据结构、首页、业务组和管理组；
- `nav-transform.ts:25-110`：将动态树转换为主菜单及底部菜单；
- `useNavMenu.ts:33-158`：远程加载、降级与刷新；
- `Layout.tsx:71-214,324-412`：搜索、递归渲染、品牌、主导航和底部区域；
- `index.less:189-397`：Rail、菜单、管理区、折叠和搜索视觉；
- `icons.tsx`、`icon-map.tsx:15-78`：SVG 图标与稳定 key 映射。

### 3.3 模块协作与调用关系

菜单来源先转换为统一树模型，再拆分主菜单和底部管理分组；搜索分别过滤两棵树；组件根据路由呈现激活态。样式不依赖业务文字。

### 3.4 数据流与控制流

`菜单来源 → 树转换 → 主区/底部区拆分 → 搜索过滤 → 展开状态 → 路由跳转`。接口失败时可以使用静态候选数据，但不能把“成功返回空菜单”误判成失败并回退全量菜单。

### 3.5 领域边界及外部系统边界

候选壳层只定义菜单发现和切换。演示门户可用本地 fixture 模拟 capability；真实项目的身份、会话、菜单来源和最终授权属于项目自己的安全边界。

## 4. 技术框架与技术栈

### 4.1 技术栈总览

来源实现采用 React、React Router、Less、Zustand、内联 SVG 和拼音匹配。候选先沉淀技术栈中立契约、JSON 和 CSS 令牌，React 实现仅用于验证场。

### 4.2 关键技术组件及作用

递归组件渲染层级，`details/summary` 表达展开，`NavLink` 表达路由激活，`localStorage` 仅保存宽度与折叠偏好，图标 registry 将数据 key 映射到实现。

### 4.3 核心目录职责

本报告只读取导航相关前端文件和截图，没有读取业务页面、后端模块或数据库 Schema。

### 4.4 数据、集成与中间件

来源实现可从远程菜单 API 取树；本候选不继承该接口。演示门户采用本地配置，并将 role 到 capability 的绑定放在 fixture 层。

### 4.5 构建、部署与运行模式

当前只形成候选资产，尚未进入验证场构建和运行。后续若获 Gate 批准，将作为现有 React/Vite 验证场的独立 Demo Adapter 接入。

## 5. 核心设计思想与实现方法论

### 5.1 架构模式与设计原则

稳定的是导航壳层和语义槽位，变化的是品牌、菜单、路由、capability 和视觉主题。主业务入口与后台治理入口在空间上分层，但仍共享搜索和权限判断契约。

### 5.2 关键实现策略

先定义菜单 Schema，再决定数据来源；使用语义令牌复现颜色、字号和密度；用稳定 icon key 隔离具体图标库；对主菜单和底部菜单使用同一节点结构与递归渲染规则。

### 5.3 核心架构决策

| 决策 | 背景 | 当前选择 | 证据 | 收益 | 代价与风险 | 置信度 |
|---|---|---|---|---|---|---|
| 管理菜单固定在底部 | 高频业务入口多 | 主区滚动、管理区独立固定 | `Layout.tsx:397-412`、`index.less:216,242-245` | 稳定发现管理入口 | 窄高窗口中管理菜单可能挤压主区 | 高 |
| 导航视觉参数令牌化 | 需要复刻同时允许换主题 | 颜色、字体、宽度、密度转为语义令牌 | `index.less:7-68,189-245` | 易于生成变体 | 令牌过多会增加治理成本 | 高 |
| 菜单树与图标实现分离 | 菜单可远程配置 | 数据保存 icon key，registry 解析 | `icon-map.tsx:15-78` | 配置稳定、可换图标库 | 未知 key 需要明确回退 | 高 |
| 动态空菜单不回退全量静态菜单 | 防止无权限用户看到入口 | 只有接口失败才启用静态回退 | `Layout.tsx:330-334` | 避免权限语义泄漏 | 前端仍不是最终授权边界 | 高 |

### 5.4 可复用的方法论

每次生成页面前先选定来源与版本；按结构、行为、视觉、数据和安全边界分别萃取；来源菜单文字只留在证据层；正式候选使用通用演示门户配置；冲突值保留为待验证变体，不静默覆盖现有正式模板。

## 6. AI/LLM 设计与落地思路

### 6.1 AI 在系统中的定位

本导航运行时未发现必须依赖 AI 的能力。

### 6.2 Agent 或模型执行链路

当前材料未发现产品内 Agent 工作流。

### 6.3 Prompt、Skill 与上下文设计

AI 可根据来源选择记录和菜单 Schema 生成通用配置，但必须输出来源定位、排除项和未确认值。

### 6.4 AI 与业务代码的协作及约束

权限判断、路由保护和菜单数据校验必须由确定性代码完成；AI 不负责运行时授权。

### 6.5 容错、评测、风险与能力边界

AI 不得把多个来源静默混合，也不得根据截图补造折叠、权限或移动端行为。

### 6.6 AI 辅助设计开发的证据

本次用户明确要求 AI 执行来源萃取；这不构成来源系统由 AI 开发的证据。

## 8. 萃取总结

本候选最值得复用的是“主业务导航与底部管理导航分区、共享统一菜单节点契约”的壳层设计。深色 Rail、品牌区、菜单搜索、递归展开、激活反馈、宽度折叠和弱化管理区由语义令牌控制，菜单文字与路由可替换。复用时必须排除来源业务、组织 IAM、专属接口及缓存 key；动态空菜单不得回退全量入口，真实项目仍以服务端授权为最终边界。当前只有源码与截图证据，尚待新切片验证。
