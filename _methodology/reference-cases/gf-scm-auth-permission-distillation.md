# 《gf_scm 认证与权限子系统蒸馏萃取报告》

> 定位：R1 抽象参考案例，不是规范源，不代表 `gf_scm` 已达到最佳实践。  
> 分析日期：2026-08-29  
> 使用边界：只用于提炼认证、账号安全和数据权限的通用原则；禁止复制项目代码、组织模型和环境约束。

## 1. 系统总览

### 1.1 系统定位与核心目标

本报告只分析 `gf_scm` 中与身份、登录、账号锁定、会话、角色授权和行级数据权限相关的材料。目标不是评价整个供应链系统，而是识别能否支持新系统首个认证权限切片的可复用经验。

### 1.2 解决的业务问题

相关材料尝试解决四类问题：确认访问者身份、保护账号凭证、判断用户能否执行操作、限制用户可看到的数据范围。

### 1.3 输入、输出与业务边界

- 输入：登录凭证、用户/角色关系、主体上下文、目标资源和操作。
- 输出：登录状态、公开用户画像、允许/拒绝决定及受限的数据范围。
- 边界：`gf_scm` 同时包含内部员工、企业客户、个人用户及外部平台集成；这些多主体和多平台语义不进入 MCRM。

### 1.4 材料范围与分析可信度

主要证据：

- 认证编排：`_ref/gf_scm/packages/account-center/src/auth/auth.service.ts:31`

- 登录锁定：`_ref/gf_scm/packages/account-center/src/auth/services/login-lock.service.ts:11`
- 最小令牌声明：`_ref/gf_scm/packages/account-center/src/auth/helpers/token.helper.ts:12`
- 统一认证错误：`_ref/gf_scm/packages/account-center/src/common/errors/error-codes.ts:9`

- 行级默认拒绝：`_ref/gf_scm/packages/account-center/src/authorization/modules/row-level/row-level.engine.ts:118`

## 2. 业务框架

### 2.1 业务域与能力模型

认证与权限可以分为四项独立能力：身份档案、凭证认证、访问授权、安全治理。新项目应先明确“谁是谁”，再判断“能做什么”和“能看哪些数据”，不能用一个角色字段同时代替全部概念。

### 2.2 端到端业务流程

```text
提交凭证 → 检查锁定 → 验证凭证 → 检查账号状态
→ 建立登录状态 → 解析最新用户/角色上下文
→ 判断操作权限 → 注入数据范围 → 返回授权结果
```

### 2.3 核心业务实体及关系

- 认证用户：稳定身份及凭证状态。
- 用户档案：姓名、组织、角色和业务属性。
- 角色：一组业务职责，不等于登录身份。
- 资源与操作：授权判断目标。
- 数据范围：主体对业务记录的可见边界。
- 会话与审计事件：登录状态及安全证据。

### 2.4 业务规则、约束与例外

- 认证失败不应泄露账号是否存在。
- 禁用、锁定或缺少授权上下文时拒绝访问。
- 前端控制仅改善体验，不能代替后端授权。
- 行级范围必须在读取和写入前生效。
- 权限依赖异常时不得扩大数据范围。

## 3. 系统应用架构

### 3.1 整体分层架构

当前材料将身份、认证、授权和安全日志拆为不同模块。这个职责分离值得保留，但模块数量和边界需要按项目规模裁剪。

### 3.2 核心模块及职责

| 模块 | 当前职责 | 可复用判断 |
|---|---|---|
| Identity | 查找身份、输出公开画像、隔离凭证字段 | 保留原则，不复制内存数据源 |
| Auth | 登录编排、锁定检查、凭证验证、会话签发 | 保留流程，删除 MCRM 范围外认证方式 |
| Authorization | 角色、权限点、主体上下文、数据范围 | 保留“操作+数据范围”分层，MCRM 固定三角色即可 |
| Security | 登录日志、审计、限流和风险规则 | 首片只保留必要日志与锁定，复杂风险引擎后置 |

### 3.3 模块协作与调用关系

认证完成后只返回安全公开画像；授权在业务请求发生时使用主体上下文重新判断。密码验证和授权计算不是前端职责。

### 3.4 数据流与控制流

值得复用的控制点是：凭证进入认证边界后不再向业务层传播；业务查询在执行前合并授权范围；详情按“业务 ID + 权限条件”一次判断，避免先查出对象再判断。

### 3.5 领域边界及外部系统边界

`gf_scm` 的门户 SSO、组织主数据、客户域和个人域是其项目边界。MCRM 已批准独立账号、独立用户档案且 MVP 不集成外部身份系统，因此必须重新设计，不能沿用其外部主体或租户语义。

## 4. 技术框架与技术栈

### 4.1 技术栈总览

当前账号中心实现采用 TypeScript、NestJS、bcryptjs、JWT、Redis 和 Prisma。这里只记录实现事实，不把它们自动提升为 MCRM 架构决定。

### 4.2 关键技术组件及作用

- bcryptjs：不可逆密码哈希，当前成本参数为 10。
- Redis：失败计数、锁定和会话状态。
- JWT：访问与刷新凭证，声明保持相对收敛。
- Prisma 扩展：尝试统一注入行级数据条件。

### 4.3 核心目录职责

- `src/auth/`：认证和会话。
- `src/authorization/`：角色、权限和数据范围。
- `src/security/`：安全日志、限流与风险。
- `test/auth/`、`test/authorization/`：关键边界测试。

### 4.4 数据、集成与中间件

材料同时存在内存身份、Redis 状态和 Prisma 数据访问。这说明子系统仍在演进，不能把当前存储组合视为稳定参考架构。

### 4.5 构建、部署与运行模式

当前材料未提供足以证明认证权限子系统独立生产部署、容量和恢复目标的完整证据；需由使用项目自己的 Architecture Gate 决定。

## 5. 核心设计思想与实现方法论

### 5.1 架构模式与设计原则

最有价值的不是类或框架，而是六条边界：身份与档案分离、认证与授权分离、公开画像不含凭证、统一失败路径、后端授权权威、授权异常默认拒绝。

### 5.2 关键实现策略

- 密码只保存哈希并通过安全比较函数验证。
- 不存在账号和密码错误走同一失败计数与对外文案。
- 失败计数与锁定状态分开，成功登录清除连续失败。
- 访问凭证尽量只带稳定主体信息，不把长期权限快照固化进凭证。
- 列表查询合并数据范围；详情、更新和删除同时带业务 ID 与范围条件。
- 角色或权限变更后应尽快影响后续请求，不能只信前端缓存。

### 5.3 核心架构决策

| 决策 | 背景 | 当前选择 | 证据 | 收益 | 代价与风险 | 置信度 |
|---|---|---|---|---|---|---|
| 统一登录失败 | 防账号枚举 | 不存在账号和密码错误统一响应 | `auth.service.ts:208`、`error-codes.ts:9` | 减少账号探测 | 运维需依赖内部日志区分原因 | 高 |
| 密码不可逆保存 | 减少凭证泄露后果 | bcrypt 哈希和 compare | `crypto.helper.ts:5` | 不保存明文 | 算法和成本需按项目复审 | 高 |
| 锁定独立建模 | 控制暴力尝试 | 失败计数、锁定键、成功清零 | `login-lock.service.ts:11` | 规则可测试、自动恢复 | 当前 30 分钟不适合 MCRM | 高 |
| 令牌声明收敛 | 降低过期权限快照 | access token 不含 roles/scope | `token.helper.ts:12` | 角色变更更易生效 | 每次授权需要可靠上下文 | 中高 |
| 后端行级限制 | 防前端绕过 | 查询前追加隔离条件并默认拒绝 | `row-level.engine.ts:118` | 统一保护数据 | 通用拦截器易掩盖业务差异 | 中 |

### 5.4 可复用的方法论

通用候选实践清单：

1. 先写角色—操作—数据范围矩阵，再设计页面和接口。
2. 登录规则至少覆盖正确登录、统一失败、连续失败、锁定期、成功清零、禁用账号和强制改密。
3. 密码规则必须在设置/重置入口验证，登录 DTO 的最小长度不能代替密码策略。
4. 客户端不得决定 owner、tenant、department 等授权锚点，必须由可信用户上下文生成。
5. 列表、详情、导出和写入使用同一授权语义；直接 ID 访问必须做越权测试。
6. 授权依赖故障 fail-closed，但失败要显式、可观察、可恢复。
7. 公共实践描述可观察约束和验收，不固化框架类名、数据库或企业平台。

这些内容当前是“参考案例候选”，需在 MCRM 首片实现并验证后，才能晋升为 `_methodology/patterns/` 的正式模式。

## 7. 现存局限、问题与演进建议

### 7.1 当前局限与问题

- 登录 DTO 只校验至少 6 位，与 MCRM 已批准的 8 位且含字母数字不一致。
- 当前锁定为 30 分钟，与 MCRM 的 5 分钟不一致。
- 当前材料未发现完整的首次登录/重置后强制改密闭环。
- 身份服务仍含内存种子账号，不是可直接复用的生产身份仓库。
- 行级引擎对 create/createMany 直接放行；新项目若照搬，客户端可能伪造负责人或隔离字段。
- 复杂的多轨主体、通配权限、RBAC/ABAC/ReBAC 和字段权限远超 MCRM 首片需要。

### 7.2 近期改进

在 MCRM Specification Gate 中先固定三角色矩阵、密码与锁定规则、负责人来源和越权行为，不引入复杂权限配置中心。

### 7.3 中期演进

首片实现后用真实测试验证：账号枚举防护、锁定自动恢复、禁用即时生效、客户端伪造 owner、列表/详情越权和授权依赖故障。

### 7.4 长期方向

只有当角色和权限频繁变化、出现字段级敏感数据或临时协作关系时，再评估可配置 RBAC/ABAC/字段权限；不能因为参考项目已有复杂引擎而提前建设。

| 优先级 | 问题或机会 | 证据 | 建议 | 预期收益 | 成本/前置条件 |
|---|---|---|---|---|---|
| P0 | create 未统一注入授权锚点 | `row-level.engine.ts:158` | MCRM 创建客户时由后端绑定当前销售 | 防止伪造负责人 | 首片集成测试 |
| P0 | 密码/锁定策略不匹配 | `login.dto.ts:21`、`constants.ts:22` | 使用 MCRM 批准规则重新设计 | 需求一致 | Spec Gate 批准 |
| P1 | 强制改密证据不足 | 当前检查未发现对应字段和流程 | 在 MCRM 首片明确状态与验收 | 降低临时密码风险 | 用户档案与认证协同 |
| P2 | 授权模型过度复杂 | 统一授权设计文档 | 首片固定三角色，不建设配置中心 | 降低交付复杂度 | 未来出现真实变化再复审 |

## 8. 萃取总结

`gf_scm` 最值得复用的是认证与授权分层、密码不可逆保存、统一失败路径、锁定状态可恢复、后端权限权威和行级数据默认拒绝；最不应复用的是特定平台集成、复杂多主体模型及当前未完成实现。MCRM 应用最小三角色矩阵打通真实客户数据，再以越权和故障测试验证这些候选实践，验证后方可晋升为通用模式。
