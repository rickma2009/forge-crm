# 《GF_SCM 客户记录工作区专项蒸馏萃取报告》

> 状态：candidate-distillation  
> 分析日期：2026-08-29  
> 目标验证项目：MCRM / 004-customer-record-workspace

## 1. 系统总览

### 1.1 系统定位与核心目标

本次只分析 GF_SCM 桌面端客户管理页面及其工作区 Tab，目标是萃取高密度企业管理页面的稳定交互骨架。

### 1.2 解决的业务问题

用户需要在查询大量记录、发起新增、浏览多个详情时保留工作上下文，并能快速返回列表。

### 1.3 输入、输出与业务边界

输入是查询条件和对象字段，输出是范围内的列表、创建结果与详情。本次不萃取 GF_SCM 的客户分类、合作信息、日志或联系人规则。

### 1.4 材料范围与分析可信度

高可信事实来自 `pages/opportunities/customers/`、`components/ListPage/`、`components/TabBar.tsx`、`lib/tab-store.ts` 和 `index.less`。参考项目在建，结论只能作为候选实践。

## 2. 业务框架

### 2.1 业务域与能力模型

客户管理被拆为查询列表、建立客户、查看详情三类用户任务。

### 2.2 端到端业务流程

客户菜单 → 查询列表 → 新增或详情 → 返回列表；每个任务可在独立页签中切换。

### 2.3 核心业务实体及关系

专项范围只有客户记录及其负责人；GF_SCM 的联系人、合作数据等不进入通用模板。

### 2.4 业务规则、约束与例外

页面只应展示目标项目已批准字段和操作；参考系统的字段与权限不是通用规则。

## 3. 系统应用架构

### 3.1 整体分层架构

页面由工作区壳层、路由页签、列表组合器、表单 Schema 和详情展示组成。

### 3.2 核心模块及职责

- `ListPage` 组合搜索、命令栏、表格、分页和操作列；
- `SchemaForm` 复用新增与编辑字段定义；
- `TabBar` 负责路由工作上下文；
- 客户页面只配置字段、查询、按钮和跳转。

### 3.3 模块协作与调用关系

列表操作通过路由打开新增或详情；URL 驱动激活页签；对象页面完成后回到列表或详情。

### 3.4 数据流与控制流

查询条件进入真实列表请求；表单提交成功后导航；详情由 URL ID 加载。失败必须在当前工作上下文中可见。

### 3.5 领域边界及外部系统边界

连接器、动态 IAM、远程按钮和字段目录属于 GF_SCM 平台能力，不作为新项目模板前置条件。

## 4. 技术框架与技术栈

### 4.1 技术栈总览

当前实现采用 React、React Router、Ant Design、AG Grid、Zustand 和 TanStack Query。

### 4.2 关键技术组件及作用

路由是页签状态来源；Ant Design 提供表单与详情组件；AG Grid 承载 GF_SCM 的复杂表格。

### 4.3 核心目录职责

证据集中在 `pages/opportunities/customers/`、`components/ListPage/`、`components/TabBar.tsx` 和 `index.less`。

### 4.4 数据、集成与中间件

GF_SCM 列表使用连接器及动态授权视图。模板只保留“真实查询契约”，不绑定连接器。

### 4.5 构建、部署与运行模式

本专项不评估部署；页面模式应可适配普通 REST/GraphQL/连接器数据源。

## 5. 核心设计思想与实现方法论

### 5.1 架构模式与设计原则

稳定骨架是“工作区 Tab + 查询列表 + 对象页头 + 分组表单/详情”。列表页负责发现对象，对象页负责聚焦任务。

### 5.2 关键实现策略

查询、命令与结果纵向排列；新增和详情使用相同信息分组；每个详情有独立 URL；页签关闭不删除业务数据。

### 5.3 核心架构决策

| 决策 | 背景 | 当前选择 | 证据 | 收益 | 代价与风险 | 置信度 |
|---|---|---|---|---|---|---|
| 路由驱动页签 | 多任务切换 | URL 创建/激活 Tab | `tab-store.ts`、`TabBar.tsx` | 可刷新、可链接 | 状态同步复杂 | 高 |
| 列表组合器 | 列表重复建设 | 声明字段和操作 | `customers/index.tsx:202-236` | 页面一致 | 通用器易过度复杂 | 高 |
| 表单 Schema 复用 | 新增编辑字段一致 | 共用 Schema | `customers/schema.ts` | 降低漂移 | 动态需求增加抽象成本 | 高 |

### 5.4 可复用的方法论

先固定信息架构和失败行为，再选择表格/表单技术；查询控件必须对应真实接口；业务字段、权限和按钮永远由目标项目 Spec 决定。

## 7. 现存局限、问题与演进建议

### 7.1 当前局限与问题

GF_SCM 的 ListPage、动态授权和 KeepAlive 复杂度较高，直接复制会把平台耦合带入小型项目。

### 7.2 近期改进

在 MCRM 用现有 Ant Table、Form 和 API 验证最小模式。

### 7.3 中期演进

第二个项目验证后，再决定是否提取框架组件或只保留页面模板。

### 7.4 长期方向

只有当多个系统都需要列视图、批量操作和页面缓存时，才评估公共 UI 包。

| 优先级 | 问题或机会 | 证据 | 建议 | 预期收益 | 成本/前置条件 |
|---|---|---|---|---|---|
| P0 | 业务字段污染模板 | GF_SCM 客户字段远多于 MCRM | 模板使用占位字段并要求映射表 | 防止需求漂移 | 需项目 Spec |
| P1 | 通用器过重 | ListPage 依赖连接器/IAM/AG Grid | 先提供轻量模板 | 降低接入成本 | 真实项目验证 |
| P2 | KeepAlive 状态复杂 | `KeepAliveOutlet.tsx` | 默认不缓存未提交页面 | 降低路由风险 | 有明确保留需求再升级 |

## 8. 萃取总结

GF_SCM 客户页面最值得复用的是“路由页签保留任务上下文、查询与命令集中在列表顶部、对象页用统一页头和分组信息承载新增/详情”的三段式结构。它能提升企业数据管理页面的一致性和可定位性，但连接器、动态 IAM、AG Grid、KeepAlive 及大量客户扩展字段属于原系统平台与业务条件。新项目应先用自身字段、权限和真实查询接口验证轻量版本，再决定是否升级为公共组件。
