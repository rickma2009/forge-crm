# 《GF_SCM 企业导航壳层专项蒸馏萃取报告》

## 1. 系统总览

### 1.1 系统定位与核心目标

本报告只分析 `gf_scm/packages/scs-web` 的桌面端导航壳层。它以固定的深色左侧 Rail、浅色顶栏和独立内容区承载高密度企业业务菜单，目标是让用户在模块较多时仍能快速识别系统、查找菜单和保持当前位置。

### 1.2 解决的业务问题

- 菜单数量多、存在父子层级，单层导航难以扩展；
- 用户需要在业务模块间频繁切换，并快速定位功能；
- 内容区需要独立滚动，导航和顶栏保持稳定；
- 不同角色获得的菜单不同，前端不能用静态菜单冒充授权结果。

### 1.3 输入、输出与业务边界

输入是当前用户可见的菜单树、当前路由、搜索词和本地交互偏好；输出是两层为主、可递归的导航树及当前激活状态。本报告不萃取 IAM、Tab 缓存、模拟登录、SCM 菜单内容和业务徽标。

### 1.4 材料范围与分析可信度

证据包括 `Layout.tsx`、`index.less`、`nav.tsx`、`nav-transform.ts`、`icons.tsx` 和 `package.json`。源码可直接证明当前交互实现；截图不作为本次实现依据。设计动机若无明确文档，只标为基于实现的推断。

## 2. 业务框架

### 2.1 业务域与能力模型

导航把系统能力组织为：系统首页、业务模块、模块下功能页、底部管理能力。MCRM 复用时只保留组织方法，不继承 SCM 的业务名称。

### 2.2 端到端业务流程

用户识别系统 → 搜索或展开一级菜单 → 选择二级功能 → 内容区切换并保持导航上下文。菜单搜索保留匹配项及祖先，避免结果失去所属模块。

### 2.3 核心业务实体及关系

核心对象是 `NavigationItem`：稳定 key、显示名称、路由、图标、可选子项和权限可见性。父项负责分组，叶子项负责导航。

### 2.4 业务规则、约束与例外

- 两层菜单默认闭合，减少首次进入的视觉噪声；
- 当前路由必须有唯一激活反馈；
- 搜索命中子项时必须保留并展开父项；
- 权限过滤先于渲染，隐藏菜单不能代替后端权限；
- 空权限不能回退成全量静态业务菜单。

## 3. 系统应用架构

### 3.1 整体分层架构

应用壳层分为菜单数据、菜单转换、交互状态和呈现样式四层。`Layout.tsx` 组合 Rail/Topbar/Main，`nav-transform.ts` 把权限菜单树转成 UI 模型，样式通过设计令牌统一控制。

### 3.2 核心模块及职责

- `Layout.tsx:51-57`：宽度、折叠宽度和持久化键；
- `Layout.tsx:71-92`：递归搜索并保留祖先；
- `Layout.tsx:348-443`：品牌、菜单搜索、递归导航、顶部搜索和账户区；
- `index.less:105-142`：两列两行 App Shell 与顶栏；
- `index.less:190-395`：Rail、激活态、折叠、浮层、拖拽和搜索；
- `nav-transform.ts`：动态树转换与管理分组分离；
- `icons.tsx`：集中管理语义图标。

### 3.3 模块协作与调用关系

权限菜单先转换为稳定前端模型，再由递归菜单组件渲染；路由提供激活态；本地存储只保存宽度和折叠偏好，不保存授权结果。

### 3.4 数据流与控制流

菜单树 → 权限/层级转换 → 搜索过滤 → 展开状态 → 路由跳转。用户调整宽度或折叠后写入本地偏好，刷新时恢复。

### 3.5 领域边界及外部系统边界

导航壳层只负责发现和切换功能，不负责判断业务数据权限。MCRM 仍由现有 Route Guard 和服务端范围控制负责授权。

## 4. 技术框架与技术栈

### 4.1 技术栈总览

当前实现采用 React、React Router、Less、Zustand、`pinyin-pro` 和集中 SVG 图标。MCRM 复用 React Router 与 Less，图标使用已有 Ant Design 图标体系；拼音搜索作为菜单规模增长后的可选增强。

### 4.2 关键技术组件及作用

CSS Grid 固定 Rail/Topbar/Main；原生 `details/summary` 承担层级展开；`localStorage` 保存纯 UI 偏好；递归函数承担树搜索。

### 4.3 核心目录职责

源码集中在 `components/Layout.tsx`、`lib/nav*.ts(x)`、`lib/icons.tsx` 与 `index.less`。本次不读取生成目录、依赖和后端业务模块。

### 4.4 数据、集成与中间件

导航可以接静态配置或权限服务，但可见性必须由已认证用户信息产生。当前 MCRM 规模较小，先用角色驱动静态树，不引入 SCM 的动态 IAM。

### 4.5 构建、部署与运行模式

该模式是前端 App Shell，不增加服务或部署单元。响应式断点把桌面 Rail 转成移动抽屉。

## 5. 核心设计思想与实现方法论

### 5.1 架构模式与设计原则

以“稳定壳层承载变化菜单”为核心：品牌、搜索、菜单、账户和内容滚动边界稳定；业务菜单、角色和路由是配置。

### 5.2 关键实现策略

一级分组默认闭合；搜索时自动展开命中祖先；激活项使用背景与左侧色条双重反馈；折叠后图标仍可识别；宽度、颜色、字体、间距和状态全部令牌化。

### 5.3 核心架构决策

| 决策 | 背景 | 当前选择 | 证据 | 收益 | 代价与风险 | 置信度 |
|---|---|---|---|---|---|---|
| 深色 Rail + 浅色内容 | 高密度业务系统需稳定分区 | `#0f1729` Rail、浅色内容面 | `index.less:190-215` | 导航边界清楚 | 深色区需单独保证对比度 | 高 |
| 两层默认闭合 | 菜单多且需要分组 | 父项展开后显示子项 | `Layout.tsx:137-153` | 降低首屏噪声 | 多一次点击 | 高 |
| 搜索保留祖先 | 子菜单可能无法直接理解归属 | 递归过滤父子树 | `Layout.tsx:71-92` | 结果仍有上下文 | 大树需性能评估 | 高 |
| 折叠与宽度持久化 | 用户屏幕和密度偏好不同 | 64px 折叠、180-400px 拖拽 | `Layout.tsx:51-57, index.less:265-368` | 提高空间控制感 | 状态与响应式处理更复杂 | 高 |

### 5.4 可复用的方法论

先定义导航数据契约与权限边界，再实现呈现；把视觉参数做成令牌；用交互案例覆盖默认、搜索、展开、折叠、激活、移动端和无权限状态；真实项目验证后才晋升为正式模式。

## 6. AI/LLM 设计与落地思路

### 6.1 AI 在系统中的定位

本导航壳层未发现产品内 AI 能力。

### 6.2 Agent 或模型执行链路

当前材料未发现。

### 6.3 Prompt、Skill 与上下文设计

当前材料未发现导航运行时依赖 Prompt 或 Skill。

### 6.4 AI 与业务代码的协作及约束

AI 可根据已批准菜单模型生成配置与测试，但权限过滤和路由守卫必须由确定性代码负责。

### 6.5 容错、评测、风险与能力边界

AI 不得从参考项目推断目标项目权限；菜单名称、层级和图标仍需项目级确认。

### 6.6 AI 辅助设计开发的证据

本次由用户明确要求使用 AI 萃取源码并沉淀方法论；不据此推断 `gf_scm` 原实现由 AI 生成。

## 7. 现存局限、问题与演进建议

### 7.1 当前局限与问题

`gf_scm` 实现支持递归层级，但折叠态浮层和 `details` 的键盘/焦点体验仍需逐项目验证；顶部全局搜索在源码中只是输入框外观，不应被误称为已接通全局搜索。

### 7.2 近期改进

在 MCRM 中先验证两层菜单、菜单搜索、折叠、角色可见性和移动抽屉；全局搜索仅连接客户查询。

### 7.3 中期演进

菜单超过约 30 个叶子项或用户反馈中文检索困难时，再引入拼音搜索；出现跨模块动态授权后再引入服务端菜单树。

### 7.4 长期方向

如多个项目采用并验证，可将框架适配器拆成独立 UI 包；在此之前维持模板和模式，不提前建设通用组件库。

| 优先级 | 问题或机会 | 证据 | 建议 | 预期收益 | 成本/前置条件 |
|---|---|---|---|---|---|
| P1 | 复用时可能把菜单可见性当权限 | `nav-transform.ts` 与 MCRM Route Guard | 明确双层防线 | 避免越权 | 保留后端鉴权 |
| P2 | 全局搜索易成为静态装饰 | `Layout.tsx:420-424` | 每个项目声明搜索范围并接通 | 降低误导 | 需具体查询能力 |
| P3 | 拼音搜索增加依赖 | `pinyin-pro` | 达到规模阈值再启用 | 控制复杂度 | 需中文菜单规模证据 |

## 8. 萃取总结

GF_SCM 导航最值得复用的不是具体菜单，而是“稳定企业壳层 + 配置化两层导航”的设计：深色 Rail 明确系统边界，品牌与搜索固定在上方，业务分组默认闭合，搜索保留祖先，激活态、图标、折叠宽度和响应式行为由统一令牌管理。复用时必须剥离 SCM 业务、动态 IAM、Tab 与模拟登录，并保持目标项目的后端权限为最终防线；只有在 MCRM 真实交互验证后，才可晋升为正式模式。
