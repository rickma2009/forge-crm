# 从 0 到 1 数字化系统搭建指南

> 版本：v0.3-draft
> 更新：2026-08-31
> 适用范围：使用 AI + SDD 从业务问题建设新数字化系统。

## 1. 基本原则

1. **先目标，后系统**：先明确业务成果和系统边界，再选择技术栈。
2. **先规格，后实现**：实现必须能追溯到已批准的验收标准。
3. **证据驱动**：阶段完成必须有文件、检查结果或运行记录作为证据。
4. **人做决策，AI 做分析与执行**：AI 不得越过四个人工 Gate。
5. **最小纵向切片**：优先打通一条端到端业务链路，再水平扩展模块。
6. **参考不等于规范**：`_ref/` 只提供素材，`_methodology/` 才是规范源。
7. **持续回流**：只有经过至少一次真实项目验证的经验才能进入通用模式库。

## 2. 标准生命周期

| 阶段 | 核心问题 | 主要产出 | 推进门禁 |
|---|---|---|---|
| -1. 治理初始化 | 输入怎样归档、AI 按什么规则工作 | `AGENTS.md`、`.specify/`、sources、Gate 初态 | 核心结构检查 |
| 0. 项目章程 | 为什么做、怎样算成功 | `project-charter.md` | Business Gate |
| 1. 业务发现 | 谁在什么流程中遇到什么问题 | `business-context.md`、术语、边界 | Business Gate |
| 2. 架构与技术 Profile | 系统如何承载业务目标 | ADR、架构基线、显式 Profile | Architecture Gate |
| 4. 功能规格 | 这个切片做什么 | requirements、clarification、spec | Spec Gate |
| 5. 验证设计 | 怎样证明它正确 | testcases、traceability | Spec Gate |
| 6. 技术计划 | 技术上如何实现 | plan、ADR、风险与回滚 | Architecture Gate |
| 7. 任务与实现 | 怎样小步交付 | tasks、代码、验证证据 | 自动质量门禁 |
| 8. 评审与发布 | 是否可安全交付 | review、release evidence | Release Gate |
| 9. 运营与回流 | 是否产生业务结果 | 指标、问题、patterns、ADR | 定期复盘 |

## 3. 阶段 -1：治理初始化

在接收和转换第一份业务材料前，先运行技术栈中立的初始化：

```bash
node _methodology/scripts/forge.mjs init <project-directory> --name <project-name>
```

它只建立 `AGENTS.md`、`.specify/memory/`、`.specify/sources/`、requirements/specs 容器和 Gate 初态，不选择数据库、前端框架或部署平台。新项目可脱离本工作台独立版本化；项目内不复制通用 Skill。

初始化不会批准任何 Gate。原始材料必须先进入 `.specify/sources/`，再进入业务发现。

## 4. 阶段 0：项目章程

使用 `templates/project-charter-template.md`，至少明确：

- 业务问题和机会；
- 目标用户、负责人和决策人；
- 可量化成功指标及基线；
- In Scope / Out of Scope；
- 时间、合规、数据和组织约束；
- MVP 假设及停止条件。

禁止在业务目标尚未确认时，仅因参考项目已有某技术就直接选型。

## 5. 阶段 1：业务发现与系统边界

使用 `templates/business-context-template.md`，完成：

- As-Is 与 To-Be 业务流程；
- 角色、权限责任和关键决策点；
- 领域术语与业务规则；
- 上下游系统、数据所有者和主数据来源；
- 系统边界、人工兜底流程和例外场景；
- NFR 初始预算：安全、性能、可用性、审计、合规。

Business Gate 未通过，不进入架构和编码。

## 6. 阶段 2：架构决策、技术 Profile 与项目骨架

### 5.1 技术选型

技术选型必须记录项目级 ADR，包括背景、选项、决策、后果和复审条件。不得把 `gf_scm` 的 CAS、数据库、主键、迁移方式、UI 组件或服务管理工具自动继承为新项目约束。

### 5.2 最小骨架

Architecture Gate 通过并明确技术选择后，才应用 Profile：

```bash
node _methodology/scripts/forge.mjs apply-profile <project-directory> typescript-enterprise-web
```

Profile 是显式选择的工程契约，不是全局默认。`typescript-enterprise-web` v0.2 会生成带冻结锁文件的 React、NestJS、PostgreSQL/Prisma 最小工程；只有实际运行 `pnpm verify` 后，具体生成项目才能声明工程基线通过。

骨架只需要证明以下能力：

- 安装、启动和停止方式明确；
- 前后端或服务边界可运行；
- 配置从环境注入；
- 健康检查可观测；
- 最小 typecheck、lint、test 命令存在且真实可运行；
- CI 能执行同一组质量命令。

项目是工作台根仓库直接跟踪的子目录时，CI workflow 应放在根仓库 `.github/workflows/`，并明确引用项目目录；不要在非独立 Git 项目中创建不会被平台识别的嵌套 workflow。独立项目继续在自己的仓库维护 CI。

## 7. 治理目录与 Skills

项目统一采用：

```text
<project>/
├── AGENTS.md
├── CLAUDE.md -> AGENTS.md
└── .specify/
    ├── memory/
    │   ├── constitution.md
    │   ├── project-charter.md
    │   └── business-context.md
    ├── specs/
    └── templates/
```

工作台首次使用时先初始化方法论级 Skills；项目默认复用工作台能力，不重复复制：

```bash
node _methodology/scripts/init-skills.mjs
node _methodology/scripts/init-skills.mjs --check
```

规则：

- 禁止创建 `_spec/`；
- `AGENTS.md` 是短小的执行路由，不重复粘贴全部知识库；
- constitution 只放稳定且可执行的项目约束；
- 企业环境约束与具体项目约束必须分层；
- 模板从 `_methodology/templates/` 获取，不从 `gf_scm/.specify/` 复制。
- 必需和条件 Skills 按 `07-Skills初始化与使用规范.md` 管理；只有项目专属且重复使用的能力才进入项目本地 Skill。

## 8. 阶段 4—6：Spec、Testcases、Plan

原始材料先按 `06-原始需求与转换管理规范.md` 进入 `.specify/sources/`，再在 `.specify/requirements/` 中形成业务可评审需求。Business Gate 通过后才拆分功能 Spec。

### 7.1 功能目录

```text
.specify/specs/<feature-id>-<feature-name>/
├── README.md
├── requirements/original.md
├── clarification.md
├── spec.md
├── testcases.md
├── plan.md
├── tasks.md
├── traceability.md
├── review.md
└── pipeline-state.json
```

### 7.2 文档职责

| 文档 | 回答 | 禁止内容 |
|---|---|---|
| `spec.md` | What / Why | 文件路径、类名、SQL、实现方案 |
| `testcases.md` | Verify | 实现代码、虚构的通过结果 |
| `plan.md` | How | 未经批准的新业务需求 |
| `tasks.md` | Execute | 无来源、无验收标准的任务 |
| `traceability.md` | Evidence chain | 无效或无法定位的 ID |

### 7.3 稳定 ID

需求和交付对象使用：`BUS-*`、`REQ-*`、`NFR-*`、`US-*`、`AC-*`、`TC-*`、`API-*`、`TASK-*`、`ADR-*`。具体规则见 `04-需求追溯规范.md`。

## 9. 阶段 7：实现

1. 从最小纵向切片开始，按任务依赖执行。
2. 每个任务完成时记录实际变更和验证证据。
3. 变更业务语义时回到 Spec Gate，禁止只改代码。
4. 变更系统边界、数据模型或安全策略时回到 Architecture Gate。
5. AI 可自动修复低风险实现问题，但不得自行扩大范围、降低质量门槛或执行生产副作用。

## 10. 阶段 8：评审与发布

评审至少覆盖：

- 需求一致性与追溯完整性；
- 功能、边界和异常场景；
- 架构、数据、安全与隐私；
- 性能、可观测性和可恢复性；
- 部署、迁移和回滚；
- 文档与运营准备。

Release Gate 需要明确批准人、证据链接、遗留风险和回滚条件。

## 11. 阶段 9：运营与方法论回流

上线后对比项目章程中的业务指标，区分：

- 功能是否正确；
- 用户是否采用；
- 业务指标是否改善；
- 运维成本是否可接受。

经验进入 `_methodology/patterns/` 前必须写清适用范围、反例、来源项目和验证次数。单次事故或单项目偏好不能直接升级为全局铁律。

### 10.1 交互与功能资产回流

当用户指出某个页面、交互或功能值得跨项目复用时：

1. 有源码时以源码、样式、路由和测试为主证据，截图只补充视觉核对；
2. 先在 `reference-cases/` 记录事实、推断、保留项、排除项和适用边界；
3. 在目标项目建立独立 Spec 和验收用例，不用模板绕过项目 Gate；
4. 按 `09-资产类型、成熟度与晋升规范.md` 分别记录实现、交互、项目采用和业务验证，不再用单一 `validated-once` 掩盖证据差异；
5. 同步提供 `templates/` 接入骨架、`examples/` 可交互案例和 `scripts/` 自动检查；
6. 后续项目进入相同设计阶段时，AI 主动提示已有候选，由项目负责人决定是否采用。

企业双层导航的当前候选见 `patterns/enterprise-two-level-navigation-shell.md`。

列表—新增—详情页面的当前候选见 `patterns/record-management-workspace.md`。

进入企业系统页面规划或原型设计前，先使用 `08-企业管理系统交互模式分类方法.md` 对页面、操作、展示、状态和特殊操作进行分类。新场景先使用 `templates/ui/interaction-pattern-candidate-template.md` 登记；未经过真实项目验证的内容不得直接标记为正式模式。

## 12. 推荐推进方式

每个新项目先完成一个 1—2 周可验收的纵向切片。金标准示例见：

`examples/000-golden-slice-customer-lead/`

在 Specification Gate 前运行规格阶段检查：

```bash
bash _methodology/scripts/check-sdd.sh <feature-directory> spec
```

完成 Plan、Tasks、实现与评审后再运行完整检查：

```bash
bash _methodology/scripts/check-sdd.sh <feature-directory> full
```
