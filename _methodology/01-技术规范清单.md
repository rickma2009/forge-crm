# 技术规范分层清单

> 版本：v0.2  
> 更新：2026-08-29  
> 本文定义如何建立技术规范，不替任何项目预先决定技术栈。

## 1. 四层规范模型

| 层级 | 内容 | 示例 | 维护位置 |
|---|---|---|---|
| 通用原则 | 与技术栈无关的工程原则 | 安全默认拒绝、配置不入库、可观测 | `_methodology/` |
| 技术栈 Profile | 某技术组合的推荐配置 | TypeScript 全栈、Java 服务 | `_methodology/profiles/` |
| 组织约束 | 企业基础设施与合规要求 | SSO、配置中心、发布平台 | 组织级文档 |
| 项目约束 | 本项目的明确决策 | schema、主键、SLA、模块边界 | 项目 constitution/ADR |

低层规则不得冒充高层通用原则。例如某项目采用 CAS、UUID `VARCHAR(36)`、手写 DDL 或某个 ListPage 组件，都不自动适用于新项目。

## 2. 通用工程原则

### 2.1 单一事实源

- 业务规则只能有一个权威定义位置。
- API、数据模型和配置应尽量机器可校验。
- 文档与实现冲突时停止推进，先确定权威来源并修复漂移。

### 2.2 最小充分变更

- 每次变更必须能追溯到批准的需求或缺陷。
- 不顺带重构无关模块。
- 复制代码前先判断依赖、业务耦合和许可证风险。

### 2.3 配置与秘密

- 密钥、密码、Token 不进入代码、文档、日志和版本库。
- 提交 `.env.example` 或等价配置契约，但不提交真实值。
- 启动时验证必需配置，安全相关配置缺失时 fail-closed。

### 2.4 数据安全

- 明确数据所有者、分类分级、保留周期和删除方式。
- 权限校验在可信服务端执行。
- 敏感字段遵循最小采集、最小展示和最小授权。
- 数据结构变更必须有兼容、迁移、验证和回滚方案。

### 2.5 可观测与恢复

- 健康检查必须区分存活、就绪和关键依赖状态。
- 日志包含可关联请求的标识，不记录秘密和不必要的个人数据。
- 瞬时失败允许恢复；降级必须范围最小、时间有界、可观测。
- 发布前明确告警、回滚触发条件和恢复验证方法。

## 3. 质量基线

所有项目必须提供真实可运行的标准入口：

| 能力 | 最低要求 |
|---|---|
| format | 统一格式或明确不启用的理由 |
| lint | 检查高风险代码与约定 |
| typecheck/compile | 静态验证通过 |
| test | 至少覆盖当前纵向切片的核心行为 |
| build/package | CI 或发布环境可重复生成制品 |
| start/health | 本地或测试环境可启动并检查健康 |

不得一边在模板中要求测试优先和覆盖目标，一边在执行规范中默认禁止运行测试。校验范围可以按风险缩小，但涉及的最小充分校验必须执行。

## 4. 架构选择规则

选择 monorepo、微服务、ORM、消息队列、前端框架或认证方案前，应回答：

1. 它解决哪个已确认约束？
2. 更简单方案为何不够？
3. 团队是否具备维护能力？
4. 失败和退出成本是什么？
5. 何时重新评估？

重大决策写入项目 ADR，不在通用规范中硬编码。

## 5. API 与契约

- API 先定义业务语义、鉴权、幂等、错误和兼容策略。
- 契约应可生成类型或被自动验证。
- 破坏性变更必须显式版本化或提供迁移窗口。
- 接口错误不得统一伪装为成功响应。
- 每个 API 必须能追溯到需求和测试。

## 6. 前端与体验

- 先定义用户任务、信息层级、状态和异常，再选择组件。
- 使用项目自己的设计 Token，禁止把某个参考项目的品牌或业务组件当成通用标准。
- 必须覆盖加载、空状态、错误、无权限、重复提交和弱网场景。
- 可访问性、键盘操作、响应式范围由项目 NFR 明确。

## 7. AI 执行规则

- 修改前读取项目 `AGENTS.md`、constitution 和当前功能规格。
- 保留用户已有改动，执行与任务直接相关的最小变更。
- 对不确定事实进行验证，不把参考案例当成权威。
- 不虚构测试、构建、部署或人工批准结果。
- 未经授权不发布、不部署、不写生产数据、不扩大范围。
- 完成时报告变更、验证证据、遗留风险和未完成项。

## 8. 项目 Profile 示例

TypeScript 全栈可以选择 pnpm workspace、React、NestJS、PostgreSQL、Zod 等，但必须由项目 ADR 确认；这只是可选 Profile，不是 sdd-forge 的强制技术栈。
