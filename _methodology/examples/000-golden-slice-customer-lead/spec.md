# 功能规格：客户线索登记

> 功能编号：000  
> 状态：specified-example  
> Spec Gate：example-approved

## 1. 目标与范围

- 关联目标：BUS-001
- In Scope：创建、校验、邮箱规范化、活动线索去重、按 ID 查询。
- Out of Scope：UI、认证、分配、评分、转化、真实数据库。

## 2. 用户故事

### US-001 登记可跟进线索

作为销售人员，我希望登记结构化的客户联系方式，以便后续跟进使用一致、可查的数据。

## 3. 功能需求

| ID | 需求 | 优先级 |
|---|---|---|
| REQ-001 | 姓名、邮箱和来源均有效时创建活动线索 | P0 |
| REQ-002 | 规范化邮箱相同的活动线索不得重复创建 | P0 |
| REQ-003 | 创建成功后可按返回 ID 查询同一条线索 | P0 |

## 4. 验收标准

| ID | 关联需求 | Given | When | Then |
|---|---|---|---|---|
| AC-001 | REQ-001 | 三个必填字段有效 | 创建线索 | 返回唯一 ID、`active` 状态和创建时间 |
| AC-002 | REQ-001 | 邮箱含大写或首尾空格 | 创建线索 | 保存规范化后的小写邮箱 |
| AC-003 | REQ-001 | 任一必填字段为空或邮箱格式无效 | 创建线索 | 返回 `VALIDATION_ERROR`，不创建记录 |
| AC-004 | REQ-002 | 已存在相同规范化邮箱的活动线索 | 再次创建 | 返回 `DUPLICATE_EMAIL`，不创建第二条记录 |
| AC-005 | REQ-003 | 线索已创建 | 按 ID 查询 | 返回该线索；未知 ID 返回 `null` |

## 5. 非功能需求

| ID | 维度 | 要求 | 验证 |
|---|---|---|---|
| NFR-001 | 可重复验证 | 不依赖网络或外部服务即可验证核心行为 | 使用 Node 内置测试运行器 |

## 6. 边界

- 姓名和来源去除首尾空格后不得为空。
- 本示例只识别常见邮箱结构，不宣称符合全部国际邮箱标准。
- 删除、关闭线索和跨租户去重不在范围内。
