# 需求追溯规范

> 版本：v0.2

## 1. ID 体系

| ID | 对象 | 示例 |
|---|---|---|
| `BUS-*` | 业务目标 | BUS-001 |
| `REQ-*` | 功能需求 | REQ-001 |
| `NFR-*` | 非功能需求 | NFR-SEC-001 |
| `US-*` | 用户故事 | US-001 |
| `AC-*` | 验收标准 | AC-001 |
| `TC-*` | 测试用例 | TC-API-001 |
| `API-*` | 接口契约 | API-001 |
| `TASK-*` | 实现任务 | TASK-001 |
| `ADR-*` | 架构决策 | ADR-001 |

ID 创建后不得重新用于其他语义。删除对象时保留 ID 并标记废弃。

## 2. 最小追溯链

```text
BUS → REQ/NFR → US → AC → TC → TASK → Evidence
                           ↘ API/ADR ↗
```

规则：

- 每个 REQ/NFR 至少关联一个 AC；
- 每个 AC 至少关联一个 TC；
- 每个 TASK 至少关联一个 REQ、NFR、AC 或技术 ADR；
- 每个实现证据必须能回到 TASK；
- 不允许用 TASK 反向创造未批准的需求。

## 3. 追溯矩阵字段

| 字段 | 含义 |
|---|---|
| 目标 | 关联 BUS |
| 需求 | REQ/NFR |
| 验收 | AC |
| 测试 | TC |
| 技术 | API/ADR，可选 |
| 任务 | TASK |
| 证据 | 测试结果、提交、截图或运行记录 |
| 状态 | planned/implemented/verified/accepted |

## 4. 变更控制

- 每次新增、修改或补充需求逻辑：先追加不可改写来源，再把有效变化整合回业务需求或切片的完整当前态需求文档；增量说明不能替代完整需求；
- 修改业务语义：更新 original/clarification/spec 以及对应 REQ、AC、TC 和追溯关系，重新通过 Spec Gate；
- 修改 NFR 或架构：更新 plan/ADR，重新通过 Architecture Gate；
- 仅实现细节变化：更新 plan/tasks，并保持原 AC 不变；
- 紧急修复：至少补充缺陷、预期行为、回归测试和事后追溯。

变更回写完成标准：新来源已归档；完整当前态需求无需依赖聊天记录或逐份增量材料即可独立阅读；被替代、废弃和待确认内容已标明；追溯矩阵与 Gate 状态一致。

## 5. 完整性检查

发布前确认不存在：

- 无来源的需求；
- 无验收标准的 P0/P1 需求；
- 无测试的验收标准；
- 无需求或 ADR 来源的任务；
- 无验证证据却标记完成的任务；
- 代码改变业务行为但 Spec 未更新的情况。
