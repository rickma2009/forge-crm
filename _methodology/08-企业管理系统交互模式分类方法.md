# 企业管理系统交互模式分类与沉淀方法

> 版本：v0.1  
> 更新：2026-08-30  
> 状态：候选方法论，待持续补充与跨项目验证  
> 适用范围：桌面端为主的企业管理系统原型设计、功能 Spec、UI 设计和前后端协作  
> 已有验证样本：企业双层导航壳层、记录管理工作区

## 1. 核心结论

企业管理系统的大部分页面结构、操作入口、状态反馈和异常处理具有明显重复性，可以沉淀为标准交互模式，并在后续项目中通过组合和配置完成原型设计。

目标不是消除前端设计，而是把前端工作从“每次自由创作”转变为：

1. 选择经过验证的页面模式；
2. 配置项目的业务对象、字段、角色和操作；
3. 补充项目特有的状态流转、权限、异常和风险控制；
4. 根据接口契约实现并验证真实行为。

因此，标准模式可以覆盖大量通用表现，但不能替代业务需求、项目 Spec、人工 Gate 或服务端授权。页面看起来相似，不代表业务语义相同。

## 2. 目标与非目标

### 2.1 目标

- 建立企业系统页面、操作、展示和特殊交互的共同语言；
- 降低原型、产品、设计、前端和后端之间的沟通成本；
- 让页面方案能够从项目 Spec 和标准模式中组合出来；
- 让相同交互的权限、反馈、失败行为和验收方式保持一致；
- 为后续补充前端操作、UI 展示页和特殊操作页提供稳定分类；
- 为 Open Design 等原型执行工具提供明确、可复用的输入约束。

### 2.2 非目标

- 不通过页面模板猜测业务规则；
- 不把 CRUD 等同于完整的企业业务；
- 不规定某个前端框架、组件库或后端技术栈；
- 不把尚未在真实项目验证的做法称为最佳实践；
- 不用客户端隐藏按钮代替服务端权限校验；
- 不因采用模板而跳过 Business、Specification、Architecture 或 Release Gate。

## 3. 分类模型

一个完整交互场景至少由六类信息共同定义：

```text
业务意图
  └── 页面模式：用户在哪种工作空间中完成任务
      └── 展示模式：信息如何组织和呈现
          └── 操作模式：用户能发起什么动作
              └── 状态与反馈：动作前后页面如何响应
                  └── 特殊约束：权限、并发、异步、敏感与不可逆风险
```

建议使用以下分类编号，便于后续建立索引：

| 类别 | 编号前缀 | 回答的问题 | 示例 |
|---|---|---|---|
| 页面模式 | `EPM-PAGE-*` | 用户在哪完成任务 | 列表、详情、向导、审批中心 |
| 操作模式 | `EPM-ACT-*` | 用户发起什么动作 | 新建、提交、分配、导入 |
| 展示模式 | `EPM-VIEW-*` | 信息怎样呈现 | 表格、树、时间线、看板 |
| 状态反馈 | `EPM-STATE-*` | 系统当前发生什么 | 加载、空数据、失败、冲突 |
| 特殊操作 | `EPM-SPECIAL-*` | 哪些动作需要额外治理 | 批量、异步、不可逆、敏感 |
| 组合场景 | `EPM-SCENE-*` | 多种模式如何形成任务闭环 | 查询—新增—详情、提交—审批 |

编号只用于方法论资产索引，不替代项目中的 `REQ-*`、`AC-*`、`TC-*` 等追溯 ID。

## 4. 页面模式分类

### 4.1 系统与任务入口类

| 候选编号 | 页面模式 | 典型场景 | 主要组成 | 关键边界 |
|---|---|---|---|---|
| `EPM-PAGE-001` | 应用壳层 | 多模块企业系统 | 导航、顶栏、内容区、账户区 | 菜单可见性不能代替授权 |
| `EPM-PAGE-002` | 工作台 | 待办、提醒、快捷入口 | 任务卡片、指标、消息、快捷操作 | 不展示无法解释或无数据来源的指标 |
| `EPM-PAGE-003` | 任务中心 | 导入、导出、计算、通知任务 | 进度、结果、失败原因、重试 | 异步状态必须来自真实任务状态 |
| `EPM-PAGE-004` | 审批中心 | 待办、已办、抄送 | 队列、摘要、审批动作、意见 | 权限、代理、会签规则来自业务 Spec |

### 6.3 状态与反馈

每种页面至少检查以下状态，不得只设计“有数据且成功”的理想界面：

| 候选编号 | 状态 | 最低要求 |
|---|---|---|
| `EPM-STATE-001` | 初始 | 告知用户从哪里开始或当前默认条件 |
| `EPM-STATE-002` | 加载 | 显示加载范围，避免重复提交 |
| `EPM-STATE-003` | 空数据 | 区分无数据、无搜索结果和无权限 |
| `EPM-STATE-004` | 成功 | 说明完成对象、影响范围和下一步 |
| `EPM-STATE-005` | 校验失败 | 定位字段或记录，并保留用户输入 |
| `EPM-STATE-006` | 业务拒绝 | 解释不满足的业务前置条件 |
| `EPM-STATE-007` | 系统失败 | 提供可理解原因、重试或恢复路径 |
| `EPM-STATE-008` | 部分成功 | 明确成功、失败和未处理范围 |
| `EPM-STATE-009` | 权限不足 | 不泄露不可见对象的敏感信息 |
| `EPM-STATE-010` | 对象不存在 | 区分删除、失效或地址错误的可行动信息 |
| `EPM-STATE-011` | 并发冲突 | 展示版本变化，并提供刷新、比较或重新提交 |
| `EPM-STATE-012` | 异步处理中 | 提供任务状态、离开页面后的查询入口 |

## 7. 特殊操作分类

特殊操作不是一种视觉样式，而是需要额外规则、反馈和验收的风险场景。

| 候选编号 | 类型 | 典型例子 | 必须补充的设计 |
|---|---|---|---|
| `EPM-SPECIAL-001` | 不可逆/破坏性 | 物理删除、终止、覆盖 | 影响范围、二次确认、授权、审计 |
| `EPM-SPECIAL-002` | 批量操作 | 批量删除、分配、改状态 | 选择语义、预检查、部分成功、结果下载 |
| `EPM-SPECIAL-003` | 异步长任务 | 大批量导入、导出、计算 | 任务 ID、进度、通知、取消、重试 |
| `EPM-SPECIAL-004` | 敏感操作 | 导出隐私数据、重置凭据 | 二次认证、脱敏、水印、有效期、审计 |
| `EPM-SPECIAL-005` | 并发编辑 | 多人编辑同一记录 | 版本号、冲突检测、对比、覆盖规则 |
| `EPM-SPECIAL-006` | 跨对象级联 | 删除组织、停用规则 | 依赖检查、影响预览、事务与补偿 |
| `EPM-SPECIAL-007` | 状态机约束 | 审批、工单、发布 | 允许迁移、守卫条件、失败原因、回退 |
| `EPM-SPECIAL-008` | 模拟后执行 | 规则发布、批量更新 | 预演结果、确认快照、正式执行一致性 |
| `EPM-SPECIAL-009` | 外部系统调用 | 同步 ERP、发送消息 | 幂等、超时、重试、补偿、外部状态 |
| `EPM-SPECIAL-010` | 锁定与占用 | 结账、编辑锁、资源预占 | 锁所有者、过期、释放、管理员处理 |

## 8. 操作行为契约

每一个可复用操作都应记录完整行为，而不只是按钮名称和位置。

| 契约项 | 必须回答的问题 |
|---|---|
| 业务意图 | 用户为什么执行这个动作 |
| 作用对象 | 单条、多条、查询结果还是整个业务范围 |
| 可见条件 | 哪些角色、状态和页面上下文可以看到 |
| 可用条件 | 什么条件下按钮可执行，禁用时如何解释 |
| 输入 | 必填参数、附件、意见或二次确认内容 |
| 前置校验 | 客户端提示与服务端权威校验分别是什么 |
| 执行方式 | 同步、异步、事务、幂等和超时约束 |
| 成功结果 | 对象状态、页面跳转、刷新范围和后续入口 |
| 失败结果 | 校验、业务拒绝、系统失败、部分成功如何反馈 |
| 可恢复性 | 能否撤销、重试、补偿或恢复版本 |
| 权限与审计 | 服务端授权、操作记录和敏感信息处理 |
| 验收证据 | 对应 `AC-*`、`TC-*`、接口结果和浏览器证据 |

| 候选编号 | 组合场景 | 页面组合 | 主要操作 | 必须关注 |
|---|---|---|---|---|
| `EPM-SCENE-001` | 查询—新增—详情 | 列表 + 新建 + 详情 | 查询、重置、新增、打开详情 | URL、权限、保存失败、返回上下文 |
| `EPM-SCENE-002` | 查询—编辑—归档 | 列表 + 编辑/抽屉 + 详情 | 编辑、保存、归档、恢复 | 并发、字段权限、历史记录 |
| `EPM-SCENE-003` | 提交—审批—生效 | 编辑 + 流程实例 + 审批中心 | 提交、撤回、同意、驳回 | 状态机、会签、代理、审计 |
| `EPM-SCENE-004` | 导入—校验—执行 | 导入向导 + 任务中心 + 结果页 | 上传、映射、预检、执行、重试 | 幂等、部分成功、错误定位 |
| `EPM-SCENE-005` | 规则—模拟—发布 | 规则设计 + 差异视图 + 审计 | 编辑、模拟、发布、回滚 | 冲突、版本、生效范围 |
| `EPM-SCENE-006` | 看板—流转—追踪 | 看板 + 详情 + 时间线 | 拖动、分配、评论、关闭 | 状态守卫、权限、并发 |
| `EPM-SCENE-007` | 报表—钻取—导出 | 指标看板 + 分析报表 + 导出任务 | 筛选、钻取、导出 | 指标口径、明细权限、数据时效 |

## 10. 从业务需求到页面方案

推荐按以下顺序形成项目页面方案：

1. 从详细需求确认角色、任务、对象、规则、状态和异常；
2. 识别用户任务属于哪类组合场景；
3. 从页面模式中选择候选页面骨架；
4. 为每个页面配置展示模式和操作模式；
5. 为每个操作补齐行为契约；
6. 识别特殊操作并增加风险控制；
7. 把页面、操作和状态映射到 `REQ-*`、`AC-*`、`TC-*`；
8. 通过 Specification Gate 后形成原型；
9. 通过 Architecture Gate 后落实接口、事务、并发、审计等技术方案；
10. 使用真实接口和浏览器证据完成验收。

页面模板负责提供起点，目标项目 Spec 负责决定最终行为。如果模板与已批准 Spec 冲突，以项目 Spec 为准，并记录是否需要回流方法论。

## 11. 与后端、前端和 Open Design 的关系

### 11.1 前后端职责

标准化后，前端仍需负责：

- 信息架构、操作可发现性和可访问性；
- 表单和状态反馈；
- 页面上下文、响应式和高密度信息呈现；
- 对服务端结果的准确表达；
- 真实浏览器交互和异常状态验证。

后端重点负责：

- 权威业务规则、权限和数据范围；
- 状态机、事务、幂等、并发与补偿；
- 查询、聚合、异步任务和外部集成；
- 审计、隐私、安全和可观测性。

这意味着后续项目可以减少重复页面设计，但不能只考虑后端。

### 11.2 Open Design 的位置

本分类方法定义“有哪些页面与行为、应遵守什么边界”；Open Design 等工具负责依据项目 Brief、设计系统和这些约束生成或迭代原型。

推荐输入结构是：

```text
项目业务 Spec
+ 本文的页面/操作/展示/特殊操作分类
+ 已验证 patterns 和 UI templates
+ 项目品牌与设计令牌
= 可评审原型
```

工具生成的原型仍是设计建议或评审草案，不能自动成为业务规则或 Gate 批准证据。

## 12. 模式资产的沉淀与晋升

每个新增场景使用 [`templates/ui/interaction-pattern-candidate-template.md`](templates/ui/interaction-pattern-candidate-template.md) 登记，并执行以下生命周期：

```text
来源证据
  → reference-cases 候选萃取
  → 目标项目 Spec 与验收用例
  → 真实项目实现和浏览器验证
  → patterns/ 正式候选模式
  → templates/ 接入骨架
  → examples/ 金标准交互案例
  → scripts/ 自动检查
```

状态建议：

| 状态 | 含义 | 是否可直接推荐给新项目 |
|---|---|---|
| `idea` | 仅有经验或设想 | 否，只能用于讨论 |
| `candidate` | 有明确结构、边界和验收草案 | 可提示，必须由项目决策 |
| `validated-once` | 至少一个真实项目验证 | 可作为候选起点 |
| `validated-multiple` | 多项目验证并记录差异 | 可优先推荐，仍不能覆盖项目 Spec |
| `deprecated` | 已发现重大缺陷或不再适用 | 否，作为反例保留 |

## 14. 当前已确认、未确认与 Gate 状态

### 已确认

- 企业系统交互可以按页面、操作、展示、状态、特殊操作和组合场景进行分类；
- 标准模式应包含行为契约、适用边界和验收要求，而不只是页面截图；
- 现有双层导航壳层和记录管理工作区可作为首批验证样本；
- Open Design 可以消费这些约束生成原型，但不替代项目 Spec 和人工 Gate。

### 尚未确认

- 各类别的完整场景数量与优先级；
- 哪些模式需要拆分为独立模板和可交互案例；
- 移动端、复杂图形编辑、实时协同等是否纳入当前范围；
- 第二个真实项目采用现有模式时会出现哪些差异。

### Gate 状态

本文属于候选方法论和分类草案，不代表任何项目的 Business Gate 或 Specification Gate 已通过。当前允许继续补充场景、来源证据、候选卡片和验收草案；在详细需求与人工 Gate 前，禁止据此直接固化项目业务规则或进入实现。
