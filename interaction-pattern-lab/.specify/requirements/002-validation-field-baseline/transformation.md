# REQSRC-007/008 增量转换与冲突分析

## 1. 来源

| 来源 ID | 作用 | 当前影响 |
|---|---|---|
| `REQSRC-007` | 将目录重新定义为“企业交互模式验证场” | 重新打开 Business Gate；历史产品化批准不再代表当前边界 |
| `REQSRC-008` | 确认 99 项目录管理、首个新增切片、状态、样式、证据与责任 | 关闭新定位下的业务澄清问题，形成 Gate 评审候选基线 |

## 2. 转换原则

- 用户原文保持不可改写；编号回答通过同一来源中的问答上下文解释；
- 分类项、模式资产、交互演示、验证切片和真实项目采用分开；
- 业务结果与技术实现分开；JSON Schema、loader 和测试 runner 留给 Architecture Gate；
- 历史实现和 Gate 证据保留，但必须标明适用切片和被新定位取代的边界；
- 不因用户授权继续整理而推定任何人工 Gate 已批准。

## 3. 关键转换

| 用户确认 | 转换结果 |
|---|---|
| 全目录可浏览 + 单一新增场景 | `BUS-001`、`BUS-004`、`REQ-201`、切片 002 候选 |
| 统一 React 应用 | 业务要求 `REQ-208`；是否沿用当前技术版本留给 Architecture Gate |
| 浏览器内确定性数据 | `REQ-211`、`NFR-205` |
| 无 Demo 项展示说明 | `REQ-206`，禁止假交互和假成熟度 |
| 三层权威与三条状态线 | `REQ-202`、`REQ-207`、`NFR-206` |
| 批量选择与部分成功 | `REQ-213`—`REQ-219`、`AC-201`—`AC-207` |
| 场景契约 | `REQ-209`、`REQ-210`，具体格式后置 |
| 中性设计系统 | `REQ-212`，排除来源品牌值的普适化 |
| 观察任务基线 | `BUS-003`，不足时保持 `baseline-pending` |

## 4. 与历史 001 基线的冲突

| 历史结论 | 新基线 | 处理 |
|---|---|---|
| 首期只在目录展示两个模式 | 99 项全部可浏览，仍只少量提供 Demo | 001 保留为历史切片；当前以 002 业务基线为准 |
| `validated-once` 单一状态模型 | 使用方法论 09 的分层成熟度 | 旧标签仅历史兼容，UI 必须纠正 |
| 模式投影只需两个 Adapter | 目录必须允许无 Demo 项并移除“正好两个”限制 | 新 Architecture Gate 重新设计扩展机制 |
| 方法论不建立机器可读清单 | 多应用消费已成为真实需要，建立权威资产索引 | 触发 ADR-001 复审条件；不得静默扩展旧 ADR |
| 旧 Business/Architecture/Release Gate 已批准 | 只对历史 001 切片和当时边界有效 | 新定位继续保持 Business Gate reopened |

## 5. 事实、判断与未知

### 已确认事实

- 方法论 08 当前有 99 个分类编号；
- Lab 已有两个可运行历史 Demo；
- 两个 Demo 的成熟度不同，当前 UI 存在统一“已验证一次”的错误表达；
- 当前目录、类型和投影检查含“仅两个 Demo”的硬编码；
- `REQSRC-008` 已确认目标、首个新增切片、样式与责任边界。

### 设计判断

- 批量分配比异步导入更适合作为首个最小验证切片；
- 共享行为契约比共享 UI 源码更适合跨技术实现防漂移；
- 全目录与单 Demo 分层推进比一次建设 99 个 Demo 风险更低。

### 当前未知

- 索引 Schema、投影生成和 Demo loader 的技术方案；
- 参与 BUS-003 基线观察的具体人员和排期；
- 切片验证后是否值得新增组合场景编号；
- 第二个真实项目采用时的差异。

## 6. Gate 影响

本增量改变目录覆盖范围、资产管理方式、首个新切片和价值验证方法，因此必须重新通过 Business Gate。通过后只允许进入索引候选卡与切片 002 的 Specification；不自动批准 Architecture、实现、资产晋升或发布。
