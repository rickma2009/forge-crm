# 数字员工（邮件助手）· 落地方案

> 状态：方案草案（design-draft，待评审）
> 形态：网页版为主 + 飞书 IM 为移动/即时入口，一套后端
> 主任务：邮件阅读与处理（读、归类、摘要、起草、发送），辅以数据记录与处理、消息发送

---

## 一、数字员工能做什么

| 能力层 | 场景 | 是否需要人工确认 |
|---|---|---|
| 只读·打下手 | 读邮件、搜索邮件、归纳要点、整理收件箱 | 否，直接执行 |
| 代写·草稿 | 起草回复、写邮件、生成摘要/周报 | 是，出草稿你确认再发 |
| 代办·发送 | 发送邮件、归档、标记已读/未读、定时发送 | 是，发送前必须人工确认 |
| 数据记录/处理 | 把邮件里的数据记入表格/台账、汇总统计、生成报表 | 涉及写/发送需确认 |
| 消息发送 | 通过飞书发送提醒/通知/汇报 | 群发、对外必须确认 |

**核心原则**：数字员工不替你决策；高风险/对外/不可逆动作一律停在人工确认。

---

## 二、形态决策

| 形态 | 是否采用 | 理由 |
|---|---|---|
| 网页版（主） | ✅ 采用 | 复用现有工作台/RBAC/审计，迭代快 |
| 单独 App | ❌ 不做 | 成本高、推广难，对办公助手收益不成比例 |
| 飞书 IM 入口（辅） | ✅ 采用 | 移动端、即时召唤，像 @ 同事一样使用 |

**结论**：一套后端，网页为主 + 飞书为移动入口，不单独开发 App。

---

## 三、邮件能力设计（主任务）

### 3.1 邮件接入
- 通过邮箱协议/API 接入（IMAP / Exchange / 企业邮箱 API）
- 支持**多账号**：个人邮箱 + 部门共享邮箱（如 support@ / info@）
- 只读拉取 + 写操作（发送/标记）分开授权

### 3.2 邮件处理流水线
```
收件 → 拉取 → 解析(正文/附件/收件人) → 归类 → 摘要 → 进入待办清单
                                                    ↓
                                        （人工确认后）起草回复 / 发送 / 归档
```

### 3.3 核心动作（按可逆性分级）
| 动作 | 说明 | 处理 |
|---|---|---|
| 读/搜索/摘要 | 按主题、发件人、时间检索，提炼要点 | Agent 直接执行 |
| 归类打标 | 自动分类：重要/待办/通知/广告/已处理 | Agent 直接执行 |
| 起草回复 | 基于邮件内容生成回复草稿 | 出草稿，人工确认 |
| 发送邮件 | 最终发送 | **必须人工确认** |
| 归档/标记 | 移入文件夹、标已读/未读 | Agent 直接执行（低风险） |
| 定时发送 | 预约发送时间 | 发送前确认 |

### 3.4 邮件规则（可设置）
用户在"邮件设置"里配置规则，Agent 按规则自动处理：
- **规则维度**：
  - 发件人（白名单/黑名单）
  - 主题/关键词（含"发票""报价""合同"等）
  - 重要程度（高/中/低）
  - 动作（置顶、归档、标记、转给某人、自动摘要）
  - 生效时间（立即 / 指定时段）
- 示例规则：
  - "来自 boss@ 的邮件 → 标记重要 + 摘要推送"
  - "主题含'发票' → 归档 + 记录到台账"
  - "发件人在黑名单 → 直接归档不打扰"

## 四、数据记录与处理（辅任务）

- **记录**：把邮件/会话里的结构化数据（金额、日期、联系人、单号）自动提取，写入表格/台账
- **处理**：汇总统计、去重、生成报表/清单
- **交付形态**：网页内表格 + 飞书表格/文档
- 复用现有 list-view / 字典 / 表格能力

---

## 五、消息发送（辅任务）

- **飞书内发送**：向用户/群/指定人发送提醒、汇报、日报、规则命中通知
- **对外消息**：邮件之外的群发/通知，一律人工确认
- 复用飞书 IM 能力（lark-im）

---

## 六、技术架构

```
┌──────────────────────────────────────────────┐
│ 入口层：网页工作台 + 飞书 IM（@数字员工）      │
├──────────────────────────────────────────────┤
│ 规划层：LLM 意图识别 + 任务拆解 + 状态机       │
├──────────────────────────────────────────────┤
│ 工具层（确定性代码执行，schema 校验）          │
│   ├─ mail：拉取/搜索/摘要/起草/发送/归档       │
│   ├─ data：表格记录/汇总/报表                 │
│   └─ im：飞书消息发送/提醒                    │
├──────────────────────────────────────────────┤
│ 规则引擎：邮件规则设置 + 自动处理 + 定时触发   │
├──────────────────────────────────────────────┤
│ 底座：RBAC(权限) + 审计(留痕) + 记忆/知识库   │
└──────────────────────────────────────────────┘
```

关键点：
- **"想"用模型，"做"用代码**：LLM 只负责规划/起草，工具调用用确定性代码+schema 校验
- **所有操作留审计**：谁、何时、做了什么
- **权限 = 用户权限 ∩ 工具授权**，数字员工绝不越权

## 七、实施路线（MVP 优先）

| 阶段 | 内容 | 说明 |
|---|---|---|
| **P0 MVP** | 邮件只读 + 摘要 + 搜索 + 归类 + 邮件规则 | 低风险、见效快，先打通 |
| **P1** | 起草回复 + 数据记录/台账 + 飞书提醒 | 高价值，人工确认兜底 |
| **P2** | 发送/归档/定时发送 + 数据报表 + 多账号 | 高风险，需更严格确认 |
| **P3** | 主动巡检 + 自动日报 + 智能规则学习 | 定时触发、编排增强 |

## 九、验收要点

1. 邮件只读/搜索/摘要正确，低风险动作无需人工确认
2. 邮件规则可按维度配置、生效正确
3. 起草回复合理，发送/对外动作必须人工确认
4. 数据记录/汇总准确，可追溯来源
5. 权限不越界，所有操作有审计
6. 飞书入口可用，网页与飞书数据一致
