# 多来源 UI 萃取与演示门户业务需求

> 版本：0.1
> 状态：`business-gate-approved`
> 权威来源：`REQSRC-013`；批准证据：`REQSRC-014`

## 1. 定位与业务成果

本增量把验证场扩展为“多来源交互资产的萃取与演示入口”：从用户明确选择的既有系统源码、页面原型和截图中形成可追溯候选，经验证后再回流 `_methodology/`；使用者可通过通用菜单浏览主题、组件、页面模板、交互模式、页面状态和组合场景。

验证场仍不是生产业务系统、低代码平台、真实 IAM 或通用规范事实源。

| ID | 业务成果 | 当前基线 | 本阶段目标 | 证据方向 |
|---|---|---|---|---|
| `BUS-005` | 建立可重复的多来源 UI 萃取方法 | 有来源治理原则和少量扁平报告，缺少每页来源选择 | 每次萃取均有来源选择、版本点、证据矩阵、冲突和复用决定 | 来源包、检查结果和人工评审 |
| `BUS-006` | 建立可供新项目选择的 UI 候选资产 | 有 103 项交互分类和两个模板，主题/组件/页面模板未独立治理 | 候选按主题、组件、页面模板和交互模式分层，正式资产与来源项目解耦 | 候选包、验证切片和成熟度记录 |
| `BUS-007` | 让使用者在统一菜单中浏览与体验资产 | 当前 Lab 是分类目录，未形成通用模板展示门户 | 通过“业务/资产菜单 + 底部系统管理”壳层连接经登记的 Demo | 菜单任务、路由任务和浏览器证据 |
| `BUS-008` | 验证菜单、页面和操作级模拟权限 | 当前 Demo 没有登录和账号 | `admin` 可访问全部已登记能力，受限账号能证明隐藏、拒绝和只读路径 | capability 矩阵、自动测试和浏览器任务 |

本阶段不预设时间节省比例或业务采用提升值。真实项目采用和业务效果仍需独立证据。

## 2. 用户与核心任务

| 角色 | 核心任务 | 责任边界 |
|---|---|---|
| 产品/需求分析人员 | 选择来源，查找页面模板，体验关键交互，形成项目采用建议 | 不批准通用资产晋升 |
| UI/交互设计人员 | 比较主题、密度、结构、状态和适用边界 | 不以截图替代行为证据 |
| 前端开发人员 | 获取字段、动作、状态、权限和接入契约 | 不把 Demo 当生产组件包 |
| 方法论维护者 | 评审来源、候选、验证证据和晋升 | 当前由 Rick 承担人工决策 |
| Demo 管理员 | 以 `admin` 体验全部菜单、页面和操作 | 仅是虚构演示身份 |
| 受限演示用户 | 验证菜单隐藏、路由拒绝、页面只读和操作禁止 | 不映射真实组织角色 |

核心任务链：

```text
明确本次页面目标
→ 选择具体来源与版本
→ 查看候选证据和适用边界
→ 从菜单进入通用页面 Demo
→ 切换模拟身份验证允许/拒绝路径
→ 形成采用、调整、拒绝或新增模式的项目建议
```

## 3. 多来源萃取需求

| ID | 需求 | 验收方向 |
|---|---|---|
| `REQ-301` | 每个来源必须登记类型、位置、版本、授权/敏感边界和状态 | 可定位且不静默覆盖旧来源 |
| `REQ-302` | 每次生成页面前必须形成来源选择记录，列明选中来源、未选来源、具体文件、保留项和排除项 | 页面决定可追溯到明确输入 |
| `REQ-303` | 源码、路由、样式、配置和测试优先于截图；截图只用于视觉核对 | 不从截图补造隐藏行为 |
| `REQ-304` | 来源冲突必须并列记录，不得自行合并成“最佳版本” | 冲突、影响和待决策项明确 |
| `REQ-305` | 用户新增的 `_ref/gscrm-sdd/` 只作为候选来源；没有后续明确指令和页面选择时不得参与萃取 | 当前候选不包含其页面结论 |
| `REQ-306` | 来源项目名称和业务专属内容仅保留在证据层；正式候选的名称、字段、菜单和文案必须去来源项目化 | 候选目录无来源项目术语 |

## 4. UI 资产与字段配置需求

| ID | 需求 | 验收方向 |
|---|---|---|
| `REQ-307` | 交互模式继续使用现有 EPM 分类；主题、组件和页面模板使用独立候选资产模型 | 不手改或污染现有 103 项索引 |
| `REQ-308` | 页面由主题、页面模板、交互模式和字段配置组合，不用单一“风格编号”隐含全部行为 | 每个 Demo 可显示组合清单 |
| `REQ-309` | 字段配置分别描述语义、展示、查询、表单和数据映射 | 模板不直接绑定数据库字段 |
| `REQ-310` | 来源复刻版与建议优化版分别保存，差异、理由和证据明确 | 不覆盖来源事实 |
| `REQ-311` | 候选先在验证场形成实现/交互证据，未经真实项目采用不得宣称 `project-adopted` 或 `business-validated` | 状态与证据一致 |

## 5. 演示门户与导航需求

| ID | 需求 | 验收方向 |
|---|---|---|
| `REQ-312` | 演示门户使用稳定的深色左侧导航壳层，包括品牌区、菜单搜索、主菜单、底部管理分组和折叠控制 | 结构与候选契约一致 |
| `REQ-313` | 主菜单使用通用分类：概览、基础规范、基础组件、页面模板、交互模式、页面状态和组合场景 | 不出现来源项目菜单文字 |
| `REQ-314` | “系统管理”固定在主菜单下方并以分隔线区分，包含用户、角色、权限策略、菜单、日志和资源目录等通用入口 | 长主菜单滚动时仍可发现管理入口 |
| `REQ-315` | 页面入口来自受检查的菜单与页面 registry；未登记或无 Demo 的页面不得伪装成完整可运行功能 | 菜单、路由和 Demo 状态一致 |
| `REQ-316` | 首个新增候选切片为“带底部管理分组的企业导航壳层”，以 `UID-001` 候选包作为来源输入 | 先完成一个端到端验证闭环 |

## 6. 模拟身份与权限需求

| ID | 需求 | 验收方向 |
|---|---|---|
| `REQ-317` | Demo 初始化 `admin` 和至少一个受限演示账号 | 两类身份均可重复进入确定性初始状态 |
| `REQ-318` | `admin` 通过统一 role-to-capability 绑定获得 Demo 当前登记的全部 capability，不使用页面内硬编码绕过 | 新增 capability 后可被一致纳入 |
| `REQ-319` | 菜单、路由、页面只读状态和页面操作使用同一 capability 语义 | 不出现“菜单隐藏但路由/操作仍放行” |
| `REQ-320` | 受限账号必须覆盖至少一个菜单隐藏、一个直接路由拒绝、一个页面只读和一个操作禁止场景 | 权限判断存在反例证据 |
| `REQ-321` | Demo 权限只用于前端交互验证，不连接真实账户数据库，不声称生产服务端授权或安全审计已完成 | UI 明示模拟边界 |

## 7. 非功能与治理要求

| ID | 要求 | 验证方向 |
|---|---|---|

| `NFR-304` | 菜单展开、搜索、折叠、路由拒绝和主要操作支持键盘及可访问名称 | 自动测试和浏览器检查 |
| `NFR-305` | 每个候选可定位来源、版本、事实/推断、冲突、适用边界和成熟度 | 链接及登记册检查 |
| `NFR-306` | 现有切片 001/002 的实现、Gate 和 Release 状态保持独立，不被本增量覆盖 | 项目状态与历史文件一致 |

## 8. 范围边界

### In Scope

- 多来源页面/原型的登记、选择、取证、冲突和候选萃取；
- 去来源项目化的主题、组件、页面模板、交互模式和字段配置候选；
- 带主菜单与底部系统管理分组的导航壳层；
- 浏览器内模拟登录、`admin` 与受限账号、capability 判断；
- 菜单、路由、只读和操作权限演示；
- 首个 `UID-001` 导航切片及相关测试、浏览器证据和回流评审。

### Out of Scope

- 真实账号数据库、密码治理、生产会话、审计和服务端 IAM；
- 自动读取或融合全部参考项目；
- 一次性实现全部页面模板或 103 个 Demo；
- 在线低代码编辑器、Schema 全自动页面渲染器和生产组件包；
- 修改 `_ref/` 中的来源项目；
- 在没有真实项目证据时宣称通用资产已完成业务验证或发布。

## 9. 人工责任与 Gate
