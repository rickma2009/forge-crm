# 企业数据库治理与组织员工权限方案决策

## 用户原始请求

> [组织员工角色权限-方案设计.md] 这个针对用户、权限等功能一个文档，通过这个文档需要完善数据库、数据表的设计规范。同时也是关于系统管理的公共功能的设计方案，可供其他系统通用的功能，这部分的功能为了会放在系统管理部分。请从企业管理信息系统的角色，你看看是否还有问题，这样设计是否合理。

> 同时，针对以上对数据表的规范，需要建立一个数据库规范文件，作为后面其他或库的约束指引，在 Agents.md 说明要引用符合此规范。在数据库规范中，也约定哪些是公共、系统类的表可作为其他系统直接复用，哪些具体业务应用类的，只与具体的业务有关。

> 业务领域的，如果是公共类的基本信息，可以 dim 或者公共作为前缀，比如：客户、供应商、产品等，这些物料是 crm 还是 scm 或 mes 都会使用的，可以不限定业务域前缀。包括订单可能在多个系统都会有，按你的理解，不限定系统是否 OK？只按业务实体命名，比如：销售订单、采购订单，直接为 sales_order、purchase_order 等。其余按建议。

Q26 经追加讨论后确认的分类原则：

- 平台能力使用 `sys_`；
- 组织员工使用 `org_`；
- 跨系统企业主数据使用 `mdm_`，`dim_` 仅用于分析维度；
- 销售订单、采购订单等稳定业务事实按业务实体命名，例如 `sales_order`、`purchase_order`，不绑定 CRM/SCM/MES 应用名；
- 集成映射和导入暂存分别使用 `int_`、`stg_`；
- 跨系统共享数据由唯一责任模块管理，其他系统通过 API 或事件使用，不允许多个系统绕过责任模块任意直写同一业务表。

## 授权边界

本来源批准完善方案文档、建立数据库治理规范、建立 PostgreSQL/Prisma Profile 约定、更新 AGENTS 路由以及配套模板和自动检查。它不批准立即变更生产数据库、连接外部系统数据库、执行物理表迁移、实现组织员工业务功能、部署或发布。
