# 销售交互增强能力方案设计

> 状态：design-draft（待评审，评审通过后按切片进入 Business / Specification / Architecture Gate）
> 适用范围：Forge CRM 销售业务层的增强交互能力
> 对标：纷享销客、销售易、Salesforce 的销售过程管理与智能推荐能力
> 决策来源：REQSRC-090（Forge CRM 复用与团队赋能目标）

## 1. 目标与原则

本方案为 Forge CRM 引入六项对标主流 CRM 的销售交互能力：**看板视图、客户360聚合、活动时间轴、记录协作流、线索评分、智能推荐**。目的是让销售过程"看得清、跟得紧、转得快"，并沉淀为可被其他模块复用的交互资产。

核心原则：

1. **过程数据优先于管理报表**：先让销售过程（阶段、活动、协作、评分）落库、可追、可看，驾驶舱/BI 是后续派生，不阻塞本期。
2. **交互资产分层**：六项能力拆成「基础数据底座 + 可复用组件 + 业务页面」三层；组件沉淀到公共层，业务页只在销售域装配。
3. **AI 是增强不是门槛**：线索评分/智能推荐一期用可解释的规则+加权（用户可手动覆盖），规则引擎跑通后再逐步接模型，避免"黑盒评分"不可信。
4. **不新增遗留前缀**：新增表沿用 `sd_`（销售）前缀，小写 `snake_case`，≤32 字符，符合 `_methodology/11-数据库设计与数据分层规范.md`。
5. **沿用既有底座**：列表/视图走既有 list-view；详情走既有 DetailWorkspace/DetailTabs；权限走 RBAC；不引入 antd。

## 2. 六项能力总览

| 能力 | 对标特色（纷享/销售易/SF） | 本项目现状 | 本期价值 | 优先级 |
|---|---|---|---|---|
| 看板视图 | 商机按阶段拖拽流转、每列金额汇总 | 商机已有 `stage`/`probability`/`expectedAmount`，list-view 仅表格 | 销售漏斗一眼可见，拖拽即推进 | P0 |
| 客户360聚合 | 一客户聚合联系人/商机/报价/回款/活动/工单 | 客户详情已有 Tab，但未聚合销售事实 | 决策时不用跨页翻查 | P0 |
| 活动时间轴 | 电话/邮件/拜访/跟进/审批统一时间线 | 无统一活动模型 | 过程留痕，跟进不脱节 | P0 |
| 记录协作流 | 记录上 @提及 + 评论 + 附件（Chatter） | 无 | 团队在记录上下文内协作 | P1 |
| 线索评分 | 按行为加权打分、高价值线索优先 | 无线索模型，有 `opportunity-analysis` 雏形 | 高价值机会优先投入 | P1 |
| 智能推荐 | 相似客户/下一步建议/赢单预测 | 有 `ai-analysis` 模块 | 缩短销售决策路径 | P2 |

## 3. 基础数据底座（先行）

六项能力共享一套"销售过程活动"数据底座。新增表如下：

### 3.1 `sd_sales_activity`（销售活动）

记录统一活动（拜访、电话、邮件、跟进、备注），作为时间轴与协作流的共同数据源。

| 字段 | 说明 |
|---|---|
| `id` | UUID 主键 |
| `tenant_id` / `application_id` | 租户与应用边界 |
| `subject_type` | `CUSTOMER` / `OPPORTUNITY` / `QUOTATION` / `CONTACT` |
| `subject_id` | 关联对象 id（含 `*` 通配表示全局） |
| `activity_type` | `VISIT` / `CALL` / `EMAIL` / `FOLLOW_UP` / `REMARK` / `SYSTEM` |
| `content` | 活动正文（≤4000） |
| `activity_time` | 活动发生时间 |
| `owner_id` / `owner_name` | 发起人 |
| `status` | `ACTIVE` / `DISABLED` |
| 审计字段 | `created_at` / `updated_at` / `version` |

### 3.2 `sd_activity_mention`（协作流提及）

记录协作流中的 @提及 与 订阅通知。

| 字段 | 说明 |
|---|---|
| `id` | UUID 主键 |
| `activity_id` | 关联 `sd_sales_activity` |
| `mention_user_id` | 被提及用户 |
| `read_at` | 已读时间（空=未读） |
| `status` | `ACTIVE` / `DISABLED` |

### 3.3 `sd_lead`（线索，为评分/推荐铺垫）

独立于商机的早期线索对象，可升级为商机。

| 字段 | 说明 |
|---|---|
| `id` | UUID 主键 |
| `lead_code` | 线索编号（按单据编号规范生成） |
| `lead_name` / `company` / `contact_name` / `contact_phone` / `contact_email` | 线索基本信息 |
| `source` | 来源渠道（字典） |
| `score` | 评分（0-100，规则引擎产出） |
| `score_detail` | 评分明细（JSON，可解释） |
| `score_reason` | 评分规则命中说明 |
| `owner_id` | 负责人 |
| `stage` | `NEW` / `QUALIFIED` / `CONVERTED` / `LOST` |
| `status` | `ACTIVE` / `DISABLED` |
| 审计字段 | `created_at` / `updated_at` / `version` |

## 4. 能力一：看板视图

### 4.1 场景
销售经理/销售员进入商机列表，以"阶段"为列展示商机卡片，通过拖拽把商机从"初步接触"推进到"赢单"，每列顶部汇总预计金额与数量。

### 4.2 交互设计
- **布局**：顶部沿用 list-view 的"视图选择/设置"工具栏；下方由表格切换为看板（视图类型 `TABLE` / `KANBAN` 存入个人视图）。
- **列**：默认按 `opportunity_stage` 的 `sort_no` 分列；列头显示阶段名 + 赢率 + 金额小计。
- **卡片**：显示商机名称、客户、预计金额、负责人、把握度、预签日期；卡片即详情入口（点击进详情，遵循 `UI-LIST-01`）。
- **拖拽**：拖卡片到目标列→更新 `stage_id` 并触发阶段变更（可选弹窗确认/填丢单原因）。
- **空态/权限**：无拖拽权限时卡片不可拖；无查看权限列不显示。

### 4.3 数据与接口
- 复用 `opportunity` 现有 `stage_id`/`stage_name`/`expected_amount`/`owner`。
- 新增接口：`GET .../opportunities/kanban`（按阶段分组+列汇总）、`PATCH .../opportunities/:id/stage`（推进阶段，含校验与并发 version）。

### 4.4 组件
`KanbanBoard`（公共组件，沉淀 `common/KanbanBoard.md`）：
- 入参：列配置（key/title/聚合）、卡片数据、拖拽回调、权限、只读开关。
- 能力：列汇总、拖拽、空态、卡片操作菜单（编辑/删除）、横向滚动。

## 5. 能力二：客户360聚合

### 5.1 场景
在客户详情一屏内聚合：基本信息、联系人、地址、商机、报价单、销售活动、协作流、评分，销售无需跨页翻查。

### 5.2 交互设计
- 沿用 `DetailWorkspace`：第一行返回箭头 + 客户名称 + 状态/操作；下方 Tab 下划线样式。
- **Tab 规划**：客户基本信息 | 联系人 | 商机 | 报价单 | 活动时间轴 | 协作/评论（权限控制 Tab 可见性）。
- 每一 Tab 内聚合列表均以对应业务编码/名称为详情链接（遵循 `UI-LIST-01`）。

### 5.3 数据
聚合 = 各业务域只读汇总接口（`GET .../customers/:id/overview` 返回各 Tab 的汇总 count + 最新 N 条），明细仍走各业务域原接口，不建冗余宽表。

## 6. 能力三：活动时间轴

### 6.1 场景
在客户/商机详情的时间轴 Tab 内，按时间倒序展示所有拜访、电话、邮件、跟进、系统变更，形成完整过程留痕。

### 6.2 交互设计
- 竖排时间线：左侧时间刻度 + 右侧活动卡片（类型图标、内容、发起人、时间）。
- 支持：按类型筛选、折叠长文本、点击活动进详情、从时间轴直接新增活动。
- 系统事件（阶段变更、状态变更）以灰色 `SYSTEM` 类型自动写入，只读。

### 6.3 数据
- 读：`GET .../activities?subjectType&subjectId`（基于 `sd_sales_activity`）。
- 写：`POST .../activities`（拜访/电话/跟进等）；系统事件由服务端在商机/报价状态变更时自动落库（`activity_type=SYSTEM`）。

### 6.4 组件
`ActivityTimeline`（公共组件，沉淀 `common/ActivityTimeline.md`）。

## 7. 能力四：记录协作流

### 7.1 场景
销售在客户/商机详情内 @同事、评论、上传附件，同事收到提醒，在记录上下文内完成讨论，无需切到 IM。

### 7.2 交互设计
- 详情内"协作/评论"区：输入框（支持 `@` 联想用户）+ 发送；每条评论可回复。
- 被提及人收到系统待办/通知（可接 cron 提醒或站内信），未读红点。
- 附件复用既有 `AttachmentPanel`。

### 7.3 数据
- 评论即 `sd_sales_activity`（`activity_type=COMMENT`）；@提及 存 `sd_activity_mention`。
- 接口：`POST .../activities`（带 mentions）、`GET .../activities/:id/mentions`、`PATCH .../mentions/:id/read`。

## 8. 能力五：线索评分

### 8.1 场景
对线索按"信息完整度 + 来源质量 + 活跃度 + 金额潜力"加权打分，销售优先跟进高分线索。

### 8.2 规则引擎（一期，可解释）
`score = Σ(规则权重 × 命中分)`，规则可配置（存系统参数或专用表 `sd_score_rule`）：

| 维度 | 规则示例 | 权重 |
|---|---|---|
| 信息完整度 | 手机+邮箱+公司均填 +30 | 30 |
| 来源质量 | 来源=官网/推荐 +20 | 20 |
| 活跃度 | 近7天有活动 +20 | 20 |
| 金额潜力 | 预估金额≥阈值 +30 | 30 |

- 评分在创建/更新/活动写入时由服务端重算；`score_detail` 存命中明细便于解释。
- 人工可覆盖最终评分（`manual_score` 优先）。

### 8.3 接口
`POST .../leads/:id/recalculate`、`GET .../leads`（按 score 排序）、规则配置接口。

## 9. 能力六：智能推荐

### 9.1 场景
基于规则与历史数据给销售"下一步建议"：该客户该先推哪个产品、哪类机会赢率高、相似客户参考。

### 9.2 一期（规则+轻量分析）
- 复用既有 `ai-analysis` / `opportunity-analysis` 模块，产出**建议卡片**（非黑盒）：
  - 下一步建议：根据阶段 + 最近活动时间，提示"跟进已超 X 天"。
  - 相似客户：按行业/规模/产品线相似度推荐可参考案例。
  - 赢率提示：按阶段赢率 + 把握度给"预计成交概率"。
- 二期（可选）再接入模型做线索评分学习与赢单预测。

### 9.3 交互
客户/商机详情内"智能建议"面板：卡片式展示建议 + 理由 + "采纳"按钮（采纳写回活动）。

## 10. 与既有底座的关系

| 底座 | 复用方式 |
|---|---|
| list-view | 看板作为视图类型扩展，视图/列配置沿用个人视图持久化 |
| DetailWorkspace/DetailTabs | 客户360、活动时间轴、协作流作为详情 Tab |
| RBAC / access | 六项能力均按菜单 action 授权（如 `opportunity.kanban`、`customer.overview`） |
| 字典 system-parameter | 活动类型、线索来源、评分规则配置走字典/系统参数 |
| AttachmentPanel | 协作流附件复用 |
| ai-analysis / opportunity-analysis | 智能推荐一期的建议引擎复用 |

## 11. 实施路线（切片）

### 切片 A：看板视图 + 客户360（P0，先做，价值最高）
- 数据：无新表（看板复用商机；360 走只读聚合接口）。
- 组件：`KanbanBoard`；客户详情扩展 Tab。
- 验收：商机可拖拽推进阶段；客户详情一屏聚合商机/报价/活动。

### 切片 B：活动时间轴 + 协作流（P0~P1）
- 数据：建 `sd_sales_activity`、`sd_activity_mention`。
- 组件：`ActivityTimeline`、协作输入框 + @联想。
- 验收：客户/商机过程留痕可回看；@ 同事收到提醒。

### 切片 C：线索评分（P1）
- 数据：建 `sd_lead`、`sd_score_rule`。
- 验收：线索可评分、可解释、可人工覆盖。

### 切片 D：智能推荐（P2）
- 复用 `ai-analysis`；验收：建议卡片可解释、可采纳。

## 12. 风险与待确认

| 事项 | 说明 | 建议 |
|---|---|---|
| 活动/评论是否全局搜索 | 量大后影响性能 | 先按 subject 索引，后续加全文检索再考虑 |
| 线索与商机是否强关联 | 线索转商机后是否保留线索 | 保留线索只读归档，关联 `converted_opportunity_id` |
| 通知通道 | 站内信/待办/企微？ | 一期站内待办（复用 lark-task 思路），二期再接 IM |
| 评分规则是否让用户配置 | 配置化增加复杂度 | 一期内置规则+系统参数可调，界面配置放二期 |

## 13. 验收要点（总）

1. 看板拖拽变更阶段有权限控制与并发保护，列汇总金额正确。
2. 客户360各 Tab 数据来源可追溯，不建冗余宽表。
3. 时间轴统一活动模型，系统事件自动留痕且只读。
4. 协作流 @ 提醒可达、未读可见，附件可上传。
5. 评分可解释（detail 可读）、可人工覆盖、规则可调。
6. 智能建议卡片含理由，采纳写回活动，不出现无依据的黑盒结论。
