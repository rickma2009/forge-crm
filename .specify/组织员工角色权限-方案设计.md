# 组织、员工、用户、角色与权限公共能力方案

> 状态：design-reviewed，等待独立 Business / Specification / Architecture Gate 后方可实施  
> 决策来源：`REQSRC-043`  
> 适用范围：企业管理信息系统的公共系统管理能力，不包含具体业务数据权限

## 1. 目标与原则

本方案建立可被 CRM、SCM、MES 等应用共同采用的组织、员工、账号和 RBAC 基线。公共能力在产品导航中可以位于“系统管理”，但数据库仍按真实领域划分：平台安全能力使用 `sys_`，组织员工使用 `org_`。

核心原则：

1. 组织和员工是企业级共享主数据，不按应用 `system_code` 重复建档。
2. 租户是企业数据边界；应用是菜单、角色和权限边界。
3. 员工、登录账号相互独立；员工可以没有账号，外部账号和系统账号可以没有员工。
4. 权限点是服务端授权事实，菜单和按钮只是权限点的界面投影。
5. 用户只能通过角色获得权限，不支持个人直接授权；多角色权限取允许集合的并集，不提供显式拒绝。
6. 角色不使用伪层级；仅需展示分类时使用角色组，不暗示权限继承。
7. 所有跨系统共享数据都必须有唯一责任模块，其他应用通过服务接口或事件使用，不能任意直写责任模块的数据表。

## 2. 领域边界

| 层级 | 表名前缀/命名 | 本方案中的内容 | 复用方式 |
|---|---|---|---|
| 系统平台 | `sys_` | 租户、应用、账号、角色、权限、菜单、审计 | 企业应用基础模块 |
| 组织主数据 | `org_` | 组织单元、员工、雇佣周期、任职、岗位、负责人 | 可选公共模块 |
| 共享主数据 | `md_` | 客户、供应商、产品等，不属于本方案 | 企业主数据责任模块负责 |
| 业务交易 | `sd_`、`scm_`、`rd_`、`fin_` | 销售、供应链制造、研发、财务事实，不属于本方案 | 对应业务域能力负责 |
| 集成/暂存/分析 | `int_`、`stg_`、`dim_`、`fact_` | 外部标识、导入暂存、数仓维度与事实 | 不作为在线业务事实源 |

完整数据库规则见 [`_methodology/11-数据库设计与数据分层规范.md`](../_methodology/11-数据库设计与数据分层规范.md)。
所有物理表名和字段名统一使用小写 `snake_case`，且均不得超过 32 个字符。

## 3. 总体关系

```text
sys_tenant
├── sys_application
├── org_unit
├── org_employee
│   ├── org_employment
│   └── org_employee_assignment ── org_position / org_unit
└── sys_user ──(optional unique employee_id)── org_employee

sys_application
├── sys_role_group ── sys_role
├── sys_permission
├── sys_menu ── sys_menu_action
└── sys_role ── sys_role_user ── sys_user
              └─ sys_role_permission ── sys_permission
```

所有租户内关系必须通过复合约束阻止跨租户引用；应用内关系还必须阻止跨应用引用。

## 4. 系统平台表

### 4.1 `sys_tenant`

企业数据边界。即使当前只有一个企业，也初始化默认租户，不使用应用编码代替租户。

关键字段：`id`、`tenant_code`、`tenant_name`、`status`、审计字段。  
关键约束：`tenant_code` 全局唯一且发布后稳定。

### 4.2 `sys_application`

登记可授权的应用系统。

关键字段：`id`、`tenant_id`、`application_code`、`application_name`、`status`、审计字段。  
关键约束：`(tenant_id, application_code)` 唯一。

### 4.3 `sys_user`

登录账号，不等同于员工。

| 字段 | 说明 |
|---|---|
| `id` | UUID 内部主键 |
| `tenant_id` | 所属企业 |
| `account` / `normalized_account` | 展示账号及规范化账号 |
| `user_type` | `EMPLOYEE`、`EXTERNAL`、`SYSTEM` |
| `employee_id` | 可空；员工型账号必须填写，并设置唯一约束 |
| `auth_source` / `external_subject` | 本地或外部认证身份 |
| `status` | `ACTIVE`、`DISABLED`、`LOCKED` |
| `password_hash` | 仅本地认证需要；不进入日志和接口 |
| 审计字段 | 创建、修改及版本信息 |

约束：

- `(tenant_id, normalized_account)` 唯一；
- `employee_id` 不在 `org_employee` 反向重复保存；
- 员工、用户必须属于同一租户；
- 不得通过账号名 `admin` 在代码中绕过权限检查。

### 4.4 `sys_role_group` 与 `sys_role`

`sys_role_group` 只负责角色展示分类；`sys_role` 不设置 `parent_id`，不提供隐含继承。

`sys_role` 关键字段：`tenant_id`、`application_id`、`role_group_id`、`role_code`、`role_name`、`role_type`、`status`、`is_system`、审计字段。

约束：

- `(tenant_id, application_id, role_code)` 唯一；
- 一个角色只属于一个应用；
- 每个有效应用恰好有一个不可删除的系统管理员角色；
- 跨系统授权通过给用户分配多个应用角色完成，不建立跨应用普通角色。

### 4.5 `sys_role_user`

用户和角色的有效期关联。

关键字段：`role_id`、`user_id`、`status`、`effective_at`、`expires_at`、`granted_by`、`granted_at`。  
有效区间统一使用 `[effective_at, expires_at)`；角色和用户必须属于同一租户。

### 4.6 `sys_permission`

权限点是前端与服务端共同引用的稳定授权事实。

| 字段 | 说明 |
|---|---|
| `tenant_id`、`application_id` | 权限作用域 |
| `permission_code` | 如 `customer.view`、`role.permission.assign` |
| `permission_name` | 管理端显示名称 |
| `resource_code`、`action_code` | 资源与动作的结构化表达 |
| `status` | 有效/停用 |
| `is_system` | 是否由系统初始化和维护 |

约束：`(tenant_id, application_id, permission_code)` 唯一；权限编码发布后原则上不可直接改名。

### 4.7 `sys_role_permission`

角色对权限点的显式授权。

关键字段：`role_id`、`permission_id`、`granted_by`、`granted_at`。  
约束：同一角色和权限点只能存在一条有效授权；角色与权限点必须属于同一租户、同一应用。

新增权限点后，由迁移或权限发布服务在事务中为系统管理员角色补齐显式授权，并执行完整性校验。

### 4.8 `sys_menu` 与 `sys_menu_action`

菜单和操作负责界面组织，不再承担唯一的安全语义。

- `sys_menu` 按租户和应用形成同作用域树；父子不能跨租户、跨应用；使用 `parent_id`，不持久化易漂移的 `level`。
- PAGE 菜单引用查看权限点；目录可不绑定权限或按其可见子项计算。
- `sys_menu_action` 引用对应权限点；服务端 API 使用相同 `permission_code` 校验。
- 新页面默认只登记 `view`；新增、修改、删除、导入、导出、审核等必须按真实业务能力显式声明。

### 4.9 `sys_audit_log`

结构化记录安全和组织关键操作，至少包含租户、应用、操作者、动作、目标类型、目标 ID、变更摘要、请求来源、关联 ID 和发生时间。审计日志不得记录密码、Token、Cookie 或不必要的个人敏感信息。

## 5. 组织员工表

### 5.1 `org_unit`

统一表示公司、事业部、部门和团队。

关键字段：`tenant_id`、`parent_id`、`unit_code`、`unit_name`、`unit_type`、`sort_no`、`status`、有效期和审计字段。

约束：

- `(tenant_id, unit_code)` 唯一；
- 父子必须属于同一租户；
- 事务内进行防环校验；
- `level` 动态计算，不作为权威字段；
- 不使用 `is_sales`、`is_rd`、`is_bu` 等固定布尔字段。

组织形态由 `unit_type` 表达；销售、研发等多维业务属性通过 `org_unit_tag`、`org_unit_tag_relation` 扩展。

### 5.2 `org_employee`

员工稳定主体，不直接保存当前部门、岗位、入离职日期或账号 ID。

关键字段：`tenant_id`、员工显示姓名及必要档案字段、状态、联系方式、审计字段。联系方式标记为敏感数据，普通列表、日志和导出不得默认完整输出。

### 5.3 `org_employment`

记录工号和每次雇佣周期，支持离职后再次入职。

关键字段：`employee_id`、`employee_no`、`employment_type`、`status`、`effective_at`、`expires_at`、审计字段。  
约束：工号在批准的企业作用域内唯一；有效期使用半开区间。

### 5.4 `org_position`

岗位主数据。关键字段：`tenant_id`、`position_code`、`position_name`、`status`、审计字段。任职记录可以保留岗位名称快照，避免历史随岗位改名而失真。

### 5.5 `org_employee_assignment`

记录主职和兼职。

关键字段：`employee_id`、`org_unit_id`、`position_id`、`position_name_snapshot`、`assignment_type`、`is_primary`、`status`、`effective_at`、`expires_at`、审计字段。

约束：

- 同一员工同一时刻最多一条有效主职；
- 允许多条有效兼职；
- 同一员工、组织、岗位和任职类型的有效期不得重叠；
- 主职部门不自动等于业务数据权限范围。

### 5.6 `org_unit_leader`

用带有效期的关系表记录负责人、代理负责人等，不在组织表保存单一 `leader_id`。

关键字段：`org_unit_id`、`employee_id`、`leader_type`、`effective_at`、`expires_at`、审计字段。

### 5.7 员工离职与账号

雇佣关系结束时，不删除用户。员工型账号默认禁用、现有 Session/Token 失效，并记录安全审计；经授权的例外必须显式登记。外部账号和系统账号不受员工离职规则自动影响。

## 6. 授权计算与安全不变量

```text
sys_user
  → 有效 sys_role_user
  → 同应用有效 sys_role
  → sys_role_permission
  → 有效 sys_permission
```

- 多角色权限取并集，不提供 DENY 或角色优先级。
- 权限数据库不可用时必须默认拒绝，不能退回“显示全部”或放行写操作。
- 前端隐藏菜单和按钮只改善体验；服务端必须使用同一权限点重新授权。
- 初始化 `admin` 通过加入每个应用的系统管理员角色获得权限，不使用用户名特例。
- 本期不实现行级和列级数据权限，但模型不得把主职部门误当成数据权限。

## 7. 页面规划

以下页面可以位于“系统管理”菜单，但页面位置不改变数据领域边界：

| 页面 | 核心能力 |
|---|---|
| 企业与应用 | 租户基础信息、应用登记与状态 |
| 组织架构 | 组织树、类型、标签、负责人和有效期 |
| 员工管理 | 员工档案、雇佣周期、主职/兼职、账号启用 |
| 岗位管理 | 岗位主数据维护 |
| 用户管理 | 账号、认证来源、员工绑定、启停、会话撤销 |
| 角色管理 | 角色组、角色、成员有效期和权限点授权 |
| 菜单与权限 | 菜单、操作与稳定权限点的映射 |
| 审计日志 | 安全和组织关键变更查询 |

页面操作权限按能力显式登记，不自动为所有页面生成增删改查和导出。

## 8. 现有表迁移范围

若后续 Architecture Gate 批准物理迁移，必须以保留数据的正式迁移完成，不删除重建，不长期双写。范围至少包括：

| 现有前缀 | 目标前缀 | 典型内容 |
|---|---|---|
| `iam_*` | `sys_*` | 用户、角色、成员、角色权限、角色列表视图 |
| `ui_*` | `sys_*` | 菜单、操作、系统/用户列表视图及偏好 |

迁移前必须形成完整映射、兼容窗口、备份恢复、前滚修复和集成测试方案。已应用 migration 不得改写。当前文档不等于已经批准或执行迁移。

## 9. 不做项

- 行级、列级数据权限；
- 角色权限继承和显式拒绝；
- 复杂矩阵组织的多父级组织节点；
- 完整薪酬、考勤、绩效等人力资源功能；
- 多个应用直接写公共主数据或交易表；
- 生产迁移、部署和外部数据库连接。

## 10. 后续 Gate 与实施顺序

1. 将本设计转换为正式需求包，明确角色、页面行为、状态流转和验收标准；
2. Business Gate 确认公共能力范围与业务责任；
3. Specification Gate 确认可观察行为和失败边界；
4. Architecture Gate 批准物理表、迁移、API、事务与兼容方案；
5. 创建 Tasks 后再实施 Prisma、contracts、server、web、Seed 和测试；
6. Release Gate 以真实空库迁移、约束、授权、故障和浏览器证据验收。

本次确认只授权文档和治理资产完善，不代表上述功能或数据库迁移已经完成。
